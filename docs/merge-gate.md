# The merge-gate procedure (recheck, record marks, protected branches)

The procedure to run when `bun scripts/merge-gate.ts <PR> [--allow-large] [--repo <owner/name>]` returns stop, and the marks to leave on the PR. The output is JSON, `{ verdict, impact, reasons, ask, recheck, notes? }`; exit 0 = merge, 1 = stop, 2 = could not decide (never treated as merge). The rules of the verdict are in `scripts/merge-gate.ts`. The prompts of the process Tasks and the `reasons` sentences of merge-gate point at the sections of this document.

## When to run local CI and how it counts

In a repository where Actions does not start (a job with 0 steps, or a run that stays `queued`) or has no run (a case where every run was skipped counts the same), run `bun scripts/local-ci.ts <PR>` only at the following times (the skill's `<ローカル CI>`; for a Task of another repository, `otherRepoRules` hands over this section):

- **When**: once, on the top PR of the stack, after the review findings of every PR in the stack have been handled and before the recheck. A single PR is its own top. Do not run it in the middle of a review, per PR, or between merges
- **Running again**: run it once more on the top only when the diff of some PR has changed (a fix commit, or a conflict resolved by a manual rebase). Do not run it again for GitHub's automatic rebase after a lower PR is merged (the head sha changes but the diff is the same), nor for the base (main) moving forward. When the newest result of the top PR is an earlier pass and only fixes were added after it, the rerun is an incremental run (see "Tests in the affected scope" below)
- **How it counts** (merge-gate's `localCiOf`): from the PR, walk up through the open PRs whose base is the head branch to find the top (if there are 0 or 2 or more above, that PR is the top). If the newest of the top PR's `[local-ci]` results is a pass, and every commit of this PR now (from the merge-base with the current tip of the base branch to the head) is in that pass's head with the same diff (`git cherry <pass の head> <PR の head> <merge-base>` has no `+` line, and any merge commit among them is in the pass head's history as it is), this PR's CI is done. A run that has not started (`queued`, `waiting`, `requested` or `pending`, that is, not yet `in_progress`) counts the same with that pass; an `in_progress` run does not count and stays unfinished. The automatic rebase after a lower PR is merged (the sha changes, the diff of each commit is the same) counts; a fix commit or a conflict resolution that changed the diff does not. If the newest is a fail, or some commit is not included, a reason to rerun on the top follows the CI reason. Only the first line of the mark is read, so a pass whose only content is a first line, written by another repository's copy of local-ci, counts the same. merge-gate fetches the commits it needs for the verdict (the pass's head, the PR's head, the tip of the base branch) without writing refs in the working tree it ran in (from `https://github.com/<owner>/<name>.git`). If it is not a git working tree, or the fetch fails, it does not decide (exit 2)
- **A pass after subtracting known failures**: when local CI subtracts the registered known failures (`known-failures.json`, read from the base; see "Known failures" in `docs/design/local-ci.md`), its result is still `[local-ci] pass <head sha> base=<base sha>` and counts like any other pass. The merge gate asks for no merge outside the gate because of it
- **Why the base is not compared**: conflicts with other PRs are stopped by `mergeStateStatus`. A defect that appears only when separate PRs are combined is found by the tag CI after the merge (the "Tag CI" section of `docs/design/releases-and-rescue.md`)
- When a PR is stacked on top later, run on the new top (the previous top's pass does not contain that PR)
- **Tests in the affected scope**: only the `bun test` step is narrowed; every other step runs. Run on the top of the stack, the selection is made from the sum of the changes of all the PRs. A change that cannot be judged (a dependency definition, the CI steps, the selection tool, a file that cannot be classified, and so on) or a selection that does not run falls back to every test, and so does `--all`. In the `テスト:` line of the result comment, a narrowed run shows the number run and the total, and a fallback shows its reason
- **Shared test parts**: a change to `fixtures/*.ts`, `fixture.ts`, `*-fake-*.ts` or `*-harness.ts` does not fall back to every test; it selects only the tests that import it (indirectly too) and the tests that declare it with `// test-reads:` (the reason line begins with `共通部品 <path> を読む: …`). A dependency that is read only in a child process needs a declaration, and a miss is caught by the tag CI
- **Incremental run**: when the newest result of the top PR is an earlier pass (head `P`), `bun test` is selected from only the files changed by the commits added after `P` (the `+` of `git cherry`; commits whose diff is unchanged by a rebase onto the base do not count), and only the install, the type check and that `bun test` run (`incrementalBase` / `incrementalSteps` in `scripts/local-ci.ts`). It is not incremental, and every step runs, when `P` cannot be fetched, when there is a merge commit that is not in `P`'s history (a conflict resolution), when the newest is not a pass, for a change that cannot be judged, and for `--all`, `--force` and `--change`. The result comment gets the line `増分: <P の 7 文字> の pass の後の <n> コミット（変更 <m> ファイル）で、型検査と選んだテストだけ` (an incremental run: n commits after the pass of the first 7 characters of P, m changed files, type check and selected tests only). The mark is the same as a full pass, `[local-ci] pass <head sha> base=<base sha>`, so merge-gate's rules do not change
- **Performance growth**: the bundle and `bytes` (`open-task` / `open-task-huge`) are judged by the increment against the thing compared with, and a growth under 1% is a pass. Do not ask the user about a growth under 1%, and do not open a PR that raises the ceiling (there is no number to act on; for the trend see the records of `perf-records` and `bun scripts/perf-ratchet.ts history`, and the opening of the "Ratchet (the CI ceilings)" section of `docs/design/perf.md`). A PR's local CI does not measure perf, so it does not fail on `grew:` (a `[local-ci] pass` needs no perf result, and merge-gate does not look at perf). A number going over a ceiling (`over:`) is judged by the tag CI after the merge (`scripts/tag-ci.ts`) and shown in the Release's `## CI`. The tag CI compares with the tag just before that tag (for the first tag, the tip of `origin/main`), so growth in a tag shows in the Release's `## CI` as `grew:` / `raised:` (the perf steps do not count toward the tag's result, so the lines are a warning and the tag stays a pass). When a tag contains several merges the growth is summed, and which merge it came from is traced with `history` and `git log`. When it shows up, either file a request to fix it or go back to the previous tag. The accumulation of growth is also followed in the records of `perf-records` (`history`)
- **What a pass means**: a narrowed pass is a safety net for the affected scope, and merge-gate counts it the same as a pass of all tests. An incremental pass counts the same (the `増分:` line is not read). The tag CI holds the safety net for the steps an incremental run leaves out (licenses, public tree check, build, perf). The tag CI holds the safety net for all tests. The limits of narrowing (for example, `scripts/public-include.test.ts` reads the list of roots, so adding a file to a root does not select it) are caught by the tag CI, and the number of misses is kept in "Record of selection misses" below

## Record of selection misses

When `bun test` of the tag CI is red, one `selection:` line is added to the tag's Release under `## CI`. It is the number of failed test files, split by whether the PR's local-ci selection (`scripts/test-select.ts`) would have selected them.

- `selection: missed <N> / selected <M>（落ちたテストファイル <N+M> 件）` (the part in parentheses reads "N+M failed test files"): `missed` means not selected, that is, a red that the PR's narrowing missed; `selected` means selected, that is, a red that the PR's local-ci should also have turned red. A range that fell back to every test because of a change that cannot be judged is all `selected`
- `selection: unclassified（理由）` (followed by the reason in parentheses): there is no previous tag, the diff or the selection cannot be read, or the failed files cannot be read from the output. It is not counted
- How to count: for each tag in `gh release list`, `gh release view <tag> --json body -q .body | grep '^selection:'`
- Limits: the range of the change is not a PR but from the previous tag to that tag. A range wider than a PR is more likely to be selected, so `missed` shows fewer by that much. Conversely, a red not fixed since the previous tag, or a flaky test's red, goes into `missed` even if it has nothing to do with that tag's change, so it can show more. Read consecutive tags with the same red as one, and use the number as a rough measure of misses

A red remains in the Release as before, and a request to fix it is filed automatically. It is not a gate.

## Recheck

When merge-gate stops and the large reason is only `[再チェック <kind>]` (with no `[聞く]`), do not ask the user; run the following for each kind in `recheck` (for the skills, see `pbi-complete` 5 and `review-triage-and-merge` 5; for a Task of another repository, `otherRepoRules` hands over the place of the procedure and the repository's own values). For a PR of another repository (`--repo`), `-R <owner/name>` and `origin` below are that repository (in Switchboard, the development repository, `開発リポジトリ`). CI, unresolved threads, commits that were not re-reviewed, and not being CLEAN are settled as usual, separately from the recheck.

| Kind | Who runs it | Pass |
|---|---|---|
| `size` | A whole-PR review by a runner other than the main review's (`[codex] review` / `[claude] review`): a Claude subagent if the main one is Codex, Codex if the main one is Claude. The materials, instructions and posting are as in steps 1 to 3 of `cross-runner-review` (the conversation's context is not passed). But the first line of the posted summary is `[<runner>] recheck size` (`post_review` does not take the first line as an argument, so when defining it inside the call, replace `printf '[%s] review\n\n'` with `printf '[%s] recheck size\n\n'`. Do not post it as `[<runner>] review`: merge-gate counts that as the main review, and it would stand in for the re-review) | 0 blocker / should-fix items in `### Findings` |
| `responsibility` | Likewise a reviewer of another runner (the responsibility files are CLAUDE.md, AGENTS.md, `ops.config.json` and the skills, and do not include `docs/design/`). Add the original request to the materials of step 1 of `cross-runner-review` (`ops-kit backlog view <PBI の ## 元要望 の番号> --fresh > "$M/request.md"`, because the reviewer's sandbox cannot read GitHub), and add to the instructions: `` 責務のファイル（`[再チェック responsibility]` の理由のパス）の変更が、`_review/pbi.md` の受け入れ条件と `_review/request.md`（元要望）の求める範囲か。範囲外の変更を 1 行ずつ `[should-fix]` で挙げる `` (whether the changes to the responsibility files are within the scope asked for by the acceptance criteria and the original request; each change outside it as a `[should-fix]` line). The first line of the summary comment is `[<runner>] recheck responsibility` (replace the first line of `post_review` as for `size`). For the same PR as `size`, one review may look at both, with the first line `[<runner>] recheck size responsibility` | 0 changes outside the scope (0 blocker / should-fix items in `### Findings`) |
| `migration` | In the checkout (worktree) of the PR's head, `env -u SWITCHBOARD_SUPERVISED bun test packages/core/src/schema.test.ts packages/core/src/transfer.test.ts` | All pass |
| `rescue` | In the checkout (worktree) of the PR's head, `env -u SWITCHBOARD_SUPERVISED bun test rescue/src` (this includes `promote.test.ts`, which covers refusing a candidate version, the automatic return after a switch, and the return from a snapshot), and `env -u SWITCHBOARD_SUPERVISED bun scripts/rescue-e2e.ts`, which checks the start and the return of an installed bundle. In addition, a review by another runner like `size`. The first line of the summary comment is `[<runner>] recheck rescue`. For the same PR as another reviewer's recheck, one review may look at them, with the kinds listed on the first line | The tests and the E2E all pass, and 0 blocker / should-fix items in `### Findings` |
| `design-rules` | The same reviewer of another runner and the same materials as `responsibility`. Add to the instructions: `` 変わった規則が README のほかの規則・既存の設計文書と矛盾しないか、`_review/request.md`（元要望）の求める範囲か。矛盾と範囲外を 1 行ずつ `[should-fix]` で挙げる `` (whether the changed rule contradicts the README's other rules or an existing design document, and whether it is within the scope of the original request; each as a `[should-fix]` line). The first line of the summary comment is `[<runner>] recheck design-rules`. For the same PR as another reviewer's recheck, one review may look at them, with the kinds listed on the first line | 0 blocker / should-fix items in `### Findings` |

When the runner specified for a recheck is at its usage limit, substitute a new session of the runner that is not at the limit, as in step 0 of `cross-runner-review`. Treat it symmetrically: Claude if Codex is at the limit, Codex if Claude is. The recheck is a new session separate from the main review; neither the conversation's context nor the main review's result is passed, and the materials and instructions are as above. The first line of the summary is `[<runner>] recheck <kind>（同じランナーの別セッション。<上限のランナー> が利用上限のため代替）` (a different session of the same runner; substituted because the runner at the limit is at its usage limit). Keep it distinct from a self-review. Because it is the same runner, oversights can overlap, but going back is possible with a tag and the scope of `[聞く]` does not change. If the substitute is also at its usage limit, stop in the Task's conversation as unreviewed. When you substituted, add `、<runner> で代替` (substituted by <runner>) to the kind in the decision log (for example `自動マージ: PR #n（responsibility、再チェック合格、Codex で代替）`).

When it passes, post the mark (the first line is the mark; the second line is the patch-id of the rechecked diff; the third line onward is the grounds: the URL of the review comment, or the number of tests):

```bash
gh pr comment <PR> -R <owner/name> --body "[recheck] <kind> pass $(gh pr view <PR> -R <owner/name> --json headRefOid -q .headRefOid)
patch-id $(gh pr diff <PR> -R <owner/name> | git patch-id --verbatim | cut -d' ' -f1)
<レビューコメントの URL / テストの件数>"
```

After the mark is posted, run the merge decision again. When the head changes (a fix commit, or the automatic rebase after a lower PR is merged), the mark no longer counts, so run it again (`migration` always reruns the tests. `rescue` also always reruns the tests and the E2E, and its review is as in the next sentence. For `size` / `responsibility` / `design-rules`, only when the current `gh pr diff <PR> | git patch-id --verbatim` equals the patch-id on the second line of the previous mark, that is, when the diff has not changed, as in the automatic rebase after a lower PR is merged, may you post the mark again on the grounds of the previous review's comment URL. If it differs, rerun it, including when a conflict was resolved by a manual rebase. `--verbatim` makes a whitespace difference a different id too, so a resolution that only changed indentation is also detected). If it does not pass, fix the findings (`review-triage-and-merge`) and rerun. If it cannot be fixed, ask in the Task's conversation as an operational confirmation.

When you merge by a recheck, add one line to the PBI's decision log: `YYYY-MM-DD: 自動マージ: PR #n（<種類>、再チェック合格）、戻すなら <tag>` (automatic merge: PR #n, kind, recheck passed; to go back, use <tag>). `<tag>` is the newest of the tags that passed CI (run `bun scripts/tag-ci.ts --latest-pass` before the merge; the command fetches the tags again. For a PR of another repository, run the Switchboard clone's `scripts/tag-ci.ts` from that repository's working tree with `--latest-pass --repo <owner/name>`. Without `--repo`, it picks the script's clone, that is, Switchboard's tags. Tags are made without waiting for CI, so the newest tag may have failed). If the command exits 1 (there is no tag that passed CI, for example in a repository where the tag CI has not yet written results), write `戻すなら: CI を通ったタグなし` (to go back: no tag that passed CI) in place of `<tag>` (do not write the newest tag instead). Going back to it is the Going back section of [`docs/design/releases-and-rescue.md`](design/releases-and-rescue.md) (`scripts/rollback-pr.ts <tag>`).

## Record marks

On a large PR, leave which kind was waived and by whom as marks in PR comments (the weekly tally `scripts/merge-audit.ts` reads them and proposes changes to the rules). The words for the kinds are `MERGE_KINDS` = `security:docs, security:words, security:lockfile, security:github, security:gates, security:host, rescue, design-rules, size, responsibility, migration` (security is per group of paths. The `security` marks from before it was split into groups in 2026-11 are not counted) (the words of `ask` and `recheck` in merge-gate's output). Every mark goes on the first line with the 40-digit sha of the head (the same form as `[local-ci]` / `[recheck]`. The time is the comment's `createdAt` and is not written in the body):

| Mark | When | How to read it |
|---|---|---|
| `[recheck] <kind> pass <head sha>` (`RECHECK_PASS`) | When a recheck has passed (the "Recheck" section above) | That kind was waived by a recheck |
| `[merge-ask] <kinds> <head sha>` (`MERGE_ASK`) | Just before asking the user "may I merge?" in the Task's conversation | `<kinds>` is merge-gate's output `ask` and the `recheck` that has no mark yet, joined with `,` (in the order of `MERGE_KINDS` above) |
| `[merge-answer] <yes\|no> <kinds> <head sha>` (`MERGE_ANSWER`) | When you resume after the reply to a PR you asked about with `[merge-ask]` (for `yes`, go on to the merge decision with `--allow-large`. When you asked for a reason other than large, such as CI, post neither mark). If there is no `[merge-ask]`, post `[merge-ask]` first (the time of both is the time they were posted) | `yes` = the user allowed it. `<kinds>` is the same as when asked |

Post with `gh pr comment <PR> -R <owner/name> --body "[merge-ask] <kinds> $(gh pr view <PR> -R <owner/name> --json headRefOid -q .headRefOid)"` (`[merge-answer]` likewise). `--allow-large` does not take effect unless the last `[merge-answer]` with the same sha as the head is `yes` and its `<kinds>` includes all of the `ask` and `recheck` of the verdict's output (a `no` after a `yes` is a cancellation. For a PR you asked about without posting `[merge-ask]`, post `[merge-ask]` and then `[merge-answer]`, in that order). Marks are not added retroactively to earlier merges.

## Branch protection and local results

A local-ci result is a PR comment; it does not become a GitHub required check (a check run / commit status). If the base branch has a protection or ruleset that requires status checks (or required approvals), GitHub makes the PR `BLOCKED` even when the local result passes, and it cannot be merged. merge-gate does not let this through silently: when it counted CI by local-ci and the PR is `BLOCKED`, it stops with `mergeStateStatus が BLOCKED: base の枝の保護（必須のチェックか承認）がマージを止めている。local-ci の結果は PR コメントで、GitHub の必須チェックにはならない` (mergeStateStatus is BLOCKED: the base branch's protection, required checks or approvals, is stopping the merge; the local-ci result is a PR comment and does not become a GitHub required check). merge-gate does not read the protection settings (that needs admin permission, and the API is not available on some plans), and does not change them. It does not bypass the requirements of review, approval or protection.

The steps for the user to check the settings (whether to change them is the user's decision):

1. `gh api repos/<owner>/<repo>/branches/<base> -q .protected` — `false` means there is no protection. The reason for BLOCKED is a ruleset or a wait for approval
2. If `true`, look at the names of the required checks in the repository's Settings → Branches (or `gh api repos/<owner>/<repo>/branches/<base>/protection/required_status_checks`; admins only). "Require status checks to pass" in Settings → Rules → Rulesets (`gh api repos/<owner>/<repo>/rules/branches/<base>`) is the same
3. While Actions does not start, the required checks cannot be satisfied. To merge, the user removes the requirement only for that period, or brings Actions back to a state where it can run. This repository's scripts do neither
