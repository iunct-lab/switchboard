# The merge-gate procedure (keys, recheck, record marks, protected branches)

The procedure to run when `bun scripts/merge-gate.ts <PR> [--allow-large] [--repo <owner/name>]` returns stop, what the gate reads as a key, and the records the app keeps for it. The output is JSON, `{ verdict, impact, reasons, ask, recheck, notes? }`; exit 0 = merge, 1 = stop, 2 = could not decide (never treated as merge). With `--merge-stack` on a PR that has PRs below it in GitHub's stack, the output is `{ verdict, stack: [{ pr, verdict, impact, reasons, ask, recheck, … }, …] }` (bottom first; the top-level `verdict` is `merge` only when every PR's is), and the stop handling below applies to each PR in `stack`. In a Task the verdict and the merge are the app's: the script asks the app to run its own copy as a job and prints the job's output (`docs/design/daemon-jobs.md`, "The gate"). The rules of the verdict are in `scripts/merge-gate.ts`. The prompts of the process Tasks and the `reasons` sentences of merge-gate point at the sections of this document.

## What the gate reads as a key

A fact the gate (or the promotion, or the front of `gh`) lets decide a merge or a release is a key: whoever can write it can open the door. A Task runs as the same OS user as the daemon and writes PRs, comments, Issues, Releases and its own diff, so a key is safe only when the Task cannot write it. This table lists every input the verdict reads, who can write it, and where it is read. `scripts/merge-gate-keys.test.ts` checks that each function named here exists in the file named, and that every field of the verdict's `PrFacts` is mapped to a row, so a field added to `PrFacts` without a mapping fails the test. Inputs read outside `PrFacts` (the environment, the front of `gh`, the tag CI's own reading) are listed here by hand. Whether the gate runs as a Task's, and where it reads the app's records, come from the environment (`SWITCHBOARD_TASK_ID` for running as a Task's, `OPS_KIT_TASK_ID` for the Task whose grant is read, `MERGE_RECORDS_URL` / `BACKLOG_URL`), which the Task's own shell can change: like the rest of this table, a key is safe from a Task that follows its procedure, not from one that rewrites its own environment or the app's database (the same OS user).

## When to run local CI and how it counts

In a repository where Actions does not start (a job with 0 steps, or a run that stays `queued`) or has no run (a case where every run was skipped counts the same), run local CI only at the following times (in a Task, ask the app for it with `ops-kit job request local-ci <PR>`: the app's job is what leaves the record the gate counts; from a terminal, `bun scripts/local-ci.ts <PR>` leaves none) (the skill's `<ローカル CI>`; for a Task of another repository, `otherRepoRules` hands over this section):

- **When**: once, on the top PR of the stack, after the review findings of every PR in the stack have been handled and before the recheck. A single PR is its own top. Do not run it in the middle of a review, per PR, or between merges
- **Running again**: run it once more on the top only when the diff of some PR has changed (a fix commit, or a conflict resolved by a manual rebase). Do not run it again for GitHub's automatic rebase after a lower PR is merged (the head sha changes but the diff is the same), nor for the base (main) moving forward. When the newest result of the top PR is an earlier pass and only fixes were added after it, the rerun is an incremental run (see "Tests in the affected scope" below)
- **How it counts** (merge-gate's `ciOf`, in `scripts/merge-gate-records.ts`): only the app's record of a local CI job counts; a PR comment that looks like a result counts for nothing. From the PR, walk up through the open PRs whose base is the head branch to find the top (if there are 0 or 2 or more above, that PR is the top). If the newest of the top PR's local CI job records that left a result is a pass, and every commit of this PR now (from the merge-base with the current tip of the base branch to the head) is in that pass's head with the same diff (`git cherry <pass's head> <PR's head> <merge-base>` has no `+` line, and any merge commit among them is in the pass head's history as it is), this PR's CI is done. A run that has not started (`queued`, `waiting`, `requested` or `pending`, that is, not yet `in_progress`) counts the same with that pass; an `in_progress` run does not count and stays unfinished. The automatic rebase after a lower PR is merged (the sha changes, the diff of each commit is the same) counts; a fix commit or a conflict resolution that changed the diff does not. If the newest is a fail, or some commit is not included, a reason to rerun on the top follows the CI reason. A run that left no record (one from a terminal, or one whose head moved before the record was written) is not counted. A run whose base alone moved leaves its record with the base it ran on, and that pass counts like any other (unless a shared file moved in the base, `sharedMoved`). merge-gate fetches the commits it needs for the verdict (the pass's head, the PR's head, the tip of the base branch) without writing refs in the working tree it ran in (from `https://github.com/<owner>/<name>.git`). If it is not a git working tree, or the fetch fails (the network, a login), it does not decide (exit 2). A record that names a commit the remote does not have (one never pushed) is not counted: it covers nothing, and a record beside it can still count
- **Settings kept on Switchboard's side are counted only as the owner confirmed them**: for a clone with no `ops.config.json` of its own, the gate reads from the daemon's index (by the clone's folder, never from `OPS_KIT_CONFIG`) the settings in force and whether a change of them waits for the owner. The judgement's `notes` name the confirmed version it used. While a change waits, the judgement has a `[聞く]` reason that `--allow-large` does not lift: the owner confirms or refuses the change among the app's questions first. A local CI pass whose record names a steps hash counts only when that hash is the hash of the confirmed `ci.steps`; with steps confirmed, a pass that names none does not count either. The index and the files belong to the daemon's user, which a Task also runs as: this makes an honest run ask, it is not a boundary ([docs/design/new-repo.md](design/new-repo.md), "Who changes the settings, and when a change is in force").
- **A pass of steps kept on Switchboard's side**: a repository that has neither `ops.config.json` nor `.github/workflows/ci.yml` is run with the `ci.steps` of the settings Switchboard keeps for its workspace ("Steps" in `docs/design/local-ci.md`). Its job record has the same shape (a pass at a head and a base) and counts like any other pass, so the verdict does not stop on "no CI check" for a repository that commits nothing for Switchboard's sake. The record also names a hash of the steps. Without any steps anywhere, local CI exits 2 and leaves no record, and the gate stops as before: there is no setting that passes a pull request with no CI
- **A pass after subtracting known failures**: when local CI subtracts the registered known failures (`known-failures.json`, read from the base; see "Known failures" in `docs/design/local-ci.md`), its record is still a pass at a head and a base and counts like any other pass. The merge gate asks for no merge outside the gate because of it
- **Why the base is not compared**: conflicts with other PRs are stopped by `mergeStateStatus`. A defect that appears only when separate PRs are combined is found by the tag CI after the merge (the "Tag CI" section of `docs/design/releases-and-rescue.md`)
- **Shared files** (`sharedFiles` in `ops.config.json`): work on these files is not held back by the parallel guard, so two PRs that touch the same one go on side by side and may merge without a conflict and still break together (two migrations taking the same number, for example). For them the base is compared: when a commit that entered the base after the pass's base (`base=<base sha>` of the result) touches a shared file that the pass's stack also touches, and that commit is not in the pass's head with the same diff (`git cherry`; a PR of the same stack merged below is, so the automatic rebase after it does not count), the pass does not count. The reason names the files; run local CI again on the top, on the newest base (`sharedMoved` in `scripts/merge-gate.ts`; `bun scripts/local-ci.ts` does not reuse such a pass either). A base that moved only on other files counts as before, and a repository without the list is judged as before. If the rebase onto the new base conflicts, the PR's own session resolves it, has the resolving commit reviewed, and runs local CI again
- When a PR is stacked on top later, run on the new top (the previous top's pass does not contain that PR)
- **Tests in the affected scope**: only the `bun test` step is narrowed; every other step runs. Run on the top of the stack, the selection is made from the sum of the changes of all the PRs. A change that cannot be judged (a dependency definition, the CI steps, the selection tool, a file that cannot be classified, and so on) or a selection that does not run falls back to every test, and so does `--all`. In the `テスト:` line of the result, a narrowed run shows the number run and the total, and a fallback shows its reason
- **Shared test parts**: a change to `fixtures/*.ts`, `fixture.ts`, `*-fake-*.ts` or `*-harness.ts` does not fall back to every test; it selects only the tests that import it (indirectly too) and the tests that declare it with `// test-reads:` (the reason line begins with `共通部品 <path> を読む: …`). A dependency that is read only in a child process needs a declaration (`./` declares the whole tree, so any change selects that test), and a miss is caught by the tag CI
- **Incremental run**: when the newest result of the top PR is an earlier pass (head `P`), `bun test` is selected from only the files changed by the commits added after `P` (the `+` of `git cherry`; commits whose diff is unchanged by a rebase onto the base do not count), and only the install, the type check, the quick tree checks the CI has (issue numbers in code comments, file sizes, public docs) and that `bun test` run (`incrementalBase` / `incrementalSteps` in `scripts/local-ci.ts`). It is not incremental, and every step runs, when `P` cannot be fetched, when there is a merge commit that is not in `P`'s history (a conflict resolution), when the newest is not a pass, for a change that cannot be judged, and for `--all`, `--force` and `--change`. The result gets the line `増分: <P の 7 文字> の pass の後の <n> コミット（変更 <m> ファイル）で、型検査と選んだテストだけ` (an incremental run: n commits after the pass of the first 7 characters of P, m changed files, type check and selected tests only). The record is the same as a full pass, so merge-gate's rules do not change
- **Performance growth**: the bundle and `bytes` (`open-task` / `open-task-huge`) are judged by the increment against the thing compared with, and a growth under 1% is a pass. Do not ask the user about a growth under 1%, and do not open a PR that raises the ceiling (there is no number to act on; for the trend see the records of `perf-records` and `bun scripts/perf-ratchet.ts history`, and the opening of the "Ratchet (the CI ceilings)" section of `docs/design/perf.md`). A PR's local CI does not measure perf, so it does not fail on `grew:` (a local CI pass needs no perf result, and merge-gate does not look at perf). A number going over a ceiling (`over:`) is judged by the tag CI after the merge (`scripts/tag-ci.ts`) and shown in the Release's `## CI`. The tag CI compares with the tag just before that tag (for the first tag, the tip of `origin/main`), so growth in a tag shows in the Release's `## CI` as `grew:` / `raised:` (the perf steps do not count toward the tag's result, so the lines are a warning and the tag stays a pass). When a tag contains several merges the growth is summed, and which merge it came from is traced with `history` and `git log`. When it shows up, either file a request to fix it or go back to the previous tag. The accumulation of growth is also followed in the records of `perf-records` (`history`)
- **Instruction files**: a PR that changes `CLAUDE.md`, `AGENTS.md`, a skill (`.claude/skills/**`, `ops-kit/skills/**`) stops with `[聞く] 指示のファイル: <paths>` (kind `instructions`). The files decide what every later Task does, and a gate cannot tell a weakened rule from a clarified one, so only the owner lifts it: the person's grant of the head (the app's record) with `--allow-large`. A recheck does not. When the change deletes or rewrites a line that carries the user's own mark, the reason lists the lines (`（利用者の決まりの行を消す・変える: <path>:<line>, …）`), also where the file's own reason is another (a credential word in its path, `rescue/`, a rename out of an instruction path). An instruction file changed with a file that is neither an instruction file nor a test (`**/*.test.ts`) stops with `[分ける] 指示のファイル（<paths>）とほかのファイル（<paths>）を同じ PR で変えている。…`; no yes lifts it, so the instruction files go in a PR of their own. `rescue/CLAUDE.md` gets both the `rescue` recheck and the `instructions` question, and a file renamed out of an instruction path is asked too. A rename is judged as a local change shows it, a file removed and a file added: renamed out to a path that is neither an instruction file nor a test, or renamed in from such a path, it is split. `ops.config.json` is the only `responsibility` file left.
- **Raising a limit or an allowance**: a PR that raises a ceiling or adds an allowance in `scripts/perf-budget.json` (a number up, a key added, a ceiling key removed — the ratchet checks only the ceilings that are there — an `exceptions` entry added), `scripts/licenses.allow.json` (a word in `allowed`, an `exceptions` entry added, a later `until`), `known-failures.json` (an entry added, a later `until`) or `scripts/file-size.ts` (`SOURCE_LIMIT` / `TEST_LIMIT` up) stops with `[聞く] 検査の上限・許可リストを上げる: <path> <key>: <before> → <after>` (kind `limits`, read by `limitsRaised` in `scripts/merge-gate-limits.ts` from the file at the merge base and at the head, for a GitHub PR and a local change alike). Only the owner lifts it: the person's grant of the head (the app's record) with `--allow-large`. Lowering a ceiling or removing an entry (other than a perf-budget ceiling) is not asked (the lowering `update` of perf-ratchet and the clearing of expired known failures pass); a file that cannot be read or is not the expected shape (a perf-budget leaf that is not a number) is asked as raised.
- **What a pass means**: a narrowed pass is a safety net for the affected scope, and merge-gate counts it the same as a pass of all tests. An incremental pass counts the same (the `増分:` line is not read). The tag CI holds the safety net for the steps an incremental run leaves out (licenses, public tree check, build, perf). The tag CI holds the safety net for all tests. The limits of narrowing are caught by the tag CI, and the number of misses is kept in "Record of selection misses" below

## Task scope and companion files

A Task's body names the paths it plans to change, but the files a change needs often differ from the plan, so a file outside the names does not stop the merge. When a file of the PR is covered by no path of the Task (a named directory covers what is under it), the judgement lists it in `notes` as `Task #<n> の名指しの外: <paths>`, with the sibling Tasks that name it. `bun scripts/merge-gate.ts <PR> --scope` (`--change <n> --scope` for a local change) prints the same list as Markdown for the main review, which checks each file for a change the Task's purpose needs against one mixed in from another Task; it judges, merges and records nothing, and prints nothing when no file is outside.

`bun scripts/merge-gate.ts --gate-paths <path>...` prints, one per line, those of the given paths that the gate itself covers (the `security:gates` group and the attack-review paths, the same lists `judge` reads); a path ending in `/` is kept when the lists cover a file under it. It judges nothing and needs no PR number or `gh`; a PR number or another flag with it exits 2. The kit calls it instead of keeping a copy of the lists.

Three kinds of file come along with a named file and are not listed as outside (`companion` in `scripts/merge-gate.ts`):

- **The test of a named file**: `<name>.test.ts` next to a named `<name>.ts` (`.tsx` too). A test of a file the Task does not name is listed as outside
- **A design document**: a `*.md` under `docs/design/`
- **The public list, for the PR's own files only**: `ops.config.json`, when the only difference is in `publicSync.include` / `publicSync.exclude`, every path added there is a file the PR adds (or renames to), and every path taken out is a file the PR removes (or renames from). Any other difference in the file is listed as outside, and so is adding or dropping a directory or a file the PR does not add or remove (dropping a directory's `exclude` would publish it). On GitLab the file's change is not read, so `ops.config.json` is listed as outside there

What passed this way is listed in the judgement's `notes` as `付いてくるファイル: <paths>`. The kinds are fixed in the script, not a setting: adding one is a PR. `scripts/perf-budget.json` is not one (raising a ceiling is the user's decision).

The scope list lifts and adds nothing else: the large reasons (`[聞く]`, `[再チェック <kind>]` — `ops.config.json` still asks for the `responsibility` recheck; the instruction files ask for `instructions`, below), unresolved threads, CI and the review of the last commit apply as before. The list cannot tell a bad change inside a companion (a weakened test, a wrong document) from a good one; the review reads them, as it does the named files. A Task therefore names the code it changes and need not name these files; naming fewer paths also keeps the parallel guard from holding other work on them.

A local change (`merge-gate.ts --change <n>`, `local-merge.ts <n>`) gets the same list: the Tasks it closes are read from the app's stored Issues (`GET /api/backlog/records`) instead of GitHub. In a workspace whose Issues are GitHub's, a change is numbered apart from them and read with the query `change=1` of the app's API; there a linked Issue that is not stored is no judgement (exit 2), and a change is not merged locally whenever a pull request of its branch exists or may exist — the PR it was made with, an open PR the stored records have for an Issue it closes, or a branch that was pushed to origin — because that PR's review threads cannot be read and are not counted as none. Such a change is made only while the app itself sees GitHub out of use for now, the person's grant of the change's head (`変更 L<n> をマージしてよい`, recorded under the workspace's own key `local:<workspace id>`) lifts an ask reason with `--allow-large` as a PR's does, and its merge lands on a ref beside `main` without moving a work tree. Every reason of the gate and how the local path evaluates it is listed in `docs/design/forge-integration.md`, "While GitHub cannot be used, and coming back".

## Record of selection misses

When `bun test` of the tag CI is red, one `selection:` line is added to the tag's Release under `## CI`. It is the number of failed test files, split by whether the PR's local-ci selection (`scripts/test-select.ts`) would have selected them.

- `selection: missed <N> / selected <M>（落ちたテストファイル <N+M> 件）` (the part in parentheses reads "N+M failed test files"): `missed` means not selected, that is, a red that the PR's narrowing missed; `selected` means selected, that is, a red that the PR's local-ci should also have turned red. A range that fell back to every test because of a change that cannot be judged is all `selected`
- `selection: unclassified（理由）` (followed by the reason in parentheses): there is no previous tag, the diff or the selection cannot be read, or the failed files cannot be read from the output. It is not counted
- How to count: for each tag in `gh release list`, `gh release view <tag> --json body -q .body | grep '^selection:'`
- Limits: the range of the change is not a PR but from the previous tag to that tag. A range wider than a PR is more likely to be selected, so `missed` shows fewer by that much. Conversely, a red not fixed since the previous tag, or a flaky test's red, goes into `missed` even if it has nothing to do with that tag's change, so it can show more. Read consecutive tags with the same red as one, and use the number as a rough measure of misses

A red remains in the Release as before, and a request to fix it is filed automatically. It is not a gate.

## Recheck

When merge-gate stops and the large reason is only `[再チェック <kind>]` (with no `[聞く]`), do not ask the user; ask the app for the following for each kind in `recheck` (for the skills, see `pbi-complete` 5 and `review-triage-and-merge` 5; for a Task of another repository, `otherRepoRules` hands over the place of the procedure and the repository's own values). For a PR of another repository (`--repo`), pass `--repo <owner/name>` to the gate and ask for the jobs from that repository's checkout (in Switchboard, the development repository, `開発リポジトリ`). Every recheck is a job the app runs and records; nothing a Task writes on the PR (a comment, a first line) passes a kind. A kind a command decides (`migration`, `rescue`, `security:lockfile`) is asked with `ops-kit job request recheck <PR> --kind <kind>` (the app runs `scripts/recheck.ts` in the PR's checkout; the commands are the app's, not carried by the request); ask for it at the same time as the local CI, on the head that will be merged. Every other kind is read by a model, and the supervisor lifts all of them with one job, the arbiter's: `ops-kit job request review <PR> --as arbiter --prompt <file> --out <file>` (no `--runner` and no `--kinds`; the instruction is `ops-kit review-arbiter prompt`, and `--follow-up` for the second and last round). A review run as `recheck` no longer lifts any kind. CI, unresolved threads, commits that were not re-reviewed, and not being CLEAN are settled as usual, separately from the recheck.

| Kind | Who runs it | Pass |
|---|---|---|
| `size` | The arbiter (below). The kind is the line count, or a protected path that is not `MIGRATION` | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `responsibility` | The arbiter. The responsibility file is `ops.config.json`; the instruction files are asked of the owner as `instructions`, and `docs/design/` is neither. The kind's viewpoint, `VIEWPOINTS["responsibility"]` in [`scripts/review-viewpoints.ts`](../scripts/review-viewpoints.ts) (the one place the text is kept), is in the material the main review reads, with the original request (`ops-kit backlog view <PBI の ## 元要望 の番号> --fresh`) | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `migration` | `ops-kit job request recheck <PR> --kind migration`: the app runs the schema and transfer tests in the PR's head checkout (`RECHECK_COMMANDS` in `scripts/recheck.ts`) | All pass |
| `rescue` | `ops-kit job request recheck <PR> --kind rescue`: the app runs the `rescue/src` tests (this includes `promote.test.ts`, which covers refusing a candidate version, the automatic return after a switch, and the return from a snapshot) and `scripts/rescue-e2e.ts`, which checks the start and the return of an installed bundle, in the PR's head checkout. In addition, the arbiter's job; both records are needed | The tests and the E2E all pass at exactly the head, and the arbiter's pass as for `size` |
| `design-rules` | The arbiter. The viewpoint `VIEWPOINTS["design-rules"]` in [`scripts/review-viewpoints.ts`](../scripts/review-viewpoints.ts) is in the main review's material | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `security:tests` | The arbiter. The kind is a path that met a credential word or `aws/host/**` and is a test or a fixture (`**/*.test.ts`, `scripts/*-e2e.ts`, `**/fixtures/**`), or a modified host file where `#` starts a comment (`aws/host/**/*.{sh,service,timer,yml,yaml}`) that differs in comment and blank lines only. merge-gate decides that from the whole file at the merge base and at the head, not from the lines of the diff: a `#` line or a blank line counts only where it does nothing — outside a here-document, outside a quoted string, not after a line ending in a continuation `\`, not the first line of the file, and in YAML outside a block scalar (`|` / `>`). So a `#includedir` line added to a sudoers file that a script writes from a here-document, and a `#` line or a blank line put between the lines of a continued command, are asked as `security:host`. So are: a file that could not be read on either side, a file whose syntax merge-gate cannot follow with certainty (a backtick substitution, a here-document inside a string, a string still open at the end, CRLF line ends), a file the base branch changed since the PR forked, a mode change, and an added, removed or renamed file. A file is also judged by its path before a rename or a copy (GitHub's `previous_filename`; a local change and a GitLab MR list both paths), and the stricter answer stands: `aws/auth.ts` renamed to `aws/fixtures/auth.ts` is asked as `security:words`. A file whose status could not be read is not taken for a test, a fixture or a document. The kind's viewpoint, `VIEWPOINTS["security:tests"]` in [`scripts/review-viewpoints.ts`](../scripts/review-viewpoints.ts), is in the main review's material | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `security:docs` | The arbiter. The viewpoint `VIEWPOINTS["security:docs"]` in [`scripts/review-viewpoints.ts`](../scripts/review-viewpoints.ts) is in the main review's material | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `security:gate-support` | The arbiter. The kind is a file that supports the gates without deciding a merge (`scripts/local-ci-notes.ts`, `scripts/local-ci-records.ts`, `scripts/local-ci-offload.ts`, `scripts/forge-resync-report.ts`); the lines that decide stay in the `security:gates` files, and a PR that also touches one of those is asked as `security:gates`, which this recheck does not lift. The kind's viewpoint, `VIEWPOINTS["security:gate-support"]` in [`scripts/review-viewpoints.ts`](../scripts/review-viewpoints.ts), is in the main review's material. | An arbiter job at the head with no ruling for the reviewer, no `missing` viewpoint and no unreadable line |
| `security:lockfile` | Only when every lock file the PR changes is a `bun.lock` and the repository has `bun run licenses:check`; for any other lock file (`package-lock.json`, `uv.lock`, `go.sum`, `requirements*.txt`, …), or a repository without the check, the recheck does not pass and the user is asked (`--allow-large`). `ops-kit job request recheck <PR> --kind security:lockfile`: the app runs `bun install --frozen-lockfile --ignore-scripts && bun run licenses:check` in the PR's head checkout and lists every package whose `bun.lock` entry changed — added, removed, or with a changed version, source (`resolved`) or integrity — one line each with the old and the new value in the job's output | The install and the license check exit 0, every changed lock file is a `bun.lock`, and the list of changed entries (version, source, integrity) is in the job's output |

The arbiter is asked with `ops-kit job request review <PR> --as arbiter` without `--runner`: the app picks the setting's recheck runner and refuses another one. The recheck runner is the setting's: the `再チェック・マージ後の監査` row (`Recheck and post-merge audit` in English) of the `どの仕事をどのランナーで` card in Settings, which reaches a Task as `OPS_KIT_RECHECK_RUNNER`. `主レビューとは別のランナー` (`other`) is the other runner than the main reviewer's; `主レビューと同じランナーの新しいセッション` (`same`) is a new session of the main reviewer's runner; unset (`レビューの設定に従う — 既定`), it takes the review setting's value. This holds for a Task whose runner has a main reviewer (Claude Code or Codex); for a Task whose runner is neither, the request must name `--runner` and the setting does not check it. When the recheck runner is at its usage limit, wait until its limit resets; the arbiter is not substituted by the other runner. The arbiter is a new session separate from the main review. It does not read the PR again: it reads the material of the earlier rounds (`_review/handled.md` with the replies and the triage summaries, the output of each round, the viewpoints the review was to look at; step 1 of `cross-runner-review`), says for each viewpoint whether a round looked at it (`covered`) or not (`missing`), and rules once, for each finding the implementer's reply disputed, whose side the written rules take (`reviewer` or `implementer`; a second and last round reads only the fixes and turns a `reviewer` ruling into `fixed` when the fix does what it asked). The implementer's answer is the implementer's judgement; the reviewer objects at most once, as `Repeat of:`, and does not raise a closed ruling again; the arbiter's rulings are in the material as `## Rulings (closed)` and, for the ones ruled for the reviewer, `## Rulings for the reviewer (standing)`. A blocker or should-fix said to be fixed is checked in the code. The weight of a finding (blocker / should-fix / nit / question) is defined once, in the text added after every review's instructions (`ops-kit review-note`).

When the jobs have ended, run the merge decision again. The gate counts a recheck only from the app's records. A kind a model reads (every kind but `migration` and `security:lockfile`): an arbiter job that ended, at the head or at one that has this PR's commits with the same diff (so the automatic rebase after a lower PR is merged does not call for a new review), whose recorded rulings have no ruling on the reviewer's side, no `missing` viewpoint and no line it could not read; a record with no rulings counts for nothing. The `[<runner>] arbiter` comment a Task copies onto the PR is for people to read: the gate never reads it, so a comment, or a first line, lifts nothing without the job's record. A command recheck at exactly the head, so a head that changed asks again (`migration` always reruns the tests, `rescue` also always reruns the tests and the E2E, `security:lockfile` always reruns the install and the license check). A conflict resolved by a manual rebase changes the diff, so it is asked again too. The gate's output lists, in `recheck`, the kinds with no record yet; the reason says which (`監督者の裁定が要る` for a kind a model reads, the command for the others). If it does not pass, fix the findings (`review-triage-and-merge`) and ask again. If it cannot be fixed, ask in the Task's conversation as an operational confirmation.

When you merge by a recheck, add one line to the PBI's decision log: `YYYY-MM-DD: 自動マージ: PR #n（<種類>、再チェック合格）、戻すなら <tag>` (automatic merge: PR #n, kind, recheck passed; to go back, use <tag>). `<tag>` is the newest of the tags that passed CI (run `bun scripts/tag-ci.ts --latest-pass` before the merge; the command fetches the tags again. For a PR of another repository, run the Switchboard clone's `scripts/tag-ci.ts` from that repository's working tree with `--latest-pass --repo <owner/name>`. Without `--repo`, it picks the script's clone, that is, Switchboard's tags. Tags are made without waiting for CI, so the newest tag may have failed). If the command exits 1 (there is no tag that passed CI, for example in a repository where the tag CI has not yet written results), write `戻すなら: CI を通ったタグなし` (to go back: no tag that passed CI) in place of `<tag>` (do not write the newest tag instead). Going back to it is the Going back section of [`docs/design/releases-and-rescue.md`](design/releases-and-rescue.md) (`scripts/rollback-pr.ts <tag>`).

## Attack review

A PR that touches what an attacker would aim at is stopped until the app has a record of an attacking review of its last commit. The reviewer is told to break the change, not to approve it. It is asked with `ops-kit job request review <PR> --runner <runner> --as attack --prompt <file> --out <file>` (the reviewer is first the runner the review setting gives it, and the other runner stands in when that one is at its usage limit; the app accepts either). A commit after the reviewed head that adds to the diff makes the record stale, as for the main review.

What needs it (`attackPaths`):

- A file in the security groups `security:words`, `security:lockfile`, `security:github`, `security:gates`, `security:gate-support` or `security:host` (a file is also judged by its path before a rename). The support files of the gates keep it although they moved to a recheck: their output (the build's exit marks) is read by the gates. A PR that only touches documents or tests (`security:docs`, `security:tests`) needs none.
- A file in `ATTACK_PATHS`: `packages/core/src/promotion.ts`, `packages/core/src/server/promotion.ts`, `scripts/promote.ts`, `rescue/**`, `packages/core/src/uplink-in.ts`, `.claude/settings.json`, `ops-kit/bin/**` (also by its path before a rename).

The reason reads `この head（か、この PR のコミットが同じ差分で入った head）で合格した攻める側のレビューの仕事の記録が無い: <paths>`, and the verdict's `attack` lists the same paths. It is a condition beside the `[聞く]` reason, not a replacement: both are needed, a recorded attacking review does not lift the ask, and `--allow-large` (with the person's grant) does not lift the attack reason. It is the same for a local change (`--change`). No comment is read for it: what counts is the app's job record of a review run as `attack` that passed and left its findings at this head (or at one that has this PR's commits with the same diff; `attackedOf` in `scripts/merge-gate-records.ts`). An attacking review is not a main review and a main review is not an attacking one. A finding of the attacking review becomes a review thread, which the unresolved-threads reason already stops on; the gate does not count findings.

## Record marks

This section is a table of the outputs the tools write for people: lines left on the PR or a Release to read. The gate reads none of them: every fact it counts comes from the app's records (the jobs it ran, the person's grants, the Task it started as direct), so a comment that looks like one of these lines counts for nothing. The weekly tally `scripts/merge-audit.ts` and the post-merge audit read the app's records too, and propose changes to the rules. The words for the kinds are `MERGE_KINDS` = `security:docs, security:tests, security:words, security:lockfile, security:github, security:gates, security:gate-support, security:host, rescue, design-rules, size, instructions, responsibility, migration, limits` (security is per group of paths) (the words of `ask` and `recheck` in merge-gate's output). Each line is on the first line of a comment, with the 40-digit sha of the head where the table says so (the time is the comment's `createdAt` and is not written in the body):

| Output | Written by | What it is for |
|---|---|---|
| `[local-ci] pass <head sha> base=<base sha>` (or `fail`) | `scripts/local-ci.ts` | The result of a local CI run, for the reader of the PR. The gate counts the app's local CI job record ("How it counts" above), not this comment |
| `[codex] review` / `[claude] review` | The main review, posted by `cross-runner-review` | The reviewer's summary, for the reader and the Task's triage. The gate counts the app's review job record |
| `[codex] attack` / `[claude] attack` | The attacking review, posted by `cross-runner-review` | The attacking reviewer's summary. The gate counts the app's review job run as `attack` ("Attack review" above) |
| `[merge-direct] <head sha>` | `--merge` / `--merge-stack`, just before a PR is merged without the main review ("Direct PRs without the main review" below) | A note on the PR that the merge skipped the main review. `scripts/kernel-report.ts` does not read it: it counts the gate job records with `merged` and `reviewSkipped`, each stack entry by its own `reviewSkipped` |
| `[post-audit] pass\|finding <merge sha>` | `scripts/post-audit.ts record` | The result of the post-merge audit ("Post-merge audit" below) |
| `[tag-ci] pass\|fail <sha>` | The tag CI, in the tag's Release | The tag CI's result. Promotion reads the app's tag CI job record, not this text; `tag-ci.ts --latest-pass` (the public sync, the rollback steps) still reads it, and a Task can write it ("What the gate reads as a key") |

`--allow-large` does not take effect for an ask or recheck reason unless the app has the person's grant of this head for the Task that runs the gate (`granted` of `GET /api/merge-records`; the kinds are not in the record, the head decides what is asked of it), or the gate is run outside a Task, where the person's own `--allow-large` is the consent. A GitLab MR is recorded the same way: the person's sentence names it as `PR #<n>` (the app reads no other form), the head is the MR's, read from GitLab when the sentence comes in, and the key is the project's path in lower case. The app not answering is no judgement (exit 2). Outputs are not added retroactively to earlier merges. After a new commit the person is asked again, because the grant is for the head it was recorded with (`docs/design/permission-modes.md`, "Merge grants").

## Direct PRs without the main review

A direct PR skips the main-review reason (`…で合格した主レビューの仕事の記録が無い…`) when all of these hold (the rule is `reviewSkipped` in `scripts/merge-gate.ts`; the table is `ops-kit/reversibility.json`, read here by pointer and not copied):

- The app started the Task that opened the PR as a direct one (its record, `direct` of `GET /api/merge-records`; the branch's name decides nothing, `sb/direct-<topic>` is only a naming convention for such a Task's branch), and that same Task runs the gate: run from the person's terminal or from another Task, the direct PR keeps the main review (the strict side). A PR another Task opened, a local change and a GitLab MR never skip the main review (the app records only the GitHub pull requests a Task opened)
- No large reason is left once the kinds the table answers `reversible` are set aside, or the PR is not large. The table has no gate kind answered `reversible` today, so for now only a PR with no large reason skips the review. A kind answered `reversible` is still large for `impact` and still needs its recheck (only `irreversible` kinds are asked); the other kinds (`compensable`, `irreversible`) keep the review, and the `irreversible` ones are still asked of the owner
- Local CI is a pass, no review thread is unresolved and `mergeStateStatus` is CLEAN, as for any PR

Run the gate first without `--merge`; ask for a review only when `reasons` names the main review (`ops-kit/processes/p1-direct.md`). When `--merge` / `--merge-stack` merges with the skip, it first posts `[merge-direct] <head sha>` on the PR for the reader, so a merge whose comment fails is not made; what counts the direct merges is the gate's job record (`merged` with `reviewSkipped`, per PR in a stack).

Going back, when a merged direct PR turns out to break something: `bun scripts/rollback-pr.ts <tag> --repo <owner/name>` (run in that repository's clone, `<tag>` = the newest tag that passed CI before the merge, `bun scripts/tag-ci.ts --latest-pass --contained-in <the commit before the PR's first commit on main> --repo <owner/name>`; without `--contained-in` a later tag that carries the mistake can be picked). It opens a PR whose one commit puts the tag's tree on top of `main` and merges nothing; that PR goes through merge-gate like any other. Without the main review a mistake is found after the merge, not before; the rework and rollbacks are the cost to read in `scripts/kernel-report.ts`.

## Post-merge audit

The merge gate and the cross-runner review look before the merge. The post-merge audit reads a sample of what was already merged, with the recheck runner's setting choosing the auditor (below), and leaves a mark on the PR. It does not replace any check before the merge, and it never reverts a merge or stops a promotion: a finding becomes a PBI, and the fix goes through the usual flow.

What it can and cannot cover:

- It can find problems left in merged code, week by week, and show the rate of findings per route (reviewed / merged without waiting for the review / lifted by a recheck only) so that a route with a bad rate can be moved back to asking
- It cannot cover a hole that was deployed between the merge and the audit (up to a week), a PR that was not sampled, or a miss by the auditing runner itself. A Task that runs as the same OS user can also rewrite the mark; the daemon trusts whoever reaches localhost, the same as the rest of the instance

**Which PRs.** `bun scripts/post-audit.ts select [--since YYYY-MM-DD] [--until YYYY-MM-DD] [--repo <owner/name>]` reads the PRs merged in the period and prints `{ repo, period, selected: [{ pr, route, auditor, mergeSha }], overflow, unsaved, uncountedAudits }`. It asks GitHub nothing: the PRs, their routes, the audited ones and the auditor come from the app's records (`GET /api/merge-records/history`: the jobs it ran, the person's grants, the PRs it stored and their comments, and the titles of the audit PBIs it stored), so the app has to be reachable (exit 2 otherwise). Each merged PR has one route, decided from those records: `recheck` (a merge verdict that asked nothing, a passing recheck record of the merged head for a kind the verdict record at that head lists as `required` (every recheck kind the change asks for, those already recorded too), and no grant of the person's for that head), `direct` (its merge verdict skipped the main review, or no main-review record exists although the records began before the merge: nobody read it), otherwise `review`. Every `direct` and `recheck` PR is a candidate; `review` PRs are a fixed number (`SWITCHBOARD_POST_AUDIT_SAMPLE`, default `DEFAULT_SAMPLE` in `scripts/post-audit.ts`). One run reads at most `SWITCHBOARD_POST_AUDIT_MAX` PRs (default `DEFAULT_MAX`): `direct` first, then the `review` sample, then `recheck` for the rest. The order inside a route is by a hash of the period and the PR number, so the same period picks the same PRs. `overflow` is the number of candidates the cap left out; `unsaved` lists merged PRs the jobs name that the app never stored (opened and closed between two imports), which have no merge commit to read and are not selected (a stored PR with no merge commit is skipped without a name). A PR that already has an audit is not selected again. A PR has an audit when the app has a finished audit review job that read the merge commit and kept `pass` as its first line; when such a job kept `finding` and the app has stored the PR's audit PBI (the title `record` gives it, `type:pbi`, open or closed, still on GitHub at the last import; the title alone, with no audit job of the app, settles nothing, since anyone can open an Issue with it); or when it has a `[post-audit]` mark by an owner, member or collaborator (a mark stored with no author is not counted). A `finding` job with no PBI is selected again: `record` stopped before it filed the PBI. An audit job asked for by a Task that asked for the PR's other jobs (the Task that implemented it) is not counted. The auditor follows the recheck runner setting as the environment of the run carries it (`OPS_KIT_RECHECK_RUNNER`; unset, the review setting's value, `OPS_KIT_REVIEW_RUNNER`, itself `other` when unset). In a Task these are the values of the `再チェック・マージ後の監査` and review rows in Settings when the Task started or was last resumed, so a later change in Settings reaches it at its next start or resume; outside a Task neither is set, so the auditor is the `other` one, as `auditorOf` in `scripts/post-audit.ts` decides it: for `other`, the other runner than the implementer (for example `codex` when Claude implemented the PR); for `same`, the main reviewer of the implementer's runner under the review setting (`primaryReviewer`). The implementer is the runner of the Task that asked for the PR's jobs (when no job names it, the other of the main reviewer's runner; when that is not known either, `claude`, and `implementerKnown` is `false`).

**Run one PR at a time.** For each selected PR:

1. `bun scripts/post-audit.ts prompt <PR> --dir <dir> [--repo <owner/name>]` makes a fresh clone at the merge commit under `<dir>`, writes the diff and the prompt into it, and prints `{ cwd, prompt, out }`. The prompt fixes the viewpoints: authentication, secrets, input boundaries, permissions, dependencies and licenses, personal data. It asks for line 1 `pass` or `finding`, then one `- <path>:<line> <viewpoint> <what happens>` line per finding, and for no secret value itself
2. `ops-kit job request review <PR> --runner <auditor> --as audit --cwd <cwd> --prompt <prompt> --out <out>` asks the app to run the review as a job (it uses the existing review job; there is no separate way to run it). Inside a Task, write the `job#<id>` it prints as the reason for stopping and end the turn; the app resumes the Task when the job ends. The cost is recorded in the ledger under the Task that asked, which is how audit spending is told apart from other spending
3. `bun scripts/post-audit.ts record <PR> --out <out> [--repo <owner/name>] [--workspace <id>]` reads the output and posts the mark. It writes nothing when line 1 of the output is neither `pass` nor `finding`. `--dry-run` reads and prints what it would write, without writing

For a repository other than the current one, pass `--repo` to all three commands; inside a Task, `record` also takes `--workspace <id>` so the PBI is filed in that repository's backlog. Outside a Task, set `SWITCHBOARD_PROJECT_URL` to that repository's Project; without it, `record` writes nothing when a finding would file a new PBI (when an open PBI with the same title exists, it posts only the mark).

**The mark.** One line on the first line of a PR comment: `[post-audit] pass <merge sha>` or `[post-audit] finding <merge sha>`, where `<merge sha>` is the 40-digit merge commit that was read (`POST_AUDIT` in `scripts/merge-audit.ts`). It is the audit's output: it marks the PR as audited for the selection and the tally, and lifts nothing before a merge. The audit job's own record keeps the first line of its output, and the tally counts it like the mark; the comment is read from the app's stored copy of the PR's comments (the import keeps those for open PRs and at their close, so a comment posted after the merge may never reach it), and only an owner's, member's or collaborator's comment counts. For a finding, the comment also lists the `- <path>:<line> …` lines.

**A finding.** `record` files a PBI titled `PBI: マージ後の監査の指摘 — <owner/name>#<PR>` with the labels `bug` and `security` and the Project fields Status `Backlog`, Priority `P2` and Story Points `2`, whose source is the periodic check, and does not file one if an open PBI with the same title exists. Whether the finding is real is decided when that PBI is worked, and a finding that is not real is closed with the reason.

The audit records feed `bun scripts/merge-audit.ts`: after its table, one line per route gives the PRs audited, the findings and their rate, and a finding on a `recheck` PR counts toward proposing that its kind go back to asking, the same as a revert.

## Branch protection and local results

A local-ci result is a job record of the app; it does not become a GitHub required check (a check run / commit status). If the base branch has a protection or ruleset that requires status checks (or required approvals), GitHub makes the PR `BLOCKED` even when the local result passes, and it cannot be merged. merge-gate does not let this through silently: when it counted CI by local-ci and the PR is `BLOCKED`, it stops with `mergeStateStatus が BLOCKED: base の枝の保護（必須のチェックか承認）がマージを止めている。local-ci の結果はアプリの仕事の記録で、GitHub の必須チェックにはならない` (mergeStateStatus is BLOCKED: the base branch's protection, required checks or approvals, is stopping the merge; the local-ci result is a job record of the app and does not become a GitHub required check). merge-gate does not read the protection settings (that needs admin permission, and the API is not available on some plans), and does not change them. It does not bypass the requirements of review, approval or protection.

The steps for the user to check the settings (whether to change them is the user's decision):

1. `gh api repos/<owner>/<repo>/branches/<base> -q .protected` — `false` means there is no protection. The reason for BLOCKED is a ruleset or a wait for approval
2. If `true`, look at the names of the required checks in the repository's Settings → Branches (or `gh api repos/<owner>/<repo>/branches/<base>/protection/required_status_checks`; admins only). "Require status checks to pass" in Settings → Rules → Rulesets (`gh api repos/<owner>/<repo>/rules/branches/<base>`) is the same
3. While Actions does not start, the required checks cannot be satisfied. To merge, the user removes the requirement only for that period, or brings Actions back to a state where it can run. This repository's scripts do neither
