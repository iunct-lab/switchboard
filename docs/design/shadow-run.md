# Shadow run — 並走 Task（同じ依頼を第二のランナーで）

Issue #99. Claude に出した依頼を、そのまま DAK（草案時の構成はローカル llama.cpp の Qwen で API 料金なし。DAK の接続先を変えれば料金はその先による）にも同時に流し、両方の結果を並べて見るための仕組み。Switchboard は Task ごとに 1 ランナーの前提で作られているので、「並走」は **Task 同士の関係**として持つ。既存の会話・差分・台帳・承認の画面と、DAK 側の設定（`agent_config.yaml`）は一切変えない。

## 関係

| 項目 | 主 Task | 並走 Task |
|---|---|---|
| `Task.shadowOf` | null | 主 Task の id（作成時に決まり、変わらない） |
| runner | 依頼で選んだもの | `shadowRunner`（主と違う検出済みランナー） |
| cwd / scope / title / 最初の依頼文 | — | 主と同じ |
| `routing` | ルール表の記録 | null（並走は判断ではないので `routing_log`（#25 の教師データ）に載せない） |
| `budgetUsd` | 依頼で決めたもの | 主と同じ値（各 Task に同じ上限。有料ランナーの並走も主と同じだけで止まり、無料ランナーは届かないだけ。合算の上限ではない） |
| `scheduleId` | スケジュール発なら id | null（そもそもスケジュールは並走しない。下の「作成」） |
| `permissionMode` | ランナーで解決 | 並走ランナーの保存した既定 / アダプタ既定で解決（DAK は null）。主のモードは引き継がない（ランナー固有のため）。どのモードで始めたかは主の会話に `status` で残る |
| `shadowStopped` | false | 利用者が並走を「中断」したら true（下の「返信の写し」） |

並走 Task は通常の Task で、Rail / Home（実行中・最近）/ Task 画面の見出しに「並走」タグ付きで並ぶ（停止済みは「並走・停止」。Rail は再開待ちタグがあるときはそちらを優先）。Ledger の行にはタグを付けていない。Brief の「並走」行から互いに行き来できる。ルーティングの「前回このリポジトリで使ったランナー」は並走を数えない。

## 作成

`POST /api/tasks` の `shadowRunner`:

- `"dak"` など: その runner で並走 Task を作る。主と同じ runner、または未検出なら **400**（UI はチェックボックスを DAK 未検出のとき無効化する）
- 省略: `Settings.shadowRunner`（`PATCH /api/settings {shadowRunner: "dak" | null}`、Home の「既定にする」）に従う。Inbox 昇格もここを通る。Home でトグルに触れていない作成も省略で送る（既定の判断をデーモンに任せる）
- `null`: 既定があっても並走しない（Home でトグルを外すとこれが送られる）
- **スケジュールは並走しない**（`Scheduler.runNow` が `null` を渡す）。無人実行に並走を付けると、重複実行ガードとキューの scheduled 節が主しか知らないまま並走が溜まり、並走の承認に答える人もいない
- meta workspace の self-dev フック（ターン終了でチェックを走らせる）は並走を無視する。並走のターン終了で主のチェック結果が無効になったり、同じ作業ツリーでチェックが 2 本走ったりしない

主 Task が先に起動し、そのあと並走 Task を作る。**並走が理由で主が失敗することはない**: 既定のランナーが未検出（保存後にコンテナが落ちた等）、既定が主と同じランナー、並走の `start()` が throw — いずれも主 Task の会話に `status` として理由が残り、主は 201 で返る。並走の `start()` が throw した場合は並走 Task が `error` になり、その会話に `error` が残る。主自身の `start()` が throw した場合も、主 Task は `error` と理由を残してから 409 を返す（起動しないまま idle で残らない）。

## 返信の写し

主 Task への追加の返信（`POST /api/tasks/:id/send`、WS `task.send`）は、主が受け取ったあと並走 Task にも同じ文面で送られる（`TaskManager.send` → 主 → `db.shadowTaskOf`）。

- 並走 Task への返信は主に戻らない（並走側だけの追加指示ができる）
- 利用者が並走を「中断」すると `shadowStopped` が立ち、以後写さない。状態は問わない（ターンの途中でも、`done` のまま止めても）。両方の会話に `status` が残る。デーモン再起動で並走が `aborted` になっただけならフラグは立たず、次の返信から写し続ける（`--resume` 相当で再開）
- 並走が **承認待ち**（`waiting`）なら写さない。DAK ではターンを押し込むと開いている確認が deny で閉じてしまうため。両方の会話に「写さなかった」を残し、答えたあと利用者が並走に直接送れる。後から自動で写すことはしない（その間に主が何ターン進むか分からず、順序が保証できない）
- それ以外（`done` / `error` / 再起動で `aborted` / ターンの途中 — アダプタがキューする）は写す。写しに失敗しても主の応答には影響せず、両方の会話に `status` で残る。並走のターンがエラーで終わったときも主の会話に残す（利用者が見ているのは主）
- 写さないターン: usage-limit 自動再開（#102）の `asResume` ターンと、「今すぐ再開」（`send(..., { mirror: false })`）。止まったのは主のランナーで、並走のランナーではない
- 主を中断しても並走は止まらない（独立した Task）。ただし並走が自動再開を予定していたら取り消す（誰も頼んでいないターンで有料ランナーが後から動かないように）
- 返信の前の Terminal 履歴の取り込み（`catchUp`）は主と並走の両方に対して行う
- DAK の agent がセッションを失っていたら（コンテナ再起動で ADK のメモリ上のセッションが消える → 再開チェックが 404）、アダプタは新しいセッションで続け、「文脈は引き継がれません」と `status` で知らせる。以前は error で終わり、以後の返信も同じ id で失敗し続けていた

## 承認・差分・台帳

- 承認は Task ごとに個別。並走 Task の `permission.ask` も UI に届く（主で allow した確認を並走に写すことはしない）
- DAK の書き込みは Workspace MCP の **staging** に留まり、UI で適用するまで作業ツリーに触れない。並走が主 Task の編集を壊すことはないが、並走は主が編集中の作業ツリーを読む（同じ cwd）
- 台帳は Task ごと。DAK はローカルモデルなら `costUsd` 0（`pricing.json` に無いモデルは unpriced）

## やらないこと

- 2 つの会話を左右に並べる比較ビュー（リンクで行き来する。定着したら別 PBI）
- 結果の自動採点・優劣の記録（#25 側）
- 承認の写し、並走 Task から主への逆流、作成後の並走の追加
