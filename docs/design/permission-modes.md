# Permission modes — align with the terminal, change from the UI

Since 2026-09-07. Before this, every Claude task from Switchboard asked for every tool: the adapter passed `--permission-mode default`, and `claude -p` (unlike an interactive `claude`) neither starts in `auto` nor reads `permissions.defaultMode`. Now the runner's own mode is a first-class task property.

## Principle

Switchboard delegates risk decisions to the runner (Knowledge `approval:` rules excepted, since 2026-09-06): Claude Code's `auto` classifier and Codex's sandbox + approval policy + reviewer. Switchboard selects Auto as its default; on Codex, its Auto uses automatic risk review rather than human review at sandbox boundaries. Human approval requests emitted by the runner reach the UI as `permission.ask`. Defaults retain risk review, but can execute approved actions without a human prompt. Unconditional full-access modes are flagged `danger` and must be picked explicitly.

### Counting what the classifier decided

The classifier's decisions are counted per Task, not reported anywhere else. A local Claude Task sends its OpenTelemetry
logs to the daemon's loopback receiver only (metrics and traces off, the parent's `OTEL_*` dropped); the daemon keeps
the `tool_decision` records with an `allow` / `block` verdict as the Task's `classifier.decision` events (verdict, mode,
category, tool and call id — no tool input, no reason text) and shows "allowed M / stopped N" on the Task's Brief. A
`block` does not ask the person: it is `permission_denied` and a failed `tool.result` (Claude Code 2.1.312 and 2.1.314,
recorded). What was recorded asking is the denial limit: the third block in a row and each one after it (2.1.314). The
CLI also asks at the twentieth in a session and on a Chrome floor block (read, not observed). The recorded ask carries
no verdict in OpenTelemetry; it is the `permission.ask` with `reason: "classifier"`, and an allow to it counts as the intervention
kind "after the classifier" rather than as an approval. No such allow has been observed (the recording answers deny, and
no Task has recorded such an ask as of 2026-10-30), so that count is 0 so far. Codex's automatic review and cloud Tasks
are not counted (shown as unknown, not 0). The values are in [claude-otel.md](claude-otel.md).

## Modes per runner

| runner | modes (`permissionMode`) | default | live switch |
|---|---|---|---|
| Claude | `auto` · `acceptEdits` · `default` · `plan` · `dontAsk` · `bypassPermissions` (danger) | `auto` (what an interactive `claude` starts in on Pro / Max / Team) | yes — `set_permission_mode` control request, takes effect immediately (`claude-stream-json.md`) |
| Codex | `auto` · `on-request` (manual boundary review) · `read-only` · `untrusted` · `full-access` (danger) | `auto` = workspace-write + on-request + auto_review | from the next turn — `turn/start` overrides approvalPolicy / sandboxPolicy / approvalsReviewer (`codex-app-server.md`) |
| DAK | none (`permissionModes: []`) | — | — (DAK's `require_confirmation` and `mcp.yaml` decide; same as `adk web`) |

Saved answer policies (`回答の方針`, since 2026-10-17) are checked after the Knowledge `confirm` rules and before `allow`; the runner's approval mode and the runner's own refusals are not changed by them.

Saved instructions (`定型の指示`, since 2026-10-21) only build the text to send: they carry no mode and change neither the approval mode nor the approval rules.

Workspace MCP `exec.run` approvals (`mcp.yaml`) are Switchboard's own and independent of the runner mode.

On Codex, Auto delegates boundary approvals to the runner's risk-based reviewer, comparable in purpose to Claude's classifier. The sandbox and network restrictions remain active. Start, resume and each turn explicitly set `approvalsReviewer`; manual modes reset it to `user`. Rejection can stop an action or lead to a safer alternative, without necessarily opening a human approval dialog. Review notifications and rationale are retained as transcript status events. Manual approval remains a one-time accept, not a persisted command rule. In the manual modes an MCP tool call that Codex asks about becomes a `permission.ask` named `MCP <server>.<tool>`, shown on the approval card like any other; the event also carries the server's own declaration (`mcpHint`: read-only, destructive, write, or unknown). The declaration is the server's claim, so it never lets Switchboard skip the approval or answer for the person.

Auto's workspace-write sandbox also blocks loopback connections to the daemon on this host (`BACKLOG_URL`, `DEVICE_AUTH_URL`, and an extra reviewer listening on localhost). The sandbox network stays closed: when `ops-kit backlog` is refused (`EPERM` / `EACCES`), it says the sandbox blocked the connection and to rerun the same command once as an approved run, and the reviewer decides that run. So that the reviewer finds the permission in the conversation, the implementation prompts (`/pbi-complete` start, resume and another repository, and `すぐ直す`) name as part of the request handing the review material (fresh clone code, PR / Task / PBI bodies, diff) to the other runner and the extra reviewer, and the Issues the skills file (review findings, request Issues and PBIs).

Verified 2026-09-20 on codex-cli 0.155.0-alpha.2.6: `curl -I --max-time 10 https://example.com` failed sandbox DNS, was auto-reviewed as low-risk/approved, then returned HTTP 200 without a manual request. Recorded notifications (outside Git; record your own outside Git with the `runner-adapter-recording` skill): `packages/adapters/codex/fixtures/auto-review-0.155.0-alpha.2.6.jsonl`. Existing Auto tasks receive the reviewer on their next start/resume/turn; a turn already in flight keeps its current setting.

## Allow rules a task gets (2026-11-03)

Auto mode's classifier refused operations the skills ask for — in the 7 days to 2026-10-20, 30 permission stops (merges after the merge gate said merge, posting the gate's marks, resolving review threads, editing skill files), and the user's OK in the conversation did not lift a second refusal. Pushes of rebased branches and Issue / Project Status writes were refused the same way. So the daemon passes Claude Code `permissions.allow` rules to a task, in the same `--settings` JSON as the guard hooks (`taskAllowRules` in `packages/core/src/tasks/sessions.ts`; only when the meta workspace exists, like the hooks):

| rule | why |
|---|---|
| `Bash(bun scripts/merge-gate.ts:*)`, `Bash(bun <meta>/scripts/merge-gate.ts:*)` | the merge: `--merge` / `--merge-stack` merge only on a merge verdict (`--merge-stack` judges the named PR and every PR below it in GitHub's stack (the set `gh stack merge` merges), each at its own head, and merges them with one `gh stack merge` only if all are merge and the stack and heads read again just before the merge are unchanged — GitHub's stack merge takes no expected head or member list, so a push or a change of the stack's members after that last read is not caught; the usage line of `scripts/merge-gate.ts`). The second form is another repository's task |
| `Bash(bun scripts/promote.ts:*)`, `Bash(bun <meta>/scripts/promote.ts:*)` | the promotion after a merge: it counts the busy tasks without the calling one and asks only when none is left, then with `force` (`force` skips the daemon's busy check as a whole; leaving out only the calling task is the script's own count) (exit 1 when others run or wait, 2 when it cannot judge or cannot ask). The second form is another repository's task |
| `Bash(bun scripts/parallel-guard.ts release:*)`, `Bash(bun <meta>/scripts/parallel-guard.ts release:*)` | releasing the task's claim at the end. `claim` and `--takeover` are not included |
| `Bash(ops-kit pr resolve-thread:*)` | resolving a review thread: one mutation, not a general `gh api graphql` |
| `Bash(gh pr comment:*)` | the review, recheck and local CI results the tools post for people to read (the gate reads none of them: it reads the app's job records and the person's grant record). The check in front of `gh` (`docs/design/secret-guard.md`) still reads every post |
| `Bash(gh stack submit:*)`, `Bash(gh stack push:*)` | pushing the stack: these write only the stack's branches |
| `Bash(ops-kit pr push-rebased)` | pushing a rebased branch: no arguments, `--force-with-lease` of the current branch only; it refuses the default branch and a detached HEAD |
| `Bash(ops-kit backlog:*)` | Issue and Project writes go through the app, and the app and the check in front of `gh` read the values |
| `Edit` / `Write` of `//<cwd>/ops-kit/skills/**`, `//<cwd>/.claude/skills/**` and the same under `//<cwd>-*/` | editing the skills in the task's folder and its worktrees (CLAUDE.md names them `<folder>-<topic>`; a worktree is made after the task starts, so it cannot be listed then). A worktree named otherwise is left to auto mode. `~/.claude/skills` is not included |

Not allowed (left to auto mode): a bare `gh pr merge` / `gh stack merge` (it would merge past the gate), a bare `git push --force` / `--force-with-lease` (a prefix match cannot exclude main as the destination), `parallel-guard claim` and `--takeover`, `ops-kit task send` (a hijacked task could send instructions to any other task without approval), a direct `POST /api/daemon/promote` (for example with `curl`; it could send `force`), `gh api graphql`, deploys (`sam deploy`, CloudFormation, IAM — decided 2026-10-29), writing or deleting secrets, destructive host operations. Codex tasks get none (`StartOptions.allow` is read by the Claude adapter only). The permission mode itself stays `auto`.

What this protects and what it does not: only the operations the skills name are allowed, the merge only through the gate, and only in tasks Switchboard starts (a terminal `claude` does not get them). A task runs as the same OS user, so it can do the same by another way (another command, the API directly) — the loopback trust model; the rules are a default so that the skills' steps do not stop, not a fence. A task that starts between the promotion script's check and its request can still be cut by the restart. Stopping a rewrite of main is the job of GitHub's branch protection, not of these rules. Skill edits still reach main only through a PR, the other runner's review and the owner's yes at the gate (the `instructions` ask). A sibling folder that happens to match `<cwd>-*` gets the skill-edit rule too. Whether an allow rule takes effect before auto mode's classifier is checked on a real Claude task after the rules are running (checked 2026-11-03).

## Grants: the person's own words for one refused operation

Auto mode's classifier counts some operations (registering a schedule, changing settings — the soft-deny rules that say the user must name the operation) as allowed only when the person's own message names that operation. Text a task reads with a tool (an Issue comment, an API response) does not count. Answering a choice by its letter (`B`) does not name the operation either.

A grant (`許可文` on screen) is a sentence that names the operation, its target and what it does — "allow only registering schedule X with enabled: false by POST /api/schedules"; a stop's grant may list several, one to a line. It reaches the task as the person's reply, once, by three paths:

- **A choice**: an operational check or a decision may end a choice's line with ` — 許可: <grant>` (the issue-workflow skill's `判断待ちの出し方`). `Ask.grants` carries it per choice. Choosing that choice on the `判断待ち` screen or the task's screen sends the choice's line as it is, grant included.
- **A refused stop**: a stop report with reason `permission` may carry `grant`, allowing only the refused operation (`stopRecoveryPrompt` in `packages/core/src/stops.ts` says how). When the same work needs more than one grant (each PR of a stack), the `grant` lists every sentence, one to a line, and the button sends them all as one reply. A pressed grant is read as one message, like a reply: the ask reason's sentence is read only when every line is a fixed sentence, so a condition the card shows beside it is never dropped, and the stop instruction tells the task to keep other lines out of such a grant. Such a stop is not shown as the runner's refusal: its card has `この操作だけ許可して続ける`, which sends the grant (`answer.kind: "grant"`, with the sentences the card showed as `answer.grant`). The grant is sent and recorded only while that text is still the stop's grant, checked when the answer comes in and again right before it is recorded and sent; a stop reported again with another grant meanwhile gets nothing, and the answer is refused with the question as it is now. A reply the task would refuse when the answer comes in (its budget is spent) records no grant. The send itself can still wait (for the task's process to close) or be refused after that last check; nothing is checked again then, and a grant recorded before such a refusal stays recorded. A stop without a grant stays the runner's refusal, as before.
- **A refused reply to another task**: when `ops-kit task send` is refused, the stop report's `grant` names it: "allow only replying to Task <id> with <gist>" (on screen, `Task <id> に <要旨> を返信することだけ許可します`). Like any grant, it covers that one reply only.
- **A stage task's next prompt**: an answer given on the app's screen to a backlog question is written as a `## 回答` whose operation keeps a `screen` mark. The next stage task's first prompt carries the newest such answer as the person's words (`screenAnswer` in `packages/core/src/backlog-edit.ts`) — only if the comment is still what the screen sent. A `## 回答` written on GitHub, an edited one, or one a saved policy gave is not carried; the task still reads those with `ops-kit backlog view`. A stop's grant is not written there: a stop that takes a person's answer, of any task, is answered as a reply to that task (below).

A grant does not spread: it is never saved as an answer policy (`POST /api/asks/answer` refuses a grant with a policy, and a question with a grant offers no scope), never becomes a `--settings` allow rule, and applies to no other task and to no later operation of the same task. Whether a grant lets the operation through is the runner's classifier's decision; Switchboard does not change it.

What this does not protect: a task runs as the same OS user, so it can call the answer API itself and send a grant to a task (the loopback trust model). The runner's classifier then judges that call as what it is.

### Merge grants: the person's words, read by a separate reader, and two fixed sentences

Some operations a task must not take without the person: merging a pull request the merge gate did not approve. The person lets it through in the task's conversation, in two ways.

**In their own words.** The person writes to the task however they like ("go ahead and merge it", "yes, that one"). The task never decides what that meant: the daemon hands the person's text, and the task's last reply before it (which says what "it" points at), to a reader that is a separate LLM turn of the configured judge runner (the fallback runner when that fails). The reader runs as the judge's turns do (in the runner's read-only permission mode, where the runner has permission modes) and sees none of the task's conversation beyond those two texts.

- Only a text recorded as `owner` is read (see "What `by` means" below); a text another task sent, or a bare call of the API, is not.
- A grant read this way is for the task's own repositories only (the reader is told to return none that names another repository). A pull request of another repository needs the fixed sentence that starts with `<owner/name> の ` (below).
- Two texts the person only passes on are not read either: the grant sentence a task wrote in its stop, when the person presses it, and an Issue's answer that the start of a stage hands to the new task (that answer gives its grants to one task only, and a read that ends late or finds nothing would not keep that). Only the fixed sentences below count there.
- The reader is told that only the person's text consents; the reply before it is context and consents to nothing.
- The person does not have to name a kind. What the task asked for in the reply the person answers (the fixed sentences written in that reply, found anywhere in its text) is put to the reader, and the reader reads whether the person agreed to it, to which part of it, and for which number; when the task offered more than one step and the person allowed one, only that one is read. Stop records are not read for this, so a stop reported outside the reply's text leaves the reader with the reply's own words. A `merge` record also answers the `answer` question for the same pull request and head (`hasMergeGrant`, for every way a grant is recorded). Nothing goes the other way: an `answer` consent never lets a merge outside the gate through, also when the task asked for that merge. When the person only says that the merge is fine, with no word for skipping the gate, the reader gives the `answer` kind alone; an agreement ("yes", "OK") to what the task asked gives the kind it asked. For a question tool's answer, the questions are the task's words: only what the person chose or wrote is the person's words: the chosen option's ` — 許可: ` sentence and the free text are read for a fixed sentence (a chosen label is not read as one), and the chosen labels and the free text are put to the reader, and for the reader each answer is paired with its question by number (`質問 n:` is the task's, `- n:` the person's answer), so one label cannot be taken for another question's; the questions go with the reply before it as what the person answers, and a fixed sentence in a question is not what the task asked to be allowed. When the reader reads no consent nothing is recorded, whatever the task asked.
- The reader chooses among candidate numbers only: the `PR #n`, `Task #n`, `#n` and `変更 L<n>` (a line reference such as `#L654` is none) that the person's text names, then those that the reply before it names, at most three. It cannot grant for a number that no text names, and a grant of a kind outside the two below is dropped. A number on a quoted line (starting with `>`) is not a candidate.
- The head is the head the pull request has when the reply arrives, read before the reader runs. A commit pushed while the reader answers is not granted.
- Sending the reply does not wait for the reader. `GET /api/merge-grants` does: while a read of that task is running it holds the answer, for twice the judge's turn time at most and never beyond 110 seconds (under the 120 seconds after which the daemon drops a response that sends nothing), and the check in front of `gh` waits up to 150 seconds for it. Within that limit the answer is not given before the read has finished; a read that takes longer is answered from what is recorded so far, which is no grant, and the person says it again or sends a fixed sentence. With nothing being read it answers at once.
- What was recorded, or that nothing could be read, is one line in the task's conversation. A text that grants nothing says nothing. When the reader cannot be run, the fixed sentences below still work.

**The fixed sentences.** The fast path needs no reader. There are three sentences: the merge outside the gate, and the two that lift the ask reason (one for a pull request, one for a local change). A closing full stop is fine; a longer clause after a sentence, or a different verb, is not a grant. The first is read at the end of any line of a message to the task, or at the end of a part of a line that ` — 許可: ` separates. The two that lift the ask reason are everyday wording, so they are read by letters only from input whose form the app decides:

1. a sentence of a question's chosen option (` — 許可: <sentence>` in its description), which reaches the grant as a structure of its own, whatever the label is and whatever the other questions were answered (a memo sent with the choice is a message of its own: a condition written there does not take the chosen option's sentence back). In an answer to an Issue's `## 判断待ち`, an option written as a quoted line (starting with `>`) is read neither as a line nor by its ` — 許可: ` sentence, and only the memo sent with it is read (a Task's own question reads the chosen option's sentence whatever its first character);
2. the button that presses a sentence the task wrote in its stop;
3. a whole message (a reply, a free answer to an Issue's question) that is nothing but fixed sentences, one to a line (a list mark before one is fine; quoted lines and empty lines are not counted). The free answers of one question tool submission are one message together: a word among them that is no fixed sentence keeps the sentences among them from being read by letters. An answer to a question on an Issue is either a text, which is one message, or a chosen option with a memo, where the memo is a message of its own (item 1). A quoted option line gives nothing, and the memo sent with it is still read.

An answer to a `## 判断待ち` on an Issue is read the same way: the app puts lines of its own in front of the person's input (which question, whether the recommendation stood), and those are not the person's. A chosen option that is a quoted line (starting with `>`) gives neither its line nor its ` — 許可: ` sentence: only the memo sent with it is read. So the chosen option's own line, its sentence and the person's input are read apart from those lines (kept with the answer as its operation's `parts` when that reads other grants than the whole text would; the option's own line, which the task wrote, is marked `選択肢: ` so that it is never a whole line of fixed sentences: it still gives the sentence that is read at the end of a line (the merge outside the gate), and never the two that lift the ask reason, even when the line is nothing but one of them), the heads of the pull requests they name are read when the answer is taken, and the stage task that starts reads the same parts.

Any other message that holds one of them (words before or after it, a condition among them, a sentence inside a free answer or after a ` — 許可: ` the person wrote) is not read by letters: it goes to the reader of the person's own words, who reads a condition or a refusal. A text longer than the reader's limit grants nothing, as what is cut off may hold a condition.

- `PR #<n> を判定の外でマージしてよい` — kind `merge`
- `PR #<n> をマージしてよい` — kind `answer`: the person allows the merge. The consent is recorded with the head the PR had, and the gate reads the record for its ask reason; no mark is posted on the PR
- `変更 L<n> をマージしてよい` — kind `answer` for a local change of the task's workspace; the record's repository is `local:<workspace id>` and its head the tip of the change's branch; the gate reads it for the change's ask reason (`merge-gate.ts --change`)

The refusal messages of the check say the first way works and quote these sentences as the second; the sentences are what a stop report's `grant` carries.

A sentence may start with `<owner/name> の ` to name the repository it is for (`acme/lib の PR #<n> を判定の外でマージしてよい`); without it the sentence is for the task's own repository: the name the backlog of its workspace goes by (the GitHub repository it syncs with; a backlog kept only in the app has a name of its own, and the grant is then also recorded for the GitHub repository the task's directory's `origin` names), else that `origin` alone. A sentence that names none in a task that has none is not recorded: no grant is made for "any repository". A quoted line (one that starts with `>`) is not read — a quote repeats someone's words, it does not give a grant.

The daemon reads every fixed-sentence line in a text sent to a task (a message — `POST /api/tasks/:id/send` or the socket's `task.send` —, a note sent with resume now (`POST /api/tasks/:id/resume`'s `text`, recorded once the resume is sent), a choice or question answer, whose chosen line carries the grant at its end as `— 許可: <sentence>`, and a refused stop's grant answered with `answer.kind: "grant"`; not an answer a saved answer policy made) and stores one record per grant in `task_grants`:

| Field | What it says |
|---|---|
| `task_id` | the task the grant is for; it holds for that task's conversation and is not used up, so a retry of the same merge of the same head is not stopped a second time |
| `repo` | the repository (lower case) the number belongs to |
| `kind`, `target` | which of the two steps, and the PR number |
| `head` | for `merge` and `answer`: the head the pull request had when the grant was recorded (read from GitHub then; for a backlog kept in the app, the tip of the change's branch). Empty when it could not be read |
| `by` | how the text came in: `owner`, `api` or `task:<id>` (below) |
| `source` | the screen answer the sentence was read from (its comment operation's id); empty for a sentence said to the task directly |
| `at` | when it was last given |

**A grant is for the head recorded with it.** A `merge` or `answer` grant answers only for the head recorded with it. For a fixed sentence said to a task, that head is read when the sentence comes in and the grant is recorded at once. For the person's own words it is read when the reply comes in, before the reader runs, and recorded with the grant the reader returns, with the time the reply came in. For a grant in a screen answer of an Issue the answer is kept first, with no head for each pull request its grants name, so that it does not wait for GitHub; the heads are read right after and put with the answer (`heads` of its comment operation). The grant itself is recorded later, when the next stage task starts, with that kept head and without reading the pull request again; a stage task that starts before the heads are in records the grant with none. When the question stopped at a pull request, a grant of that pull request is for the head read by the check the answer went through (the pull request is not read a second time); a check that reads no head, or gets no reply in time, refuses the answer and nothing is kept. A head pushed between the answer and that start is not the head granted, and a head that could not be read when the answer is taken is none: that grant answers for no head. What remains is the time between the person opening the screen and sending the answer: the screen does not send the head it showed, so a commit pushed in that time, or before the read made right after the answer is kept returns, is the head the answer is taken for. A screen answer taken before answers kept their heads has none kept, and its grant is recorded with the head at the start of the stage task. A commit pushed after the head is read is a different head: the check asks again. That includes the rebase GitHub makes after a pull request below it in a stack is merged — the same rule every grant follows (it answers only for the head recorded with it), so there is one notion and not two. A grant whose head could not be read, and every grant recorded before grants carried a head, answers for no head. A merge outside the gate goes through only in a form that hands GitHub the head. The check in front of `gh` asks with the head the command names (`--match-head-commit`), else with the pull request's head now, and adds `--match-head-commit <that head>` to a `gh pr merge` it lets through, so GitHub merges only the head that was checked; a merge through `gh api` (`PUT …/pulls/<n>/merge`) must carry the head as `sha` in its body (`-f` or `--raw-field`) and is checked for that head; a body without it, with another one, or given by `--input` stops. Outside the gate, a command the front reads as a merge goes through only in one fixed shape that it reads as gh does — `gh pr merge <n or github.com PR URL>` (a PR number of up to nine digits) with, optionally, `-R <owner/name>`, one of `--rebase` / `--merge` / `--squash`, `--delete-branch` and `--match-head-commit <head>` (40 lower-case hex digits), or `gh api -X PUT repos/<o>/<r>/pulls/<n>/merge` (one `-X`, the same nine-digit number) with the field `sha` (the granted head) and, optionally, `merge_method`, `commit_title` and `commit_message`, each once, by `-f`, `-F`, `--field` or `--raw-field` (`sha` by `-f` or `--raw-field` only, so it goes as the text written) — and any other shape is stopped (for example a flag's value, a group of short flags, a PR URL and `-R` naming different repositories, a body from `--input`) rather than guessed at. `gh pr merge` gets `-R <owner/name>` added for the repository the grant was checked for (the URL's or `-R`'s; with neither, the one the front reads for the clone: `GH_REPO`, else the clone's default repository), so gh does not pick another remote. With `-R` set, gh does not touch the local clone, so `--delete-branch` deletes the remote branch only and leaves the local one; the `gh api` shape names its repository. The grant is recorded by `owner/name` with no host, so `GH_HOST` naming a host other than github.com stops the merge; a host gh picks from its own configuration is not checked. Which commands it reads as a merge at all is listed in `secret-guard.md` ("Merges"). A merge written so that the front does not read it as one is not caught by this check; that is a known gap, not an allowance: outside the gate only the fixed shape above is allowed, with the granted head handed to GitHub. `gh stack merge` cannot carry a head, and the front does not read the pull request of a GraphQL `mergePullRequest`, so neither is asked about and both stop before the app is consulted; only the gate's own merge (the gate job the app runs, `daemon-jobs.md`; no variable of the Task's shell stands for it) runs `gh stack merge`, and a stack is advanced outside the gate one pull request at a time from the bottom with `gh pr merge <n> --rebase --match-head-commit <head>`.

**What `by` means, and what it does not.** On loopback the daemon cannot tell the person from a task: both reach the same routes as the same OS user, and a task can also write the database. So `by` records how the text came in, not who typed it:

- `owner` — nothing said it was someone else: the request named no sending task and looked like the web UI's (this origin with `Sec-Fetch-Site: same-origin`; on the cloud host, the login cookie). A screen answer of the Issue is the same rule one step earlier: an answer route (`POST /api/backlog/:n/answer`, `POST /api/asks/answer`) marks an answer as the screen's only when its own request looked like the web UI's and named no sending task; an answer a bare call or a task posted still answers the question, is kept with `by: api` / `by: task:<id>` on its stored operation, and is never the person's words or permission to the next stage task.
- `api` — the request named no sending task and did not look like the web UI's: a bare call of the API, also over the socket (`task.send`; the web UI does not send replies there).
- `task:<id>` — the request said it came from that task. `POST /api/tasks/:id/send` takes `from` (`ops-kit task send` always sends it): the text then reaches the runner under the line `（Task <id> からの返信）`, which the daemon writes. `POST /api/backlog/:n/answer` takes the same `from`.

Every route that can record a grant decides this through one function (`grantSource` in `packages/core/src/server/task-hooks.ts`): `POST /api/tasks/:id/send`, `POST /api/tasks/:id/resume`, `POST /api/asks/answer` (a reply to a task's question, and an answer to an Issue's), `POST /api/backlog/:n/answer`, and the start of a stage task, which records the grants of an answer those routes marked. The socket's `task.send` is always `api`. A caller of the recording function that does not say how the text came in is recorded as `api`.

Only `owner` answers a check. This is advice against mistakes — a forgotten `from`, a text relayed from another task, a bare `curl` — and **not a boundary**: a task that sets the two headers, or leaves `from` out of a request made to look like the screen's, is recorded as `owner`. The same holds for which task a check speaks for: the check in front of `gh` reads the task from `OPS_KIT_TASK_ID` and finds the app through `BACKLOG_URL`, both of which the task's own shell can change. The record keeps a slip from passing; it does not fence a task.

A question tool's option may carry a grant sentence in its description (`… — 許可: <sentence>`); choosing that option sends the sentence as part of the answer. For the reader of the person's own words, each answer is put on a numbered line paired with its question; a line break in what the task wrote (a question, an option's label) is flattened to one line there, while the person's free text keeps its lines, so a quoted line stays quoted and a fixed sentence among other words is left to the reader. The screen shows the description beside the option's label, so the sentence is visible where the choice is made. The person's text is not shortened there; only a long question is, keeping its start and its end. When the person's text is longer than the reader is given, nothing is granted and the conversation says so (the person says it shorter, or sends the fixed sentence).

A stage task with an Issue gets the person's answer to a decision as its Issue's `## 回答`, which starts the next stage task; the grant sentences in that answer (the screen's, as `screenAnswer` reads it — the newest answer of the Issue or of one of its Tasks) are stored for the first stage task other than a `check` stage task started after that answer, whatever started it (the answer, a button or a schedule), and not for later ones. That an answer gave its grants is read from the records themselves: an answer whose id stands in a record's `source` (other than an old `scope` row, which is not read) is spent, however long ago and however many answers came since. An answer without a grant sentence leaves no record. A stage task's stop answered with its grant (`answer.kind: "grant"`) is not this path: the sentence goes to the stopped task as one reply, as a text reply does, and is recorded for that task (`by` follows the same rule); unlike a text reply, it is not copied to a shadow running alongside that task. If the reply cannot be sent (the task's budget), the answer reports `failed` with the reason and the stop stays open.

The record only answers; what stops a step is its caller. `GET /api/merge-grants?taskId=&repo=&kind=&target=&head=` (`{ granted }`) is for a check in front of `gh` that refuses a merge without a grant; where no such check runs, these records stop nothing. `head` is the head about to be merged, or the head the answer is asked for; a `merge` or `answer` check without it is answered `false`. The caller asks with the repository it is about to write to: the one the command names (`-R`, `GH_REPO`, the path of a `gh api` call, a pull request URL), else the clone's own; when it cannot tell which, it does not ask and refuses. It needs `repo` (400 without it) and uses the same login as the rest of the API. As above, a task runs as the same OS user and can send these sentences to itself through the API without `from`; the record keeps a slip from passing, it does not fence a task.

The sentence that let a task add a path to its own body (kind `scope`) and the record of the gate's stop for a file the body does not name are gone: the gate does not stop for such a file (it lists them when the Task's body names paths), and `ops-kit backlog edit` saves a body that names more paths without asking. The daemon neither records nor answers `scope` (`GET /api/merge-grants` refuses the kind with 400, and `/api/merge-grants/scope-stop` does not exist). The table `task_scope_stops` and the `scope` rows of `task_grants` stay, unread, because migrations only add and a rolled-back release reads them.

The tables `merge_grants` and `merge_scope_stops` held these records before they named a repository and a giver. Their rows were moved once (under the repository of each task's workspace, as the person's; the answers remembered as used became spent sources) and the tables stay, unread, because migrations only add. The moved rows did not say how their text had come in (a text another task sent used to be recorded like the person's) and carry no head, so none of them answers a `merge` or `answer` check: the person is asked again. A release rolled back to writes its list of used answers into the settings again; it is folded into the records at every start, not once.

## Where the value comes from

`TaskManager.resolvePermissionMode`: explicit `CreateTaskInput.permissionMode` → saved runner default (`settings.defaultPermissionMode[runner]`) → adapter default. The resolved value is stored on the task (`tasks.permission_mode`) so the record says what the task actually ran with; a runner without modes stores `null`. Unknown values are rejected with 400 (`RunnerAdapter.permissionModes` is the authority); a stale saved default falls back to the adapter default instead of failing the task.

## API

- `GET /api/health` — `runners[].permissionModes` (value / label / description / danger) and `runners[].defaultPermissionMode` (effective: saved setting, else adapter default).
- `GET /api/settings` / `PATCH /api/settings {defaultPermissionMode: {claude: "plan", codex: null}}` — save / clear a runner default (sqlite `settings` table). Validated against the runner's list.
- `POST /api/tasks {…, permissionMode}` — per task.
- `POST /api/tasks/:id/permission-mode {mode}` — change an existing task. Live session with `setPermissionMode` → the runner is asked first and the record changes only once it confirmed (Claude answers the control request; a refusal is a 409 and a `permission mode not changed` note; Codex applies from its next turn); otherwise the idle process is released and the next turn resumes with the new mode (a turn in flight keeps taking follow-ups on the old process and the restart happens at the next idle turn — never two processes). A `status` line records the change in the transcript.

A mode flagged `danger` cannot be saved as a default (400) — it is a per-task choice, because schedules run unattended on the default. `null` clears a saved default even for a runner that is no longer detected.

Tasks created before 2026-09-07 have `permission_mode` NULL; when such a task is resumed the mode is resolved the same way (saved default → adapter default) and recorded on the row.

Schedules carry no mode of their own: a fired task uses the saved runner default.
