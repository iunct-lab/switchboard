# perf (measuring the speed of the main operations under the same conditions)

Measure the speed of Switchboard's main operations (starting up, starting a Task, opening one, sending) under the same conditions with one command. The point is to decide where it is slow by numbers, and to check the effect of making it faster by a before-and-after comparison.
The measurement stays local. The measure is kept on the page and is sent only to one's own daemon, as a record of everyday use (see "Recording from everyday use" below; it is not sent outside — within what the README's "No keys, no telemetry" covers). The CI ratchet is in "Ratchet (the CI ceilings)" below.

## Background (what it draws on)

Reference: the work that made claude.ai faster (https://claude.dev/blog/how-we-made-claude-ai-faster). The main points:

- **Align by journey**: measurement was placed on the 4 user journeys that make up 95% of use (start up / start a conversation / open an existing conversation / send), each in the form "starts with a user action, ends when the result is drawn". It lets you see whether the work is the client's or the server's, and compare screens with each other
- **Do not rely on the wall clock alone**: durations wobble, so in the lab they also measured numbers that do not wobble (instruction counts, React commit counts, the number of style recalculations and DOM changes, headless Chrome's frame control), and used them after confirming that they help the wall-clock improvement
- **Ratchet**: a benchmark that has been confirmed becomes a CI ceiling, and a PR that makes things worse fails. When a number gets better, a nightly job lowers the ceiling (a ceiling only goes down)
- **Loop**: find a slow place → make a benchmark that reproduces it in the lab → a small PR → measure after the deploy → if it worked, fix it with the ratchet, if not, redo it → the next slow place. In 2 weeks the geometric mean of 13 measurements became 3.1 times faster

Similar outside mechanisms: Lighthouse CI's assertions (fail CI on a ceiling per metric) and size-limit (a ceiling on the size of the bundled result). Both stop at "set a ceiling and fail when it is exceeded"; the part that lowers the ceiling automatically is our own.

Switchboard does not do instruction counts (Valgrind) or 120 Hz frame control (out of scope. The Web UI's weight is on the browser's side, and we first see whether the number of requests and Chrome's `LayoutCount` / `RecalcStyleCount` are enough).

## The four journeys and `open-task-huge`

`journeyStart(name)` in `apps/web/src/perf.ts` places `performance.mark("sb:<name>:start")`, and `journeyEnd(name)` leaves `performance.measure("sb:<name>")` after the drawing (2 `requestAnimationFrame`s) (the start time is taken when the end is called; it does not move even if the same journey starts while waiting for the drawing). An end with no start, and a double end, do nothing. When the operation fails it is thrown away with `journeyCancel(name)` (so that a later unrelated end does not close it). The names are the `Journey` in `packages/protocol/src/model.ts`.

| Journey | Start | End |
|---|---|---|
| `launch` | The page load (`performance.timeOrigin`; no mark is placed) | `App.tsx`: the drawing after both `api.tasks()` and `api.health()` have returned (the list is shown, and the runner in the input box and `開始` are usable) |
| `new-task` | The top of `createTask` in `App.tsx` (Home's `開始`; thrown away if the creation fails) | `TaskView.tsx`: after the first item of the transcript has been drawn |
| `open-task` | `openTaskFromRail` in `App.tsx` (a Task was pressed in the Rail. Pressing the Task that is already open again, and a transition from another screen, are not measured) | `TaskView.tsx`: after the last item of the loaded transcript has been drawn. The transcript is drawn from the last 200 items, and earlier ones are added with `以前の会話を読む` |
| `send` | The top of `send()` in `TaskView.tsx` | `TaskView.tsx`: after the events that contain a `session.end` newer than the time of sending have been drawn (thrown away if the sending fails) |

**`open-task-huge`** (perf-bench only, not a `Journey` of the app): after `send`, perf-bench makes a task of 20,000 events named `huge` and opens it from the Rail. It reads the same `sb:open-task` measure (the app's action is the same open; only the bench names the size) and clears that measure before the action, so the second open in the page is not read as the first. It comes last so that the four journeys' counts do not move: made before `launch`, it would add a row to the Rail. Why 20,000: a large real task holds tens of thousands of events, and 20,000 is the order of the biggest. Since the task screen reads the last page only (below), its responses are about as big as the 2,000-event `open-task`'s. Its `bytes`, compared with the tag before, catches a change that reads the whole task again: with 20,000 events that grows by an order of magnitude, far over 1%.

The events of the Task detail `GET /api/tasks/:id` are the last 200 (`limit`, at most 5000; `limit=0` gives the other fields without events). The previous page is `?before=<seq>&limit=` on the same route. When the cut falls in the middle of a reply (where `message.delta`s with the same `messageId` continue; a long reply is several hundred of them), it is returned including everything back to that reply's first delta (so the screen does not start in the middle of a reply.). One answer holds at most 5000 items (the same as the upper limit of `limit`), and a reply longer than that is cut there. For this reason `bytes` in "Task size" below is the size of the last answer. `events` is counted by the last seq. The catch-up read after a reconnect, `?after=`, returns everything without cutting. No new route is made; an argument is added.

## Recording from everyday use

To notice slowness that does not show in the lab (the amount of real data, the real network, smartphones), and to check by comparing periods whether an improvement worked in real use, the journeys that ended in everyday operation are also recorded. There is one user, so it is not statistics: the same person's same operation is compared by period and by Task size.

- **What**: every time `journeyEnd` leaves a measure, `{ journey, device, build, ms, taskId, bytes, events }`. `build` is the hash in the file name of the JS of the loaded module (the `<hash>` of `/assets/index-<hash>.js`; `dev` on the dev server); it is recorded but not used in the aggregation. `device` is `mobile` when the screen width is under 700px, otherwise `desktop`
- **Task size** (`open-task` / `send` only; `launch` / `new-task` are null): `taskId` = the id of the Task that was drawn, `events` = the seq of that Task's last event (the screen holds only the tail since the paging was introduced, so the Task's size is counted by seq, not by the number it holds. The gap from what moved to S3 is also counted), `bytes` = the size in bytes (after decompression) of the response of that Task's last `GET /api/tasks/:id` without a query (since the paging, the tail: going back to the start of the reply, at most 5000 items). `bytes` is taken from the browser's Resource Timing `decodedBodySize`, and `req` in `api.ts` is not changed. The catch-up read after a reconnect (`?after=`), the re-fetch after a turn (`?limit=0`) and the previous page (`?before=`) are not the Task's size, so they are excluded. When the Resource Timing buffer (250 entries by browser default) is full, it is cleared so that later responses are also recorded (what dropped when it was cleared is null = unknown). The columns are `task_id` / `bytes` / `events` of `perf_samples`. Rows from before these columns stay null (they are not filled in). A new field may not be omitted, so a POST of the old shape from a tab that has been open since before the promotion is dropped with a 400 (no compatibility layer is made)
- **Where to**: the Web UI (`apps/web/src/perf.ts`) sends them together every 5 seconds (up to 50 at a time; the excess is dropped) with `POST /api/perf` to its own daemon, and they go into `perf_samples` in the daemon's DB. The sending uses the existing `req()` (with the auth header). If it fails it is not resent and no error is shown (it does not stop the operation). But the common handling of `req()` remains (when the cloud host is stopped or the passkey cookie has expired, it moves to the login screen. The next operation's API does the same, so it is not separated). Durations over the API's limit (10 minutes per item) (a turn over 10 minutes, a tab that was in the background until it ended) are not sent. If the tab is closed during the 5-second wait, or the browser discards a background page, what was waiting is lost (if it only went to the background, it is sent when it comes back. `sendBeacon` cannot attach the auth header, so it is not used; the last 1 or 2 items of a short use may be missing). Nothing is sent to an external measurement service. perf-bench does not count this POST in `requests` (it is not the journey's work)
- **When it is deleted**: on every save, rows older than 30 days are deleted. There is no periodic job
- **Where to look**: the sub-heading `速さ` of the `運用` section of Insights (`GET /api/perf/summary`). The Ledger screen has only a link to it. Rows = journey × device × size class, columns = the median / p90 / count of the last 7 days, the same numbers for the 7 days before that, and the change. A row whose median of the last 7 days is 20% or more slower than that of the 7 days before is red (the change is judged on the value rounded to 0.1%, so the figure in the table and the red do not disagree). A row with no records in one of the periods is also shown, and that row does not turn red. There is no notification when it gets slower. It does not follow Insights' switch between `直近 7 日 / 30 日` (because the comparison is fixed at 7 days)
- **Size classes**: by `events` (the last seq; what moved to S3 is also counted): `small` up to 1,000 items / `medium` up to 5,000 / `large` over 5,000; a row with no count (`launch` / `new-task`, rows from before the column was added) is "—". The boundaries are constants. It is to tell whether only big Tasks got slower or all sizes did
- **Period comparison**: the last 7 days (from now back to 7 days ago) and the 7 days before that (from 14 days ago to 7 days ago). The count, the median and the p90 (nearest-rank) are computed from all the rows of each period. The period is fixed at 7 days and is not a setting (there is no `?days=`)
- **Why the comparison by build was dropped**: it used to compare "this build vs the previous build" (build = `build`), but builds were replaced within hours, and a promotion of core alone does not change the web hash, so the two builds being compared were often both fragmentary or did not have a change between them. Comparing by period does not depend on the number of promotions. Instead, the effect of one change is looked at over a period that spans the day the change went in (wait 7 days before and after the change)

## How to run

```bash
bun run --cwd apps/web build
bun scripts/perf-bench.ts [--runs N] [--json <file>]      # N の既定は 5。Chrome は CHROME_BIN、無ければ /usr/bin/google-chrome → /usr/local/bin/chromium
```

On each run, with a fresh daemon (`SWITCHBOARD_HOME` is a temporary directory) and a fresh tab, it runs the 4 journeys in order: open `/` (`launch`) → choose a Workspace on Home and send (`new-task`) → go back to Home and press `long` in the Rail (`open-task`) → send a reply (`send`).

- Fake runner: the prompt `long` emits 2,000 events (`tool.call` / `tool.result` / the assistant's `message.delta` in a fixed order); any other prompt emits 200 `message.delta`s and then `session.end`. The `long` Task is made and finished through the API before the start
- Browser: headless Chrome, 1280×800, `prefers-reduced-motion: reduce` (the pulse of the running dot recalculates styles every frame, so `RecalcStyleCount` wobbled in proportion to time). Fonts (`fonts.googleapis.com` / `fonts.gstatic.com`) are blocked with `Network.setBlockedURLs`
- Home's Workspace is not set to `自動` (a turn where the runner chooses would be inserted)

## Load and overlap

The four journeys run on a nearly empty home, so they show neither what grows with the data nor the delay when background work overlaps. After them `perf-bench` always measures `launch` and `send` once more on another daemon, in one run (`LOADED_RUNS`; `--runs` does not apply). local-ci skips it for a change that does not reach perf-bench (`--skip-loaded`; the result then has `loadedSkipped` and no `loaded`, and the ceiling is not judged); the tag CI and Actions always measure it ([local-ci.md](local-ci.md), "Perf is not measured in a PR's run").

- **Size**: `LOAD` in `scripts/perf-load.ts`: 1,500 Tasks, 30,000 backlog records, 4,000 `backlog_operations`, sized after a real home. `seedLoad` makes them through `Db` and the real import; nothing is read or copied from a real home. The database is about 80 MB, the real size. It is generated once before the runs, and each run starts a daemon on a copy.
- **What overlaps** (with `launch` only): (a) one `POST /api/backlog/sync`. The fake GitHub (`loadGh`) raises its `generation`, so the import rewrites every Issue: heavier than a usual import, on the side of not missing a stall. (b) The rescue page's status check: `checkDaemon` and `tasksThatStop` from `rescue/src/promote.ts`, called as they are every 2 s.
- **Window**: from the start of the import until both the journey has gone quiet and the import has answered. The wait for quiet before the action is outside it. Only `launch` has a window: `send` runs on the same loaded daemon with no import, and opening `long` before it is not counted. A failed import fails the run. A loaded journey waits up to 5 minutes, so a daemon stuck for longer than the journeys' usual 30 s reads as a high value rather than a timeout.
- **Daemon delay**: `/api/health` every 50 ms inside the window, keeping the longest. The value is that window's longest. The daemon shares this process with the measuring code, so a stall stops the timer too: the time counts from when the call was due. Counted from the start of the call, a stall would read as the fast answer after it.
- **Why one run and one import**: several runs with several imports each would make every local CI run take minutes while it holds the machine's heavy-job slot, and other heavy jobs would wait behind it. The measure only has to tell a daemon stuck for minutes from a working one; a stall of a few seconds stays inside the spread of the same code even with several runs. One import under `launch` keeps the first and costs a fraction of the imports.
- **Duration**: how long `loaded` adds to a perf-bench run depends on the machine; read it from the run's own output.
- **When `loaded.healthMaxMs` rises far above its ceiling**: profile one run (`bun --cpu-prof scripts/perf-bench.ts --runs 1`) and look for one long synchronous stretch inside the import. This number measures the longest stall of the daemon's event loop, not the number of concurrent `gh` calls, so the fix is to break the work up or index it (a scan over all the stored records for every Issue is the kind of work that shows here), not to lower the concurrency.

`loaded` in the result JSON:

```json
{ "tasks": 1500, "backlogRecords": 30000, "operations": 4000, "overlap": ["backlog-sync", "rescue-status"],
  "journeys": { "launch": { "msMedian": 0, "msP90": 0 }, "send": { "msMedian": 0, "msP90": 0 } },
  "healthMaxMs": 0, "healthMaxMsP90": 0 }
```

With one run, `healthMaxMs` and `healthMaxMsP90` are both that run's value (the fields keep the shape of several runs). The `launch` / `send` times are for reading in the table, like every time in this document; they are no ceiling.

## What the numbers mean

A journey's numbers are the difference from just before the operation to "the measure appearing and the `/api/` traffic having been quiet for 500ms" (the rest of the stream and the re-fetches it triggers are also counted in that journey). Before the operation too, it waits for the same quiet (so that loading the screen starts by itself — Home's candidate query has a 250ms debounce — is counted in neither the previous nor the next journey). The values in the table and in the JSON are the median of N runs.

| Name | Meaning | Wobble |
|---|---|---|
| `msMedian` / `msP90` | The median / p90 (nearest-rank) of the duration (ms) of `sb:<journey>` | Wobbles. It is also dragged by the host's load (it became 2 to 3 times when run at the same time as another heavy job). It is only looked at in the table, and not used for comparison or CI |
| `requests` | The number of requests to `/api/` (CDP's `Network.requestWillBeSent`. WebSocket and the measurement's own `POST /api/perf` are not included) | Only `new-task` wobbled by ±1: Home re-read `/api/history` on every change of the Task list, and depending on whether the creation's response and the WebSocket's `task.updated` were gathered into one drawing, it was 1 or 2 times (the app's behavior). Home no longer does this re-read, so check the count by measuring |
| `layoutCount` | The difference in `Performance.getMetrics`'s `LayoutCount` | ±1 (the difference of whether concurrent API responses gather into the same frame or split. It is not removed even by frame control) |
| `recalcStyleCount` | The difference in `RecalcStyleCount`, likewise | ±1 (the same reason as `layoutCount`. Without reduced motion it wobbles by tens in proportion to time) |
| `layoutShift` | The sum of the values of `PerformanceObserver` (`layout-shift`, excluding right after input) | The lower decimal digits wobble. A screen whose layout changes with timing spreads more (`launch` spread over a range wider than its band on the same commit when the temporary directory moved from RAM to disk) |
| `bytes` | The size of the journey's `/api/` responses: the sum of CDP's `Network.loadingFinished` `encodedDataLength` over the same requests as `requests` (not `POST /api/perf`). The daemon does not compress, so this is the responses' size | Does not wobble: repeated `--runs 5` give the same value every time, for every journey. The daemon writes the responses, whatever the Chrome. The bench's tasks run in a repository perf-bench makes, not in the checkout: a task's cwd is in its responses, and so is its footprint (the files and bytes under the cwd). With the checkout, a local-ci worktree's longer path moved `bytes`, and so did the checkout growing by a few files (one more digit, one more byte). The bench's repository has a path of fixed length (`/tmp/sb-perf-bench-repo-XXXXXX/repo`), one README in one commit, and a sparse file of 11,000,000 B left out of Git, which keeps the Task screen's context meter full, as the checkout does |
| `bundle` | The total bytes of `apps/web/dist/assets/*.js` / `*.css` gzipped | The same for the same code |

The shape of `--json <file>`: `{ runs, journeys: { <name>: { msMedian, msP90, requests, layoutCount, recalcStyleCount, layoutShift, bytes } }, bundle: { js, css } }`. `<name>` is one of `launch`, `new-task`, `open-task`, `send` and `open-task-huge`. `open-task` and `open-task-huge` also have `responses`: `{ "<path shape>": { count, bytes } }`, the same bytes by the shape of the response's path (an id segment such as a task id becomes `:id`), from the last run.
The only one that can be assumed to match when the same code is run twice is `bundle`. `requests`, `layoutCount` and `recalcStyleCount` are compared with a band of ±1. The sources of the wobble are all in how the app's drawing gathers, and cannot be removed on the lab side (frame control is out of scope).

A count that sits on its ceiling flips between runs of the same code: a median on its ceiling is not a band that is too narrow. `launch.layoutShift` can also spread wider than the 2 × 0.03 between over and improved. The bands are left as they are. When a count flips again, the tag still passes: the perf steps do not decide the result (**Perf does not decide the result** below), and the flipped count is a warning in the Release. Neither the band nor the ceiling is moved for one flip and the user is not asked; whether the count keeps coming back is read from the rows on `perf-records` (`spread`).

## Ratchet (the CI ceilings)

How to run the improvement (pick a slow journey → reproduce it in the lab → 1 PR, 1 improvement, with a before-and-after table → measure after the merge → lower the ceiling once the last 3 tags are below it) is in the skill `.claude/skills/perf-loop/SKILL.md`.

**Where this runs: the tag CI, not a PR.** A PR's local CI does not run the perf steps (no web build for the bench, no `fetch main`, no perf-bench, no perf-ratchet), so a PR never fails on the bench's `over:` / `raised:` / `improved:` / `grew:`, and the merge gate counts its `[local-ci] pass` without any perf result. The one ceiling a PR's local CI still compares is its own seconds (`local.durations`, the type check's and `bun test`'s, in the bullet on times below): over it, the PR still passes and its comment carries a warning with the `over: durations.*` line (the seconds do not decide the result, like the perf steps in the tag CI). The tag CI (`scripts/tag-ci.ts`) on the commit main reached runs every step, perf included, and the verdict is in the Release's `## CI` part. The text below says "the PR's value" and "the check" for the measure and the comparison themselves; they happen in the tag CI's run. The perf steps do not decide the tag's result: an `over:` there is a warning in the Release, not a fail (**Perf does not decide the result** below). The comparisons (`grew:` for the bundle and `bytes`, `raised:` for the ceilings) are with the tag before this one (`PERF_BASE_REF`, which `tag-ci.ts` sets; the first tag is compared with `origin/main`'s tip as the tag CI fetches it), so `grew:` / `raised:` show what the tag added. When a tag holds several merges the growth is their sum; which merge it came from is followed with `history` and `git log`. So are `grew:`, `raised:` and `improved:`: the `[tag-ci]` line stays `pass` and the lines are kept as a warning (see the tag CI in `releases-and-rescue.md`). The growth of the bundle and `bytes` over the merges is followed in the rows the tag CI writes to `perf-records` (`history`, **Bundle history** below), and is dealt with after the merge: a request for the fix, or going back to an earlier tag.

**The rule for every count: a value that does not wobble is compared with the tag before (the compared ref), not with a ceiling.** A count that comes out the same every time for the same code has no absolute ceiling. The tag's value is compared with the value of the tag before (the first tag: `origin/main`'s tip), measured in the same run. A PR that adds 1% or more fails (`grew:`); a smaller growth passes and is printed with the difference. The compared ref's value of each run goes to the `perf-records` branch, so growth that adds up over many PRs can be looked back at with `history` (**Bundle history** below). Today that is the bundle and `bytes`, and both share one 1% (`BUNDLE_GROWTH_LIMIT`). Nobody is asked to raise a ceiling for them, and no PR raises one: a ceiling with no room fails every PR that adds a byte, so it only hands the user a decision and prevents nothing. A ceiling that is a few bytes above the value would stop PRs on a response read twice that grew by 22 B, and each stop would ask the user whether to merge. The counts that keep an absolute ceiling, and why:

- `requests`, `layoutCount`, `recalcStyleCount`: the same code moves them by ±1 even as a median of five runs. Judging them against the compared ref would need it measured five times in every run and a band for the comparison; moving them is a change of its own.
- `layoutShift`: moves in its low digits, and on some screens by more than its band (below).
- `loaded.healthMaxMs` and `durations` (the type check's and `bun test`'s seconds): times, moved by the host's load. They are judged on the high side only, and an over is a warning, not a fail.

A new count follows the same split: one that does not wobble is compared with the compared ref and recorded; one that wobbles gets a ceiling, with a band measured for it.

A confirmed number becomes the ceiling, and the ceiling only goes down. The ceilings are in `scripts/perf-budget.json` (`requests` / `layoutCount` / `recalcStyleCount` / `layoutShift` per journey, and `loaded.healthMaxMs` under `local`). The bundle and `bytes` have no ceiling: they are compared with the tag before in the same run (**Bundle** and **`bytes`** below).

`loaded.healthMaxMs` is not compared with other durations, nor are the other durations in "Seconds of `bun test` and the type check (an exception)" below.

`layoutShift` of `open-task` and `layoutCount` of `send` are removed from the ceilings of both environments and are only looked at in the measurement table. The reason is that even within the same code and the same Actions environment, they moved by more than the band depending on how the drawing for the input box disappearing and coming back gathered. The remaining items continue to be judged.

One set of ceilings per environment: `github` (Chrome on Actions' ubuntu-latest) and `local` (the host's Chrome, which local CI uses). `github` when `GITHUB_ACTIONS=true`, otherwise `local` (local CI sets `CI=true` but not `GITHUB_ACTIONS`). It can be chosen again with `--env github|local`. The reason for separating them: even with the fonts aligned (perf-bench shows only Noto Sans + Noto Sans CJK), how the drawing gathers changes with the machine's speed, and numbers that differ by more than the band remain for the same code (the drawing where the input box vanishes for a moment and comes back lands in a different frame on a slower host). The two items removed above did not fit in the band even within one environment. The per-environment ceilings continue to be used for the difference in the measured values of the other items.

```bash
bun scripts/perf-bench.ts --runs 5 --json perf-result.json      # CI と同じ 5 回の中央値（1 回だけだと幅より大きく動く）
bun scripts/perf-ratchet.ts base origin/main perf-base.json   # 比べる相手（タグの CI は前のタグ、PERF_BASE_REF。最初のタグと PR は origin/main の先端）を隣の worktree で build して bundle を測り、その perf-bench を 1 回（--runs 1 --skip-loaded）回して bytes を測る
bun scripts/perf-ratchet.ts check perf-result.json --base perf-base.json   # 超え / 良くなった（これだけでは tag CI は落ちない）/ main より上げた / bundle か bytes の 1% 以上の増加、のどれかがあれば exit 1（その環境の上限で）
bun scripts/perf-ratchet.ts update    # 結果ファイルは取らない。perf-records 枝の counts.tsv の直近 3 タグが続けて ceiling − 2 × 幅 を下回る数だけを、その 3 つの最大 + 幅 に下げる。上げない
bun scripts/perf-ratchet.ts spread --last 10 --env local   # 数ごとの直近のタグの散り（下の表の出し方）
```

- **Band**: a number that moves even for the same code has a fixed band (the ±1 in "What the numbers mean" above. The wobble of the median of 5 runs). `requests` / `layoutCount` / `recalcStyleCount` are 1, and `layoutShift` is 0.03 (the spread of the median of 5 runs of `launch` on one commit). It is not made a setting (the band is the wobble of the same code, not how much worse it may get). `--runs 1` moves by more than the band (`layoutCount` of `launch` spans 4 to 6 over single runs), so give `check` / `update` the result of 5 runs
- **`bytes`**: `open-task` and `open-task-huge` are compared with the tag before, like the bundle; `scripts/perf-budget.json` has no number for them (the other journeys' `bytes` are in the table only). `perf-ratchet.ts base` runs the compared ref's own perf-bench once in its worktree (`--runs 1 --skip-loaded`: a response's size does not wobble, so one run is enough; about a minute more per run), and `perf-base.json` holds `journeys.<name>.bytes` and, when that ref's perf-bench has them, `responses`. `check` prints `bytes: <journey> <n> B (main <m> B, +<d> B, +<p>%)` for both journeys, then each response whose size differs, by the shape of its path: `/api/tasks/:id/evals +22 B × 2` (the same count: the change per response times the count) or `<path> +<d> B（<n> 回、main <m> 回）`. 1% or more above the compared ref's is `grew: bytes.<journey> …` and exit 1, with the same limit as the bundle; under 1% passes. A `perf-base.json` without `journeys` (a ref measured before this was added) judges nothing and says so in one line. This replaced a ceiling with no room (2026-11-04 to 2026-11-05), which failed every PR that added a byte.
- **Ceiling = value + band**: over = value > ceiling, improved = value < ceiling − 2 × band (below the measured value by more than the band). An improved count does not fail the tag CI: it stays in the Release as a ceiling that can be lowered, and `update` lowers it only when the last 3 tags (`LOWER_AFTER`) are all below ceiling − 2 × band, to the largest of those 3 values + the band (one low run is not enough: the next high run of the same code would then be `over`). This replaced a two-sided gate that failed on `improved` and made the improving PR lower the ceiling in the same change. Except `loaded.healthMaxMs`, which is never lowered (see the bullet below). The range of the same code's wobble (measured value ± band) hits neither — when "improved" was ceiling − band, every time the same code gave a value one step below the lowest so far, the CI of unrelated PRs failed. In exchange, a worsening of 1 on the side that does not wobble (for example open-task's `requests` 5 → 6) passes, and so does an improvement up to the band
- **CI**: in the steps of `scripts/ci.ts` (which Actions' `ci.yml` runs), after the web build: fetch `origin/main` → `perf-ratchet.ts base "${PERF_BASE_REF:-origin/main}" perf-base.json` (the tag CI uses the tag before; a PR and the first tag use `origin/main`) → `perf-bench.ts --runs 5` → `perf-ratchet.ts check --base perf-base.json`. `scripts/local-ci.ts` does not run these for a PR; `scripts/tag-ci.ts` runs them for the tag's commit (the same `runCheckout`, with perf on).
- **Raising**: `check` exits 1 if any item is raised above the `scripts/perf-budget.json` of what it compares with (the tag before in the tag CI, otherwise `origin/main`) (not only for the environment measured but for both `github` and `local`; a PR that raised `local` in Actions also fails). A PR's local CI does not run `check`, so a PR that raises does not fail there. Raising is the user's decision, and the user is asked before the merge.The bundle and `bytes` have no ceiling to raise: under 1% nobody is asked, and no PR raises a number for them.
- **Bundle**: the bundle (js / css, gzip) has no ceiling in `scripts/perf-budget.json`, so a PR never edits a number for it. `perf-ratchet.ts base <ref> perf-base.json` builds the compared ref (the tag before in the tag CI, otherwise `origin/main`'s tip) in a worktree next to the checkout (not under `/tmp`, which may be a RAM-backed tmpfs; check with `findmnt /tmp`), and `check --base perf-base.json` compares the merged build with it. It always prints `bundle: js <n> B (main <m> B, +<d> B, +<p>%) / css …`. When js or css is 1% or more above the compared ref's, it prints `grew: bundle.<js|css> …` and exits 1. Under 1% the check passes and prints the growth. Only a PR's Actions run measures a PR this way; its local CI does not, and the tag CI compares with the tag before (above). Outside the tag CI the comparison is with `origin/main`'s tip, not the PR's base branch, so the top of a stack compares the whole stack. 1% is the maintainer's rule, meant to be looked at again (raised or dropped); `bytes` shares it. To change it, edit `BUNDLE_GROWTH_LIMIT` in `scripts/perf-ratchet.ts` and this paragraph. Small growths add up; **Bundle history** below keeps the record of the compared refs' sizes to look back at.
- **Wobble of `layoutShift`**: the user is asked about a red of `launch.layoutShift`. But for a PR that does not touch web, if running local CI twice makes the value wobble around the ceiling (one run over, one under), the user is asked with a recommendation to merge. The user is asked once per stack, with a note of which PRs touch web). A PR's local CI does not measure perf, so this red now shows only in the tag CI
- **Known exceptions**: an excess the user accepted goes in `exceptions` of `scripts/perf-budget.json` as `{ "key": "<env>.journeys.<name>.<count>", "issue": <n> }` (`key` as `raised` prints it). While that Issue is open, `check` prints `known exception:` for the count and does not exit 1. An Issue that is closed or cannot be read (`gh` missing or without a login, as in Actions) makes it `over:` again. An exception the compared ref does not have fails with `added exception:`, and is merged by hand like `raised`. The number is read in the checkout's default repository, and an exception does not cap the value.
- **`loaded.healthMaxMs`** (the daemon's delay under load and overlap): a ceiling in `local` only: no Actions run measured a `github` value, and a ceiling nobody measured is a guess. The value is in `scripts/perf-budget.json`. The band is twice the spread of several one-run measures of the same head, rounded up to 50 ms, with 100 ms as its floor; the ceiling is the lowest of those measures plus the band, rounded up to 50 ms. One run moves by more than a median of five, so the band is wide on purpose: it has to tell a daemon stuck for minutes from a working one, and a stall of a few seconds does not reach it. The `launch` / `send` times under load stay out of the ratchet. It is judged on the high side only, like the seconds of `durations`: above the ceiling is `over`, but far below it is never `improved`, and `update` never lowers it. The load of the host moves it by more than twice a narrow band, which would fail PRs that did not touch it.
- **Seconds of `bun test` and the type check (an exception)**: `local` only, as `durations` in `scripts/perf-budget.json`. These are the seconds of the type check and `bun test` that a local-ci run measures (the `local-ci-seconds` line of its pass). perf-bench does not have them, so `perf-ratchet.ts check` does not compare them: `scripts/local-ci.ts` calls `judgeDurations` after every step passed, and a value above its ceiling does not fail the run: the pass mark stays and the comment gets a warning with an `over: durations.<key>` line. A run that narrowed `bun test` to the affected tests compares the type check only; its `bun test` seconds stay in the `local-ci-seconds` line, and the `local-ci-tests` line of its result says it was narrowed (`ran` is not null), so leave those runs out when setting a ceiling. The tag CI, which runs the whole `bun test`, compares both against the same ceilings and lists an over in the Release's `## CI` without changing the tag's result ("Tag CI" in `releases-and-rescue.md`). A value far below its ceiling gives no warning, because a quiet host moves it down as well; lower a ceiling by hand. Raising one fails as `raised`, like any ceiling, and is the user's call. The band is twice the spread (highest minus lowest) of five runs on the same head with other Tasks running as usual, rounded up to whole seconds. The ceiling is the highest value in recent real local-ci passes plus the band, not the lowest of the five runs used for the band: runs on one head with few running Tasks vary less than real runs, which differ by head, load and recordings. Take the first ceilings from main in local-ci's environment. So a ceiling catches a jump, not a slow creep. The values are in `scripts/perf-budget.json`. `local.durations.test` is the time budget of the whole `bun test`: the budget has no second value or file of its own. On a warning, look at the load first: if another heavy run overlapped, the next runs tell whether the time really grew. If the time really grew, fix the cause. If `durations.test` is still over and no single change caused it, the next step is a test audit: run `bun scripts/test-audit.ts candidates`, and open a PR for the candidates worth removing, merging or making lighter (the `task-to-pr` skill says how to check a removal; the PR's review decides). Raising a ceiling is the last resort, and the user merges that by hand.
- Values: the ceilings in `scripts/perf-budget.json` are measured on main with `--runs 5` (the lowest of several runs + the band; the bundle is the measured value). A ceiling is raised only by the maintainer's decision, when main alone is over and every local CI of a PR that does not touch the Web UI would fail; the history of each change is in the git log of that file. For `github`, the values are one CI run of main on GitHub's runner (`--runs 5`, its medians, no band), and are only lowered from there, by hand: the tag CI writes `local` rows only to `counts.tsv`, so `update --env github` stays `waiting`.

## Perf does not decide the result: records (`perf-records`) and a warning (the Release's `## CI`)

The tag CI runs the perf steps (`bun scripts/perf-bench.ts` and `bun scripts/perf-ratchet.ts check`) but does not count them toward the tag's result. `[tag-ci] pass|fail <sha>` follows the other steps alone (`bun test`, the type check, the build): a tag whose only failed steps are perf's is a pass, and a tag where another step failed is a fail with that step's lines only. The reason is that a count that flips between runs of the same code (the wobble above) turned tags red that no merge had worsened, and telling a flip from a worsening by measuring again cost a second run of the bench for each red tag.

What the perf steps leave instead:

- **The record.** Every run writes the compared ref's bundle and `bytes` and the tag's counts to the `perf-records` branch (below), pass or fail, so a worsening that adds up over merges is read back with `history` and `spread`.
- **The warning.** When a perf step failed, the Release's `## CI` part has a heading line `perf の警告（合否には数えない）:` and, under it, each line the check printed (`over:` / `raised:` / `grew:` / `improved:`, at most 20, indented by 4 spaces, without the machine's file paths). A perf step that failed without a verdict (the bench fell, or the check stopped before judging) leaves one line saying it could not judge. A run whose perf steps all passed has no such heading. The warning is read by a person looking at the Release; it opens no request and moves no ceiling.
- **`improved:`** is a ceiling that can be lowered: `update` lowers it only when the last 3 tags are below it.

A perf step always lets the steps after it run, even in a repository whose CI does not mark it `keepGoing`, so a perf failure never leaves the other steps unjudged.

Every tag's four banded counts per journey (`requests`, `layoutCount`, `recalcStyleCount`, `layoutShift`) are written to `counts.tsv` on the `perf-records` branch, one row per tag, environment and count (`measured_at env tag sha key value`). `bun scripts/perf-ratchet.ts spread [--env github|local] [--last N]` prints each key's values over the last tags, oldest first, with the min, max, spread (max − min), the band and the ceiling, and marks a key whose spread is wider than its band. The same rows are what `update` reads.

### Wobble and worsening

A warning in one Release does not say whether the key wobbled or got worse, so a single `over:` or `grew:` asks nobody for anything. The tag CI reads the warnings it left in the earlier Releases (the lines under `perf の警告（合否には数えない）:`, only the results that carry a `[tag-ci]` mark; a tag without one is passed over, however many, since only every few tags gets a result; the read stops at a Release it cannot read) and counts a key as worsening when the same key (`launch.requests`, `bundle`, `bytes.<journey>`) stands in an `over:` or `grew:` line of 3 results in a row (`PERF_STREAK`). `raised:`, `improved:` and the line saying it could not judge name no key and break the run. A `grew:` line compares a tag with the one before it, so 3 in a row reads as 3 tags that each grew by 1% or more; the growth that adds up is not counted separately.

Only then does Switchboard's own run file one request per key, titled `perf が悪化し続けている: <key>` (`type:request`, from the periodic check); when a request with that title is open, the run adds a comment `<tag> (<sha7>) でも続いた` instead. Nothing new is stored: the count comes from the Releases' text, and the request is filed through the same path as the other tag-CI requests.

Why 3: on 2026-11-12, `counts.tsv` on the `perf-records` branch held 29 tags measured in the `local` environment. Against the ceilings of that day, the longest run of tags over the ceiling for a key that only wobbled (`new-task.recalcStyleCount`) was 2, while `launch.requests` and `new-task.requests` were over for the 3 newest tags in a row, and those 3 came from a change in the code that made them worse. `bun scripts/perf-ratchet.ts spread --env local` prints the same rows to check this again. Asking at 2 would ask about the wobble; at 3 the wobble is not asked about and the worsening is. It is also the 3 that lowers a ceiling (`LOWER_AFTER` in `scripts/perf-ratchet.ts`).

### Keys whose spread is wider than the band

`spread` marks a key whose spread over the last tags is wider than its band. What happens to such a key, and what is decided about it:

- A key with no ceiling is not judged, so it cannot turn a tag red, whatever its spread.
- A key with a ceiling: an `over:` is a warning and `improved:` is too, so the spread does not turn a tag red and the band stays. A flip does not move a ceiling or a band, and the user is not asked about one. A ceiling is looked at again when `spread` shows the key over for several tags in a row.
- Lowering after 3 tags below the ceiling, to the largest of the 3 values + the band, makes a ceiling inside the spread less likely but does not rule it out: 3 low tags in a row can still all sit at the low end of a wider spread (for example 8, 6, 6, 6 under a ceiling of 10 lowers it to 7, and the next 8 of the same code is `over:`). Such an `over:` is a warning like any other and the tag passes.

#### Why `new-task.recalcStyleCount` wobbles

One run of the same code can give 7, 8 or 9, so a single tag's value can sit above its ceiling without a regression.

The cause was found from CDP traces (`devtools.timeline`, with the JS stack of every `ScheduleStyleRecalculation`) and a `MutationObserver` / `fetch` log, between the click on `開始` and the quiet end. Every run draws the same recalculations up to the first conversation, which replaces the placeholder in one commit (this is where `journeyEnd` fires). What changes from run to run is only the tail after that:

- Opening a task mounts the side panel (`Brief`), which reads `footprint`, `ops/load`, `evals`, `checks` and `staging` for the task; in the same window the app reads the task's `device-auth` (`App`) and the task view reads its `artifacts`. Each response ends in its own `setState`, so each is its own React commit. The ones that change styles are the `evals` block (the placeholder `div.hint` is replaced by 41 to 48 elements), the `footprint` meter (`<i style="width">` and `.meter.warn`, 2 elements) and a six-element block that one of the panel's `checks`, `staging` or `ops/load` responses appends (the traces do not tell which of the three).
- A frame runs at most one style recalculation, so commits that land in the same frame cost one recalculation and commits that land in different frames cost one each. The responses arrive within about 50 ms of each other, a few frames wide, so which commits share a frame depends on where the frame boundary falls: all the tail commits in one frame gives one recalculation (total 7); `evals` and the meter in different frames gives two (total 8); the `evals` block, the six-element block and the meter in three frames gives three (total 9). The same split is the `layoutCount` wobble (every extra recalculation here is followed by a layout).
- The mutation log shows the same thing in the DOM: in a 7 run the `evals` rows, the meter and the extra block are added at the same timestamp; in a 9 run they are added about 20 ms apart, with a `requestAnimationFrame` in between.

The cause is therefore the side panel's responses being committed one by one, not a state update that the conversation depends on. The wobble goes away when the panel commits these reads in one update (its reads settled together and set in one `setState`); whether it does is checked by measuring, not assumed. Nothing here changes how the bench measures.

## Bundle history

Each time the tag CI measures the bundle of the ref it compares with, the tag before (the first tag: `origin/main`'s tip) (the `perf-base.json` that its CI steps write for the bundle check), it appends one row to `bundle.tsv` on the branch `perf-records` of the repository, whether the run passed or not. A PR's local CI does not measure it and writes no row. The branch is never merged; the tag CI makes it the first time (a root commit with a README) and adds rows with the GitHub contents API, not in a working tree. The columns are `measured_at` (ISO, UTC), `js` and `css` (gzip bytes, as perf-bench measures them) and `main` (the sha that was measured, for reference). A row is a measure, not a commit: the same commit measured twice is two rows, and a commit nobody measured has none. Writing a row never changes the run's result; a failure prints one line. When another run wrote first, the row is put again once on top of it. Once the file is over 1 MB the contents API no longer returns it, and the tag CI writes nothing and says so (it does not replace the rows); `history` says so too. When the file nears 1 MB, splitting it is a request of its own (nothing here splits it). A GitLab repository, or a checkout whose CI writes no `perf-base.json`, writes nothing.

```bash
bun scripts/perf-ratchet.ts history                       # every row, in time order
bun scripts/perf-ratchet.ts history --since 2026-11-01    # rows measured on or after that day (UTC)
bun scripts/perf-ratchet.ts history --repo <owner/name>   # another repository; without it, this checkout's origin
```

It reads the file once and prints a table: each row's sizes and its increase from the first row of the period, in B and %, then `期間の増加:` (the last row against the first). With no rows it prints `記録なし`. Old commits are not built again to fill the table: the rows start from the first measure after this was added. The increase is a number to look back at; nothing checks it or notifies about it.

The compared ref's `bytes` are kept the same way, in `bytes.tsv` on the same branch, from the same `perf-base.json` (when it has `journeys`). A measure is one row per journey (`open-task`, `open-task-huge`) and response path shape, with the columns `measured_at`, `journey`, `path`, `count`, `bytes` and `main`. When the compared ref's perf-bench gave a journey's total alone, its row has the path `(total)`. `bundle.tsv` keeps its four columns. `history` prints the bytes table after the bundle's, with the same `--since`: per measure, each journey's sum over its paths and its increase from the first measure, then `期間の増加:`. With no rows it prints `bytes: 記録なし`. To see which response grew, read the rows of `bytes.tsv` for two measures. About ten paths per measure make about 20,000 rows before the 1 MB limit above; the same limit and the same rule apply.

## Test flakiness

Local CI runs about 1,400 `bun test`s in one process, so a test with a time assumption can fail from run to run on the same head while passing alone. The usual cause is a child process, an HTTP round trip or a git operation that has to fit into bun test's default per-test limit of 5 seconds, together with a wait bounded by a fixed count of short sleeps.

- **How it is fixed**: the expected values are not changed; only the upper limit of the wait is. The wait is bounded by a deadline (20 seconds), not by a count, and `30_000` is attached to that test. The global default in `bunfig.toml` is not changed (it would hide all the slow tests). It is not wrapped in `retry` (it would hide the wobble)
- **When a new test waits for an external process, HTTP or git**: bound the wait loop with a deadline of `Date.now() - t0 < 20_000`. Do not leave that test's limit at 5 seconds; attach `30_000`, and write the reason in the comment (the form is `}, 30_000);` in `transfer.test.ts`)
- **Ordering**: the value waited for and the value read can be written at different times. A longer limit cannot fix this: wait for the value that is read
- **Idle window**: widen a window that steps depend on, and wait for the release by its state, not a fixed sleep
- **Fixed sleep before a count**: wait for the count, with a deadline
- **Read the failure's duration first**: failures that all land just over 5 s are the limit; a test that fails under its limit is not fixed by a longer one
- **Checking**: run the load build in another worktree. In the same one, a test that reads `apps/web/dist` fails while the build rewrites it

## Current values

The measured values are not copied here, because they change with every tag. Read them where they are kept:

- the ceilings: `scripts/perf-budget.json`
- the values of each tag: `bun scripts/perf-ratchet.ts spread --last 10 --env local` (the `counts.tsv` of the `perf-records` branch), and `bun scripts/perf-ratchet.ts history` for the bundle and `bytes`
- a measure now: `bun scripts/perf-bench.ts --runs 5` on your own host (the numbers depend on the machine, Chrome and the fonts, so compare runs on the same host, not with values written in a document)

When a number differs between environments, check first that the temporary directory is the same: `launch.layoutShift` moves with whether it is RAM or disk, so a bench run for a ceiling and the run that is checked against it should use the same `TMPDIR`.
