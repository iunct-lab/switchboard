# GitLab security review: gitlab.com, self-managed, glab, least privilege

A safety review to read before Switchboard is pointed at a real GitLab (`docs/design/forge-integration.md`, "GitLab"; `docs/design/gitlab-adoption.md`). It is research, not a setup. Switchboard's GitLab support has so far been checked only against a fake `glab`.

Method and limits. Only primary sources are cited: GitLab's patch release notes on `docs.gitlab.com`, the CISA Known Exploited Vulnerabilities catalog, GitLab's product documentation, and the `gitlab-org/cli` repository. News and vendor blog posts were used only as hints about what to look for and are not cited. "Recent" means 2025-11-10 to 2026-11-10. Every item ends with its source and the date it was read: `(checked 2026-11-10)`. Anything that could not be read from a primary source is marked "not verified" and is not guessed. GitLab publishes each advisory on the release date and makes the detailed issues public 90 days later, so "disclosure" below is the release date.

What the sources show about severity and exploitation:

- Since 2026-08-17 there were six GitLab critical patch releases on five dates in about ten weeks (two on 2026-09-23), plus an AI Gateway critical patch release on 2026-10-02, and four of the criticals are unauthenticated (CVE-2026-19478, CVE-2026-85706, CVE-2026-97229, CVE-2026-110264). Two of them are in the CISA KEV catalog, which lists CVE-2026-85706 as added on 2026-09-11 (the day after its patch release) and CVE-2026-97229 as added on 2026-10-29 (https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json, checked 2026-11-10). CVE-2026-110264 was not in the catalog at the time of checking, and its release note reports no observed exploitation (https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/, checked 2026-11-10).
- Two unauthenticated CVSS 10.0 regex-compiler overflows (CVE-2026-97229, CVE-2026-110264) were fixed nine days apart; the second affects every version back to 7.0, and installations that bring their own Ruby also have to upgrade Ruby to 3.3.13, 3.4.12, 4.0.9 or later (https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/, checked 2026-11-10).
- On 2026-10-29 GitLab removed trust for eight compromised intermediate CA certificates (CVE-2026-111943, no CVSS given); self-managed owners must also upgrade GitLab Runner and the AI Gateway separately and rebuild job images that ship their own `ca-certificates` (https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-3-released/, checked 2026-11-10).

A recent problem in how GitLab handled vulnerabilities could not be identified with certainty. No primary source read here describes a failure in GitLab's own handling (a missed fix on gitlab.com, a withdrawn advisory, a patch that did not fix the issue). The candidates the primary sources do support are: (a) CVE-2026-85706 was a CVSS 10.0 unauthenticated file read that CISA listed as exploited one day after the 2026-09-10 fix, and the fix was backported to 19.0 and 18.11 only on 2026-09-23; (b) the run of critical releases above, including two regex-compiler flaws nine days apart. ## gitlab.com and self-managed

gitlab.com. GitLab operates it and patches it itself. Each release note in the Source column of the table above, and the 2026-10-29 release note, states that gitlab.com "is already running the patched version" when the note is published, and that GitLab Dedicated customers need no action, so a gitlab.com user did not have to act on any of them (for example https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/, checked 2026-11-10; the other notes are linked per row). What this does not mean: the window between the code being vulnerable and GitLab fixing it on gitlab.com is not published, and the release notes do not say whether anyone exploited gitlab.com before the fix. That is not verified. Secrets and data on gitlab.com are only as safe as the account and token (see "Least privilege for Switchboard").

Self-managed. The operator applies every fix. The maintenance policy backports security fixes to the current stable release and the two previous monthly releases (19.5, 19.4 and 19.3 at the time of checking), patch releases come twice a month, and "we always address high and critical security issues with a patch release". Exceptions to backport further are possible but rare: the 2026-09-23 and 2026-10-21 releases reached 19.0 and 18.11 (https://docs.gitlab.com/policy/maintenance/, checked 2026-11-10). An instance that is two minor releases behind the window gets no fix and must upgrade first. Because four recent criticals are unauthenticated and two were exploited within days to weeks of the fix, a self-managed instance reachable from the internet has to be patched within days of each critical release; one reachable only from a private network or VPN has a smaller exposure, not zero. A release can also need work outside the GitLab package (Ruby, Runner, AI Gateway, see above), and single-node upgrades with migrations mean downtime (https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-3-released/, checked 2026-11-10).

## glab

- Token storage. By default `glab` stores credentials in the operating system keyring when one is available. With no keyring (a headless host usually has none), or with `--insecure-storage`, it stores the token as plaintext in its global config file; in CI it always uses the config file; running `glab auth login` again moves plaintext credentials into the keyring. Every process of the same OS user, including every Switchboard Task, can read that file (https://gitlab.com/gitlab-org/cli/-/blob/main/docs/source/auth/login.md, checked 2026-11-10).
- Login methods. `--web` is the OAuth browser flow; `--device` is the OAuth device flow for headless hosts (GitLab 17.9 or later); `--token` takes a personal access token on the command line, which leaks to shell history and process lists; `--stdin` reads the token from standard input and is the safe form of token login; `--job-token` is for CI. If `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN` or `OAUTH_TOKEN` is set, glab uses it instead of the stored credentials (https://gitlab.com/gitlab-org/cli/-/blob/main/docs/source/auth/login.md, checked 2026-11-10). The default scopes the web and device flows request are not stated on that page and were not verified; check the consent screen before approving.
- glab's own vulnerabilities. No advisory or CVE for `glab` itself was found. The advisories page of the repository returned HTTP 403 to an unauthenticated read, and the NVD query could not be completed, so "none exist" is not verified. The project's policy is to report through a confidential issue (https://gitlab.com/gitlab-org/cli/-/raw/main/SECURITY.md, checked 2026-11-10). It releases weekly (v1.128.0 on 2026-11-03 is the newest read), so keep it current (https://gitlab.com/api/v4/projects/gitlab-org%2Fcli/releases, checked 2026-11-10).

## Least privilege for Switchboard

What the kit calls. All GitLab traffic goes through `glabApi` in `ops-kit/src/forge-gitlab.ts` (`glab api --hostname <host> -X <method> projects/<path>/…`, REST API v4), plus `glab auth status` to check the login. `glab` is not used for anything else.

| Group | Calls (project-scoped REST) | Needs |
|---|---|---|
| Read | GET issues (list and one), issue notes, milestones by title, merge request (one), its diffs, commits, notes and discussions, `members/all/:id`, `repository/branches/:name` | read access to the API |
| Write issues | PUT issue (title, body, state, labels, milestone), POST issue, POST issue note | write access to the API |
| Write merge requests | POST merge request, POST discussion on a merge request, PUT discussion resolved, POST merge request note, PUT merge request merge | write access to the API |
| Push | `git push` of a branch (not `glab`) | Git write access |

Derived token. The `read_api` scope is "read access to the API"; only `api` is "complete read and write access to the API", and `write_repository` "doesn't support API authentication", so the write calls cannot be made with `read_api` or `write_repository`. The minimum for the full Switchboard flow is therefore a personal access token with the single scope `api`. For a personal token, `api` also grants Git over HTTP, so `write_repository` is not needed in addition when pushing over HTTPS (https://docs.gitlab.com/security/tokens/access_token_scopes/, checked 2026-11-10). A read-only use (import and merge-gate reads, no sending) needs only `read_api`, but the kit uses one `glab` login for both, so that split would need a second login and is not built. Even `read_api` is not harmless: CVE-2026-12664 let a `read_api` token create work items on affected versions (https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/, checked 2026-11-10).

Which token type. GitLab recommends project access tokens with minimal permissions for project automation (https://docs.gitlab.com/user/profile/personal_access_tokens/, checked 2026-11-10), but on gitlab.com "project access tokens require a Premium or Ultimate subscription"; self-managed offers them with any license (https://docs.gitlab.com/user/project/settings/project_access_tokens/, checked 2026-11-10). On a free gitlab.com account the narrowing therefore has to come from the account, not the token: a personal access token "inherit[s] permissions from the user who created them" (https://docs.gitlab.com/security/tokens/, checked 2026-11-10), so use a separate account that is a member of the test project only. Fine-grained personal access tokens are generally available in 19.2 on gitlab.com in the Free tier and can grant permission per resource (https://docs.gitlab.com/auth/tokens/fine_grained_access_tokens/, checked 2026-11-10). Whether one can be restricted to a single project, whether it covers every call in the table, and whether `glab` accepts it were not verified, and the 2026-10-12 release fixed an authorization flaw in fine-grained tokens (CVE-2026-78335); treat them as a later improvement, not the first choice.

Role. Create issue and comment need Guest; creating a merge request needs Developer; merging into the protected default branch needs Maintainer by default, or Developer if the branch's "Allowed to merge" says so (https://docs.gitlab.com/user/permissions/, checked 2026-11-10). These are the minimum roles the calls need. With a single dedicated account on the Free tier, the account that creates the test project in its own namespace is that project's Owner, and its token inherits Owner on that project; the role cannot be lowered without a second account that owns the namespace. The narrowing on gitlab.com Free is therefore what the token can read: the only private data it reaches is that one empty project. It is not a lower role, and it does not stop the account from acting elsewhere: with `api`, the account can still create projects and groups, and comment, open issues and open merge requests from forks on public projects, in its own name.

Expiry. A token expires at midnight UTC on the chosen date; with no date it is 365 days, which is also the default maximum (https://docs.gitlab.com/user/profile/personal_access_tokens/, checked 2026-11-10). Choose a short life for verification (30 days or less), revoke it when the verification ends, and never extend it silently.

2FA. When 2FA is on, the password no longer works for Git over HTTPS or the API, and a token does (https://docs.gitlab.com/user/profile/account/two_factor_authentication/, checked 2026-11-10), so 2FA does not stop Switchboard and should be on for the account that owns the token. WebAuthn registrations are tied to one browser and have no recovery codes, so register a one-time-password app as well.

Isolation. Put the verification project in a separate namespace (the user namespace of the test account, not a group the real work account belongs to; the test account is then its Owner, see "Role"), keep it private, and never push this repository's code to it; only issues, notes and a throwaway branch are needed. A token that leaks then exposes one empty project's data, while the account can still write to public projects in its name (see "Role"); revoke the token as soon as a leak is suspected. Switchboard refuses to send text that holds a GitLab token (`findSecrets`), but that is a last guard, not a storage rule: store the token with `glab auth login --stdin`, on a host with a keyring where possible, and never on the command line (https://docs.gitlab.com/security/tokens/, checked 2026-11-10).

## Recommendation

Going ahead with a verification on gitlab.com is reasonable under these conditions: a new account dedicated to the check (not the account used for real work) with 2FA on, a private test project in that account's own namespace holding no real code and no other project in that account (the account is the project's Owner; the private data the token reaches is that one project, but the account can still write to public projects and create projects, see "Role"), a personal access token with only the `api` scope and an expiry of 30 days or less, `glab` kept current and logged in with `--stdin`, and the token revoked once the verification is done. Self-managed should wait: four of the recent criticals were unauthenticated, two were already exploited, and running one means patching within days of every release (and also Ruby, Runner and AI Gateway); adopt it only after the gitlab.com check and with an owner who accepts that cadence. These findings are as of 2026-11-10; the patch releases of 2025-11 to 2026-01 were not read and those of 2026-02 to 2026-07 only in part (see "Coverage"). The decision to create the account and token, and to proceed, is the operator's.
