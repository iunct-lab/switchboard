# Releases and rescue — a self-update that fails can be undone from a browser

PBI #178, from request #177 (a self-update that fails must have a way back, and forcing an SSH session to repair it is not one). `bun run dev` — `--watch` on the working tree, `docs/design/self-dev.md` — stays as it is for development. This document is about running Switchboard for real: from a release, under **sb-rescue**.

Three layers, each of which works when the one above it is broken:

1. The running daemon is an **immutable release**, not the tree agents edit.
2. A new version becomes current only through a **promotion** that tests it first and goes back by itself.
3. **sb-rescue**, a separate process that shares no code with Switchboard, serves a one-page UI with the buttons to go back — and can start an agent to repair the failed version.

## Layout

```
~/.switchboard/                  (SWITCHBOARD_HOME)
  releases/<sha>/                one commit (the newest 5 promoted, plus current / previous, are kept): `git archive` + `bun install --frozen-lockfile` + the web build
  releases/current -> <sha>      relative symlinks, switched by rename
  releases/previous -> <sha>
  releases/history.jsonl         every promotion, rejection, rollback, restart, restore — one JSON object per line
  snapshots/<time>-<label>.db    `VACUUM INTO` copies of switchboard.db; the newest 3 are kept (`KEEP_SNAPSHOTS`)
  rescue/sb-rescue.js            the installed rescue service (one bundled file)
  rescue-work/<time>/            worktrees of the rescue agent
  daemon.log                     the daemon's output and sb-rescue's notes about it
```

A release is built aside and renamed into place, so a directory named after a commit is always complete. Nothing writes into it afterwards. The history is a file rather than database rows because it has to be readable while Switchboard — and possibly its database — is the thing that is broken. Single-binary releases (#21) can replace the exported tree later without changing anything else here.

The daemon learns two things from its environment: `SWITCHBOARD_REPO_ROOT`, the checkout that is the meta workspace (what agents edit, where self-dev checks run), and `SWITCHBOARD_RESCUE_URL`. On the cloud host it also gets `SWITCHBOARD_WEB_URL`, the distribution's https origin (`/switchboard/web-url`, #399): the rescue page a person opens — the link at the top of the web UI, the one in a failed promotion's PBI — is then that origin's `/rescue/` instead of sb-rescue's own address, which a phone cannot reach. A changed value reaches the daemon with the rescue page's 再起動 (#435). The web UI it serves and the shipped defaults under `packages/core/config/` come from the release it runs from (`codeRoot`), so editing `mcp.yaml` in the working tree does not change the MCP policy of the running daemon.

## Start (Linux)

```bash
bun run rescue:install            # bundles rescue/ into ~/.switchboard/rescue/sb-rescue.js
SWITCHBOARD_REPO_ROOT=/path/to/switchboard bun ~/.switchboard/rescue/sb-rescue.js
```

With no `current` yet, the first start builds the checkout's `HEAD` and makes it current. The daemon listens on `SWITCHBOARD_PORT` (47831) as usual; the rescue page is `http://127.0.0.1:47841/` (`SWITCHBOARD_RESCUE_PORT`; `SWITCHBOARD_RESCUE_HOST` to listen elsewhere — then every request needs the token in `~/.switchboard/token`, and the page is opened with `?token=`). Requests that carry a foreign `Origin` are refused and, on loopback, a `Host` that is not `localhost` / `127.0.0.1` / `[::1]` (#1135, the daemon's rule).

sb-rescue is installed as a bundle so that it does not run from the tree agents edit. It is **not** part of self-update: a change to `rescue/` goes through a reviewed PR, and takes effect when a person runs `bun run rescue:install` again and restarts it. Keeping sb-rescue itself alive is the job of the OS (systemd; the systemd unit and `OnFailure=` belong to the AWS PBI #181).

## What the supervisor does

- Starts `bun packages/core/src/main.ts` from the **resolved** `current` directory, so switching the link affects only the next start.
- Exit code 75 (the daemon's "restart me", `docs/design/self-dev.md`) → start again at once.
- Any other exit → retry after 1 s, 2 s, 4 s; a daemon that lived 30 s counts from zero again. After the third retry it stops at `failed` and **does not change the version**: outside a promotion, a crash loop may have nothing to do with the version (a taken port, a full disk), and the page has the button.

## Promotion

Under sb-rescue a person promotes from two screens through one component (`ReleasePanel`), and is told about a newer version on every screen: **設定画面の「動いている版」** (the running version, HEAD with its subject and 「N コミット先」 or 「最新の版が動いています」, the newest history line, why a tag is held, a failure, and the button 「この版を昇格（<sha>）」), the **header's 「新しい版 <sha> →」** (not a promote button: it opens that section; shown on every screen only while HEAD is ahead of the running version; read when the page loads and when the daemon reconnects, so a promotion's restart clears it), and **a meta-workspace task (Brief → Self-dev)**, the second screen, which shows the same section in place of 「適用してデーモン再起動」. Outside sb-rescue the section is one line (「リリースから動いていないので昇格はありません」) and has no button. The daemon only relays (`POST /api/daemon/promote` → sb-rescue; `GET /api/daemon/release` for the state: `head`, `headSubject`, `ahead` — commits from the running version to HEAD, 0 when HEAD is the running version or inside it, `null` when it cannot be counted — and `busyTasks`) — it cannot be the judge of its own replacement. The button is enabled only when `ahead` is 1 or more. A promotion is per **commit** (the checkout's `HEAD` by default; uncommitted changes are not included and the UI says so), and is refused while tasks are running unless forced, because it ends in a restart. With Tasks running or waiting the first press sends nothing: the section says 「動いている Task N 件: 昇格するとデーモンが再起動します」 and offers 「待たずに昇格する」, which sends with `force`.

1. Build the release if it does not exist. A failing build is a rejection.
2. Snapshot the database. The newest 3 are kept (`KEEP_SNAPSHOTS`; the one being restored is never pruned). To go back further, use Litestream's point-in-time restore (`aws/host/litestream.yml`) or the daily archive (`aws/host/archive.sh`, 30 days).
3. Start the **candidate** on a spare port with a throwaway home and a copy of the snapshot. `SWITCHBOARD_CANDIDATE=1` makes the daemon start no scheduler, no usage-limit resumer and no session-log import, so nothing runs a real runner against the copy. Within 30 s it must pass the check: `/api/health` says ok, `/ws` opens. Like the daemon under the supervisor, the candidate does not get sb-rescue's own `SWITCHBOARD_STARTER_TOKEN` (#2077).
4. Not passed → **rejected**: `current` is untouched, the running daemon was never stopped, and the reason (the end of the candidate's output) is in the history, on the rescue page and in the Brief.
5. Passed → switch `current`, restart. The new daemon must pass the same check within **60 s** and still pass it, without a crash, **10 s** later. Once confirmed, built releases other than `current`, `previous` and the newest 5 in the history are removed (`KEEP_RELEASES`); a rejection or rollback removes nothing.
6. Not confirmed → **automatic rollback**: `current` and `previous` go back to exactly what they were (the failed release must not become "previous"), the daemon is restarted, and the history says `auto-rollback` with the reason.

## Migrations are additive

Going back does not restore the database: the older daemon runs on the newer schema. That only works if **no table or column a released version reads ever disappears or changes its name**. New columns (with a default) and new tables are fine; a column that is no longer used stays. `packages/core/src/schema.test.ts` holds this: the schema of a fresh database must contain everything in `schema-baseline.json` (append-only — add a line with the column, never remove one), everything new must be added to the baseline, and `db.ts` may not contain `DROP TABLE` / `DROP COLUMN` / `RENAME`.

The snapshot taken before each promotion is for the case where going back is not enough (a new version wrote data the old one chokes on). Restoring replaces `switchboard.db` and loses what was recorded since; what is replaced is kept first as a `pre-restore` snapshot.

## The rescue page

One self-contained HTML document, usable at 390 px: state (does the daemon answer, and why not), current and previous release, the history, the last 200 log lines; **再起動**, **前の版に戻す**, **この版に戻す** (any built release), **DB をスナップショットから戻す**. Each is a confirmed POST that answers 202 and runs in the background, one at a time; the page polls every 2 s while its tab is visible (a hidden tab stops; coming back asks once at once).
Before any of them is pressed, the page lists the tasks that 再起動 and the release switches stop — the daemon's `running` and `waiting` ones, read from the `busyTasks` of its `GET /api/health` with the same token as the health check (not the whole task list, which the 2 s poll would otherwise build again and again) — under the buttons and again in their confirm text (#435).

On the cloud host **再起動** restarts sb-rescue itself (`SWITCHBOARD_RESCUE_RESTART_BY_EXIT=1` in `switchboard.service`, #435): it stops the daemon and exits, and systemd starts it again after its `ExecStartPre` — `sb-host-update` (the host scripts from `main`) and `sb-env` (Parameter Store) — so a changed `/switchboard/*` value or host script reaches the daemon with that one button. The page is gone for 10–30 s — longer if `sb-env` fails (no `/switchboard/edge-header`, Parameter Store refusing): it has no `-` in the unit, so sb-rescue stays down and systemd tries again every 5 s until it succeeds (a failed `sb-host-update` does not hold the start). Without the variable it restarts the daemon alone, with the environment sb-rescue started with.

**/tmp** (#797): when `/tmp` (a small tmpfs on the cloud host) is full, the agents' Bash gets no output (`ENOSPC`) and cannot be asked to clean up, so the page shows the usage and the 30 biggest entries right under it (size, last change), read from `GET /api/tmp` when the page opens, on 再読込 and after a clean — not in the 2 s status, because it walks the tree (synchronously: while it walks, sb-rescue answers nothing else, which is why it is read on request only). **古い作業ディレクトリを消す** sends `POST /api/tmp/clean` with the names it listed, after a confirm that shows them and their total. Only a directory goes: its name is one Switchboard and its kit make (`CLEANABLE.own` in `rescue/src/tmp.ts`: the review / recheck clones `<repo>.review<N>.XXXXXX`, `sb-candidate-*`) — and where `/tmp` is Switchboard's alone, also what any `mktemp` / `mkdtemp` makes (`<name>.XXXXXX` or `<name>-XXXXXX` with a capital or a digit in the suffix, not the template itself), a bunx cache (`bunx-<uid>-<pkg>@<version>`), `node-compile-cache` or a headless Chrome profile (`CLEANABLE.shared`). Only the cloud host says so (`SWITCHBOARD_RESCUE_OWNS_TMP=1` in `switchboard.service`: a machine of its own, whose `/tmp` is a small tmpfs; #2058); elsewhere the user's other apps keep their folders in `/tmp` too, so those names stay (the page says 型に合わない). It also belongs to sb-rescue's user; nothing in it (itself and everything under it) changed for 2 hours; and no running process has it (or something under it) as its working directory, executable or open file (`/proc/<pid>/cwd`, `exe`, `fd/*`; the page says 使用中). A process that does not let itself be read (another user's, or one of the same user's that is not dumpable, as ssh-agent or rootless docker's pasta) shows only its command line, so a directory it names (as an argument, after an option's `=`, or in a `:` / `,` list) counts as in use; one such process using an old directory without naming it is not seen (failing closed on them would stop every clean while docker runs on the cloud host). Without the running processes (no `/proc`, as on macOS, or one that does not list sb-rescue itself) nothing goes: whether a directory is in use is unknown (使用中か確かめられない). Symbolic links are not followed, no path is taken from the request (a name one level under `/tmp`), and each name is judged again right before it goes. Every 30 minutes (`SWEEP_MS`, a constant; the first time 30 minutes after sb-rescue starts, not at start, because `scripts/rescue-e2e.ts` starts the bundle on the host's real `/tmp`) sb-rescue also cleans by itself with the same judgement, so nobody has to open the page; the last one (time, count, total) is only remembered, not stored, and shows in the page's ディスク section from `GET /api/tmp` (`sweeps.tmp`, `null` until the first). The POST passes the same Origin / token / recent passkey check as the other buttons; it is not one of the background operations (it answers 200 with what went and what stayed, and why — including a directory `rm` failed on, which may then be partly gone).

**The rest of the disk** (#2549): the same timer also cleans what else fills the host's disk, in `rescue/src/cache.ts`. On any machine, local CI's leftovers under `~/.cache` — the worktree `<repo>.local-ci-<PR>.XXXXXX`, main's worktree `<repo>.local-ci-<PR>-base.XXXXXX` and a failure's log `<repo>.local-ci-<owner_repo>-<PR>-log.XXXXXX` (`CACHE_WORK`), left when local CI is killed before its `finally`, and one log per PR — go when nothing in them changed for `CACHE_WORK_STALE_MS` and no process uses them (the same `inspect` / `inUse` as `/tmp`); for a worktree, `git worktree prune` then runs in the repository its `.git` file names, so `git worktree list` forgets it (`sweepCacheWork`). Only on a machine of Switchboard's own (`SWITCHBOARD_RESCUE_OWNS_TMP=1`), because elsewhere the user's other apps share them: the uv and bun package caches' entries (`~/.cache/uv/<bucket>/<entry>`, `~/.bun/install/cache/<entry>` and `@<scope>/<entry>`; not a dot-name) untouched for `CACHE_STALE_MS` (`sweepCaches`; per entry, not `uv cache clean` / `bun pm cache rm`, which empty the whole cache), and the images no container uses, running or stopped (`sweepDocker`: `DOCKER_PRUNE`, docker itself keeps a container's image; no docker is 0). `GET /api/tmp` answers `disk` (the root file system's `used` / `total` / `percent`) and `sweeps` (`tmp`, `work`, `cache`, `docker`: the last result of each, `null` until the first; `cache` and `docker` stay `null` elsewhere), and the page's ディスク section shows the root disk's usage (red at 80 %), one line per kind (自動の片付け（/tmp）/（作業の残り）/（キャッシュ）/（docker）: when, how many, how much; the キャッシュ and docker lines only on a machine of Switchboard's own), then `/tmp`'s usage and entries. The values are constants in the code; retention as a whole is in [host-disk.md](host-disk.md).

**救援エージェントを起動** runs `claude -p` (stream-json, so the page shows what it says and does while it runs) in a new worktree (`rescue-work/<time>`, branch `rescue/<time>`) at the running release, with the history, `git diff --stat` between the last two releases and the log on stdin. It is told to fix the cause and open a pull request. A person reviews the PR and promotes. It uses the Claude subscription, so it only ever starts from that button.

What keeps it from promoting by itself, and how far that goes:

- Approvals are not switched off. `--permission-mode acceptEdits` plus an allowlist: the read/edit tools, `git status|diff|log|show|add|commit|push`, `gh pr create`. Nothing else runs without an approval, and in `-p` nobody is there to give one.
- **No command on the list runs code from the repository** — no `bun test`, no `bun install`. Code the agent can write and then run could POST to sb-rescue on loopback (which needs no token there) or write under `~/.switchboard`. The checks run in CI on the pull request instead; the prompt tells the agent to say so in the PR.
- This is Claude Code's permission system, not an OS sandbox: the agent is the same OS user as sb-rescue. The PBI for AWS (#181) is where a separate user or container belongs.
- What it must not have is not in its environment either: sb-rescue's `SWITCHBOARD_STARTER_TOKEN` (作り直す) and `SWITCHBOARD_EDGE_HEADER_VALUE` (the CDN's shared header, used by sb-rescue and the daemon) are removed before `claude -p` starts; the rest of the environment stays (#2077). A file-reading tool can read `/proc/self/environ`, so what is not there cannot leak.

## Tags and unattended updates

PBI #282, from the answer on #267 (request #261: merging unattended is fine as long as there is a way back — fine-grained GitHub release tags, so that a version that does not start, or any other, can be undone).

**Tags.** A commit on `main` is tagged without waiting for CI: on a push to `main`, `.github/workflows/release-tag.yml` runs `bun scripts/release-tag.ts <sha>`, and without Actions the same command runs by hand right after a merge, from any clone: `bun scripts/release-tag.ts $(git rev-parse origin/main)` (after `git fetch origin`). The commit gets a tag `v<MAJOR>.<MINOR>.<PATCH>` and a GitHub Release whose notes list the commits since the previous tag (their `(#n)`) and a compare link. The step is mechanical, from the commit subjects since the previous tag: a `!` before the colon (`feat!:`, `fix(core)!:`) → MAJOR, else any `feat` → MINOR, else PATCH; the first tag is `v0.1.0`. A commit that already has a tag, or is older than the newest tag (a slower run finishing late), gets none; the workflow runs one at a time. There is no rule for 1.0 — retag by hand if you want one. These are the development tags; the public mirror numbers its releases separately (`publicSync.versioning: "independent"`), so `v1.x` here is not the public version.

Before tagging, the script fetches origin's tags and `main` and refuses (exit 1, nothing tagged) a commit that is not on `origin/main`. A tag is not a CI pass: whether a tag passed is read from its Release (Tag CI below). It is safe to run again or at the same time: one run at a time per clone (a lock file in the git directory, taken over after 30 minutes when a run crashed); a push another clone beat drops the local tag, reads origin's tags again and decides again (at most 3 times), so the same version is never made twice. Two clones that pick different versions at once (an older fix → `v1.0.1`, its descendant with a feature → `v1.1.0`) both get their push in; so after its push each reads origin's tags again, and one whose commit is already inside another tag takes its own tag back (`git push origin :refs/tags/<tag>`, its own just-pushed tag only) before making a Release — an older commit is never tagged after a newer one. A run cut off between its push and that check leaves its tag, and the next run makes its Release: the versions are still the ones the two runs would have made one after the other (a descendant whose bump is bigger than its ancestor's gets the same version from either tag), so only the Releases' commit lists overlap. A tag pushed whose Release failed gets its Release on the next run. Recovering by hand: a local `v*` tag that origin does not have (a run killed between the tag and the push) is removed with `git tag -d <tag>` before the next run; a Release that is wrong is deleted with `gh release delete <tag>` and made again by the next run; a wrong tag on origin is a person's (`git push origin :refs/tags/<tag>`), never the script's.

**Tag CI.** `bun scripts/tag-ci.ts [--repo <owner/name>]` runs the same steps as `scripts/local-ci.ts`, in the same environment (`docs/design/local-ci.md`), on the newest `vX.Y.Z` tag whose Release has no result yet, and adds the result to the end of that Release's body: a `## CI` section whose line `[tag-ci] pass|fail <sha>` is the result (the last such line of the tag's commit counts; a fail lists the failed step and its `(fail)` / `over:` / `raised:` lines, at most 20, without host paths). A fail walks back to the tag before it, until a pass or a tag that already has a result; the tags walked past are not run, and tags older than that are never run. A tag without a Release is not run and the walk stops there. A perf-ratchet check whose only finding is `raised:` (an older tag can have a ceiling above main's, lowered after it) counts as a pass and its line says `(raised only)`: `raised` is a rule for a PR before its merge, not a result of a merged tag. When the newest tag already has a result, nothing runs. The output is one line of JSON (the tags looked at, newest first); exit 0 = the newest tag passed, 1 = it failed, 2 = nothing was judged. Read a result with `gh release view <tag> --json body -q .body | grep "^\[tag-ci\]"`, or on the Release's page. A scheduled run in the app runs it for Switchboard and for the other repositories tagged by `release-tag.ts` (the schedule lives in the app). When the newest tag failed, Switchboard's own run files a request Issue (`type:request`, `誰の言葉: 定期の検査`) naming the tag, the step, its lines, the last tag that passed (read from the older Releases when the walk stopped at a recorded fail) and the commits between; the same failure (same step and lines, so the same title) adds a comment to the open request instead, and a later pass comments `<tag> で通った` on the open tag-CI requests without closing them (the PBI that fixes it closes them). Every run follows up the newest tag, run now or read from before (a fail is read back from its Release), and says only what the open request does not say yet, so a run whose filing or comment failed is made up by the next one (not when the Release left the failed lines out for holding a value usable for auth: then the next run files nothing). The same failure is the same step and the same lines a Release keeps (the first 20). With `--repo` no request is filed: on every run whose newest tag failed, its text goes to stderr (stdout stays the one line of JSON) and the scheduled Task reports it as its stop.

**Unattended updates** (only under sb-rescue; `bun run dev` has no promotion). Before the backlog sweep (`backlog-next`) picks an item, it compares the newest `v*` tag with `current`:

- newer than `current` (not already contained in it — a release promoted by hand past the tag is left alone), and no task is running or waiting → it asks sb-rescue to promote that commit (the same `/api/promote` as the 「この版を昇格」 button (設定画面, Brief): build, check on a spare port, switch, automatic rollback) and starts nothing that round, because a promotion restarts the daemon;
- newer, but a task is running or waiting → it waits (「N 件の Task が動いているので <tag> の昇格を待つ」). It does not wait for the next firing: when a task's turn ends (or the task ends) and none is running or waiting any more, the daemon runs the same check once and asks for the promotion (the schedule log says 「バックログを進める: Task が空いたので <tag> の昇格を依頼」; #626). Why it waits is kept in memory only (a restart forgets it and the next firing finds it again), cleared before the request so a second task ending does not ask twice, and never set up for a tag that failed. Running tasks are never stopped for a promotion, and the next item still starts at the next firing;
- the newest tag was rejected or went back by itself (sb-rescue's history; a rollback by hand is not a failure of the tag) → it is never asked for again, the sweep starts nothing new while it is the newest tag (the log says 「昇格に失敗した版のまま: <tag>」), and the PBI behind that commit gets one `## 判断待ち` with sb-rescue's reason and the rescue page's URL. A later tag (the fix) is promoted as usual.

The promotion does not look at the tag's CI result (Tag CI above): tags are made without waiting for CI, so the newest tag may have no result yet; the candidate's check on a spare port and the automatic rollback guard it, as before.

Why the newest tag is held is on `GET /api/daemon/release` as `hold: { tag, failed, reason, busyTasks } | null` (what the last check found; `busyTasks` counted when asked), and the backlog screen shows it as one line above 「承認待ち N 件 →」: 「<tag> の昇格待ち: 動いている Task N 件が終わると入る」, or 「昇格に失敗した版のまま: <tag>」 with a link 「救援画面 →」 (a new tab). No line when nothing is held or outside sb-rescue. The screen reads it when it opens and on 再読込; there is no button there (the place to act is 設定 → 動いている版).

**Going back.** On the rescue page the releases, current and previous show the tag before the sha (`v0.4.1 1a2b3c4 fix(core): …`): **前の版に戻す**, or pick a tagged release in **この版に戻す**. A tag that was never built here is promoted with `POST /api/daemon/promote { "commit": "v0.4.1" }` (the 「この版を昇格」 button in the 設定画面 and the Brief promotes the checkout's `HEAD` only). Tags are read from the local checkout, so a tag shows up after a `git fetch --tags` — backlog-next runs one each firing; without it, fetch by hand. A rejected tag is not asked for again automatically, also when the cause was passing (for example a network error while building); promote it again by hand once the cause is gone. Merges that were not supposed to go in unattended are kept out by `scripts/merge-gate.ts`; `rescue/**` is always large there, so sb-rescue itself is still changed only through a PR a person merges.

## Other repositories

PBI #564, from request #560 (going back should be easy with version tags; Switchboard seems to have this already, and the other repositories need the same). The other registered repositories are developed unattended too, so a merge there that breaks something has to be findable and undoable in the same way.

**Tags.** The Switchboard stage Task that merged a PR in another repository tags it right after the merge, from that repository's clone: `git fetch origin`, then `bun <switchboard>/scripts/release-tag.ts $(git rev-parse origin/main) --repo <owner/name>` (the instruction is in `otherRepoRules`, `packages/core/src/backlog.ts`). The rule is the one above, continuing from that repository's newest `vX.Y.Z` (hand-made tags are not redone). With `--repo` the script first checks that the clone's `origin` is that repository, fetches its tags, and creates the Release with `-R`; its compare link points at that repository. A tag whose push is rejected (two Tasks racing for the same version) is deleted again, so a clone kept between runs never builds on a tag GitHub does not have. No workflow is copied into the other repositories — they differ in language and CI, and one path is one place to fix — so a PR a person merges by hand gets no tag of its own and goes into the next tag's Release.

**Going back** is a pull request, not a promotion: those repositories are not applications Switchboard runs, so nothing is swapped or restarted here, and deploying stays with each repository's own procedure. `bun <switchboard>/scripts/rollback-pr.ts <tag> --repo <owner/name>`, from that repository's clone, checks that the tag exists and is an ancestor of `origin/main`, then pushes one commit whose tree is the tag's tree on top of main (`git commit-tree <tag>^{tree} -p origin/main`; no chain of reverts to conflict, the work tree is not touched) to `rollback/<tag>` (the script's own branch, replaced on a rerun), and opens the PR "revert: <tag> に戻す" listing the commits it takes back. It is reviewed and merged like any other PR, through `scripts/merge-gate.ts --repo`; the script never merges. There is no button for it (a command first; the rescue page stays Switchboard's own).
