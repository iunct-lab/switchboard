# flow-metrics（開発の進み方を、段ごとの時間で測る）

閉じた PBI ごとに、要望から閉じるまでを 7 つの段に割り、どの段で時間を食ったか・そのうち利用者の返事待ちがどれだけか・レビューを何往復したか・Switchboard の Task がどれだけ動いていくら使ったかを、1 コマンドで出す（PBI #650）。開発の進み方のどこで時間を食っているかを勘ではなく数字で選び、手を打った効果を前後で比べるため。画面での表示は #651、改善のループは #652。

## 考え方（参考にしたもの）

- **claude.ai を速くした取り組み**（https://claude.dev/blog/how-we-made-claude-ai-faster。[perf.md](perf.md) と同じ記事）: ユーザージャーニーを「操作で始まり結果で終わる」に揃えて段ごとに測り、一番時間を食う所を選んで直し、効果を数字で確かめるループを回した。開発の進み方に当てはめると、ジャーニーは「要望 → PBI → Task 分解 → 着手 → PR → レビュー → マージ → PBI を閉じる」になる
- **DORA**（https://dora.dev/guides/dora-metrics/）: 変更のリードタイム・デプロイ頻度・変更失敗率・復旧時間・手戻り率の 5 つ。比較や目標ではなく、改善の向きを見るために使う（目標にすると数字が歪む）
- **サイクルタイムを段に割る**: 「コーディング / レビュー待ち / レビュー / デプロイ」のように割ると、詰まる段が見える。ここでは段を Issue・PR・コメントの時刻で切る
- 変更失敗率・復旧時間は測らない。ロールバックは 2026-09-29 までのマージ済み PR で 1 件だけで、数として意味を持たない。必要になったら足す

## 段の定義

どの段も「印の時刻から印の時刻まで」。必要な印が 1 つでも無ければ **不明**（`null`）で、推測で埋めない。切り出しは純粋関数 [`flowOfPbi`](../../packages/core/src/flow.ts)（テストは作り物の PBI: `packages/core/src/flow.test.ts`）。

| 段 | から | まで |
|---|---|---|
| `request` | 元要望の Issue の起票（PBI の `## 元要望` の最初の `#N`。「なし」なら不明） | PBI の起票 |
| `split` | PBI の起票 | 最後の Task（sub-issue）の起票 |
| `wait` | 最後の Task の起票 | 最初の着手（Task の着手コメント）。着手の印が無ければ最初の PR の作成 |
| `build` | 最初の着手 | 最初の PR の作成 |
| `review-wait` | PR の作成 | その PR の最初の `[codex\|claude\|dak] review` コメント。PR ごとに出して中央値 |
| `review` | その PR の最初のレビュー | その PR のマージ。PR ごとに出して中央値 |
| `close` | 最後の PR のマージ | PBI を閉じた時刻 |

- **印**: Issue・PR の `createdAt` / `closedAt` / `mergedAt`、Task の着手コメント（`<!-- parallel-guard:task-claim -->` か、行頭が「着手」の行）、PR の `[codex|claude|dak] review` コメント（`scripts/merge-gate.ts` と同じ形）、`## 判断待ち` / `## 回答` コメント（`issue-workflow` の「判断待ちの出し方」）。どれもスキルが必ず残す
- マージされていない PR（閉じただけ）は数えない。1 つの PR が複数の Task を閉じるときは 1 回だけ数える
- **返事待ち**（`userWaitMs`）: PBI と各 Task で、`## 判断待ち` から次の `## 回答` までを Issue ごとに対にして足す。回答が無い判断待ちは 0（まだ開いているか、記録が無い）。運用の確認（マージの可否など）は Task の会話で聞くので Issue に印が無く、ここには入らない
- **レビューの回数**（`reviewRounds`）: PR ごとの `[codex|claude|dak] review` コメントの数。修正のあとの見直しも 1 回と数える

## Project の Status の履歴を使わない理由

段の区切りに Project の Status の変更時刻は使わない。API で Status を変えた Issue には `ProjectV2ItemStatusChangedEvent` がタイムラインに 1 件も残らない（2026-09-29 に #535 の GraphQL で確認）。このリポジトリの Status は作業者が API で変えるので、履歴は当てにできない。Status を自分で記録する仕組みも足さない（スキルが残す印の時刻で段が割れる）。

## 使い方

```bash
bun scripts/flow-report.ts [--days 30] [--repo <owner/name>] [--json <file>]   # 形
W=$(mktemp -d /tmp/switchboard.flow.XXXXXX); bun scripts/flow-report.ts --days 30 --json "$W/flow.json"   # そのまま回せる例
```

- 期間内に閉じた PBI（`type:pbi`）を GitHub から読む。`--repo` の既定は cwd の `gh repo view`
- 表は 2 つ。段ごとの「中央値 / p90 / 件数」（不明は件数に入らない）と、期間内に閉じた PBI の数・Story Points の合計・中央値が一番大きい段。PBI ごとの「各段 / 返事待ち / レビュー回数 / Task / 費用」。`--json` は `stages`（段ごとの p50 / p90 / count）、`pbis`、`cutPbis` ほか
- **Switchboard の Task**: DB（`SWITCHBOARD_HOME` の `switchboard.db`、読み取り専用）から、そのリポジトリを `origin` に持つ workspace の Task のうち、工程 Task（`stage_issue` が PBI か Task の番号）または題が `#<PBI または Task の番号> ` で始まるものを数える。件数・実行時間（作成から最後のイベントまで。`routingLog` と同じ）・費用（台帳の合計）。Issue の番号はリポジトリをまたいで重なるので、workspace で絞る。DB が無い、または workspace が見つからないときは Task の列を出さない
- 自分のリポジトリの表は、その clone で `bun scripts/flow-report.ts --days 30` を回すと先頭に出る
- 読み方は下の「数の読み方」

### GraphQL の消費と止まる条件

GitHub の GraphQL は 1 時間 5,000 ポイントをホストの全 Task が共有する（[github-api-budget.md](github-api-budget.md)）。

- 実行の最初に残りを読み、**500 未満なら何も読まずに理由を出して止まる**（exit 1）
- 1 ページ（25 件）は Task 10 件・PR 1 件までで読む。費用は「接続の数 × 親の数」で決まるので、足りない PBI だけを 1 件ずつ広く（Task 30 件・PR 3 件）読み直す。コメントの一覧は大きさが費用に効かないので 100 件まで読む。1 回の実行が **100 ポイントを超えそうなら呼ぶ前に止まる**
- 実測では 1 PBI あたり約 0.35 ポイント。最初の形（Task 15 件・PR 2 件）はその約 2 倍かかった
- 限界: コメントが 100 件を超える Issue・PR、広く読み直しても 30 件を超える Task や 3 件を超える PR を持つ PBI は、一覧が切れて数が少なく出る。切れた PBI は表で `*` を付け、`cutPbis` に番号を出す
- GitHub が HTTP 504 を返すことがある（読み取りだけなので、数秒おいて再実行してよい）

## Backlog の画面と `/api/flow`（#651）

Backlog の画面の一番下に「流れ（直近 30 日）」の節がある（新しい画面・タブ・グラフは足さない）。コマンドを打てない環境でも、詰まっている段に気づいて手を打つ段を決められるようにするため。

- **何を出すか**: 段ごとの中央値・p90・前の 30 日の中央値・変化（7 行）、期間内に閉じた PBI の数と Story Points、中央値が一番大きい段、段の合計が長い順の PBI 5 件（押すと GitHub の Issue が開く）。20% 以上遅くなった段は赤、20% 以上速くなった段は緑。どちらかの期間で不明の段は「—」で、変化を出さない（0 とも書かない）
- **`GET /api/flow`**: 登録した全ワークスペースのリポジトリの、直近 30 日と前の 30 日に閉じた PBI を `summarize` して返す（読み方は上の `fetchFlow`）。何も保存しない。取り込んだことのない workspace は読む先が無いので、数に入れず `unread` に名前を出す（節に「取り込み前で、数に入っていません」と出る）
- **1 時間のキャッシュ**: 結果はデーモンのメモリに 1 時間持ち、その間は GitHub を読まない。読めなかったリポジトリがある結果（`errors` が空でない）は持たず、次に開いたときに読み直す。`?refresh=1`（画面の「読み直す」）で読み直す
- **読めないとき**: GitHub の API の残りが少ない（500 未満）・上限を超えそう・`gh` の失敗は、そのワークスペースの `errors` に理由が入り、ほかのリポジトリは返る。節には理由の行が出て、Backlog の一覧は流れとは別に読むので今までどおり出る

## 数の読み方

- **目標にしない、他と比べない**。DORA の注意と同じで、数字を目標にするとエージェントの動きが歪む。見るのは自分の前後（手を打つ前と後の中央値と p90）と、どの段が大きいか
- 中央値は典型、p90 は長引いたもの。段の大きさは「どこが詰まったか」の手がかりで、原因は PBI の Issue を読んで決める
- 返事待ちは PBI 全体の合計で、どの段で待ったかは分からない（段の内訳ではない）。段が大きい理由を返事待ちと決めない。Issue ごとに足すので、別々の Issue で重なった時間は二重に数える。その段の中身は PBI の Issue のコメントで確かめる
- 件数が少ない段・不明が多い段の中央値は信用しない（印が残っていない PBI は不明になる）
- 期間内に閉じた PBI だけを数える。今止まっているものは Backlog の画面の「止まっている」で見る（[backlog.md](backlog.md)）
