# A work machine beside the instance

> **Not for use in this version. Closed in the code.** The settings of section 1 alone do not switch this feature on: `loadUplink` (`packages/core/src/config.ts`), the one place the mode is read, gives no mode unless a second, separately named variable is set as well — `SWITCHBOARD_UPLINK_PREVIEW=not-for-use`. That variable is **not for use until the deployment conditions listed in section 8 ("Before deployment") are met**; it exists so the feature's own tests can run it against an S3 kept in memory. Without it, an instance with `SWITCHBOARD_UPLINK=receive` runs alone (no request to the bucket, no timer of the uplink or the leases, no lease, no role; one line in its log says so), and a daemon with `SWITCHBOARD_UPLINK=send` does not start — a work machine must not run as an instance of its own instead (`uplink-server.test.ts`, "the settings of the feature alone switch nothing on in this version").
>
> **Do not deploy before section 8.** Before you enable this, check every item of "Before deployment" (section 8) against your own AWS account and bucket and write the results down; item 2 includes the permission that binds a lease's writer to its machine (section 7).

There is one instance: one daemon that keeps the record (Tasks, costs, evaluations, the backlog) and is the only one that writes to the backlog's service. A second machine may run Tasks for it as a *work machine*. A work machine makes outbound requests only, keeps no record of its own that is not also sent to the instance, makes no write to the forge, and decides nothing by itself that the instance decides. The two meet in one S3 bucket (the *uplink bucket*), so nothing has to be reachable on either machine and the instance may be stopped while the work machine goes on.

The instance treats everything it reads from the bucket as input from a machine it trusts less than itself: anything with the work machine's credentials — the daemon there, a Task there, a person with the same keys — can put an object. Section 5 says what is checked.

Code: `packages/core/src/machine.ts` (the two judgements everything reads: "this Task belongs to another machine" and "this daemon is a work machine"), `s3.ts` (the one interface to the bucket and its in-memory fake), `uplink.ts`, `uplink-in.ts` and `uplink-s3.ts` (the records of Tasks), `backlog-export.ts`, `backlog-replica.ts` and `backlog-upbox.ts` (the backlog), `lease.ts` (who works on a PBI), and the wiring in `server/backlog-read.ts` (`setupBacklog`) and `server/lease.ts`.

## 1. Settings: off unless configured, and closed in this version

In this version the variables below take effect only together with `SWITCHBOARD_UPLINK_PREVIEW=not-for-use` (see the note at the top: not for use until the conditions of section 8 are met). A daemon that sets none of the variables below runs alone, exactly as before: there is no mode, no bucket object, no timer of the uplink or of the leases, and S3 is never asked (`uplink-server.test.ts`, "alone, none of it runs"). A candidate daemon (`SWITCHBOARD_CANDIDATE=1`, a copy of a database) shares nothing either, whatever is set. On the EC2 instance the three values are not set by hand: creating the SSM parameter `/switchboard/uplink-machines` (the value of `SWITCHBOARD_UPLINK_MACHINES`) and restarting the service (the rescue page's `再起動`, or a reboot; the daemon's own restart keeps the environment it has) makes `aws/host/sb-env.sh` write `SWITCHBOARD_UPLINK=receive`, `SWITCHBOARD_UPLINK_PREVIEW=not-for-use` and that registry into `/etc/switchboard.env`; without the parameter, or with a value holding a character outside letters, digits and `._/=+,-` (spaces and tabs around `,` and `+`, after `=` and at the ends are dropped first, as the daemon trims those), the instance runs alone; a value of allowed characters that the daemon cannot read stops its start with the reason. Only whoever can write Parameter Store can switch it this way: the instance role reads the parameter and cannot write one (what the instance role may do in the uplink bucket does not depend on the parameter). The daemon removes these variables from its own environment at start, so a runner, terminal or a daemon a Task starts does not inherit them; only its own replacement, when it restarts itself without a supervisor, gets them back.

A value that is wrong stops the start with the reason (`send` without a machine name or a bucket, a mode that is neither, a registry that cannot be read). The bucket is asked through the `aws` CLI with the machine's own credentials and region. A failed request is reported by its kind only (`AccessDenied`, `ExpiredToken`, …): the CLI's own text names the role and the bucket, and what is thrown ends in logs and API answers.

What the credentials need, and nothing more. `aws/template.yaml` holds them (`Uplink`, `UplinkPolicy`, the work machines' managed policy `UplinkWorkMachinePolicy`, and the matching ranges in `InstanceRole` and `Boundary`), written from this list and checked in `aws/template.test.ts` as text only, not against a real bucket (section 8 item 2 is still open). The bucket policy refuses a put without `If-None-Match: *` under `uplink/`, `backlog/` and `backlog-refused/`, a put under `lease/` with neither `If-None-Match` nor `If-Match`, and any delete by the instance or the work machine. The work machines are one managed policy for all of them, with no machine name and no principal in the template: its prefixes use the policy variable `${aws:PrincipalTag/switchboard-machine}`, so each principal that carries that tag (an IAM user or role made for one PC, with the policy attached) writes under its own name only, and adding a machine is done in IAM, with no deploy (each statement requires the tag to exist and to hold no `/`; no access to the data bucket; the `Boundary` and the deploy role name no machine and cannot tag a user). A principal tagged with the instance's own name still cannot write the instance's lease proofs: the bucket policy denies that prefix to any principal that carries the tag, whatever its value:

- work machine `<m>`: `s3:PutObject` on `uplink/<m>/*` and `backlog/<m>/*` (`<m>` is the value of its own tag `switchboard-machine`) only with `If-None-Match: *` (a key is written once and never over) and `s3:GetObject` on `backlog/<m>/*` (it reads back a key it finds taken, to tell its own earlier try from another's); `s3:GetObject` and `s3:ListBucket` on `backlog-refused/<m>/*` (what the instance refused of its edits; it cannot write there) and on `backlog-export/<m>/*` (its backlog copy, section 6; it cannot write there. The list carries a prefix condition, and with it a GET of a missing key answers NoSuchKey; the work machine still lists its own key before it reads it, to read the size first and to tell a key that is not there from a read that is refused); `s3:GetObject` and `s3:PutObject` on `lease/*` only with `If-None-Match` or `If-Match`; `s3:ListBucket` on the `lease/` and `lease-proof/` prefixes; `s3:GetObject` on `lease-proof/*` (to check who wrote a lease; the list shows a proof is there before it is read) and `s3:PutObject` on `lease-proof/<m>/*` only (its own proofs, section 7). No delete anywhere, and no other machine's prefix (the tag's variable in every prefix). It has no access to the data bucket, and the read of the backlog is only its own `backlog-export/<m>/*`.
- instance: `s3:GetObject` and `s3:ListBucket` on the prefixes `uplink/`, `backlog/`, `lease/` and `lease-proof/` of the uplink bucket; `s3:PutObject` on `lease/*` with a condition, `s3:PutObject` on `lease-proof/<instance>/*` (the template's `InstanceMachineName`, default `instance`, the same name as the instance's `SWITCHBOARD_MACHINE`; the bucket policy refuses that prefix to every principal that carries the tag `switchboard-machine`) and `s3:GetObject` on `lease-proof/*`, on `backlog-refused/*` only with `If-None-Match: *`, and `s3:ListBucket` on the `backlog-export/` prefix (to find an export to withdraw) and `s3:PutObject` on `backlog-export/*` with no condition (an export is written over the one before; the bucket policy's write-once rule does not name this prefix, and no work machine may put there). No delete.
- the work machine's login to the forge (`gh`, git): **read only**. Section 4 says why this is the only thing that closes a Task's own `git push`.

Nothing in this code deletes a key: deltas and backlog edits end by the bucket's lifecycle, a lease and a backlog export are overwritten (the old versions of both go after a week).

## 2. The records of Tasks (work machine → instance)

On its interval the work machine packs what changed since its last send into deltas (`buildDelta`) and puts each under `uplink/<machine>/<delta id>.tar.zst`. A key that is already there is left as it is. The mark of what was sent moves only after every delta of a send is in the bucket, and the files built are removed either way. A delta's id carries a time that only grows on that machine, also when its clock goes back, so the instance — which takes keys in their order — never passes one over.

A delta holds the rows of the Tasks (the Task, its events, costs, evaluations, check runs, decided staged changes, artifacts, attachments, and the usage limits per account) and the files of two kinds: a Task's attachments and the files of a Task's artifacts. **A runner's session file is not sent and not taken in.** It is that runner's own state on the machine it ran on; the conversation is in the events. Nothing a delta carries is ever written under `~/.claude`, `~/.codex`, a repository or a runner's memory on the instance, so taking a delta in cannot change what a runner there reads as its instructions.

The instance takes the bucket in once at start — everything put while it was stopped goes in then — and on its interval, for the registered machines only. Each machine's deltas go in in the order they were made; the last key taken per machine is kept, so a round with nothing new is one list request per machine. A delta from a database newer than the instance's is not taken in: it is kept with both levels, shown as a band at the top of the screen and written to the log, and it holds that machine's later deltas (not another machine's) until the instance is updated.

## 3. A Task of another machine is read only on the instance

A Task taken in carries the name of the machine it ran on (`tasks.machine`). It shows in the Task list and on the Task's screen. The instance never runs it, resumes it, answers for it, stops it or writes to the forge for it.

There is one predicate (`otherMachineOf`, `machine.ts`) and one place that enforces it: `TaskManager.requireLocal` / `requireOwn`, called first by every method that acts on a Task — `send` (a person's reply, the planned resume, the daemon's own turn), `startDeferred`, `abort`, `respondPermission`, `recordStop`, `setResumeAt`, `setPermissionMode`, `setModel`, `setEffort`, `forkTask`. A caller that made no check of its own is still refused, with `この Task は <machine> で動きました。返信は <machine> の Switchboard から行います。`. So the routes (409), the WebSocket's `task.send` / `permission.respond` / `task.abort` (an error message), an answer to a question (`/api/asks/answer`), the automatic resume of a Task that waited on other work (`depends-resume.ts`) and the wait watch are all refused by the same line. In addition:

- the lists the daemon acts on by itself (`Db.listTasksUpdatedSince`, `listTasksOnStops`, `listTasksWithWaits`) hold this machine's own Tasks only, so such a Task is not among the questions put to the person and is not looked at by the automatic resume or the wait watch;
- the history import (`HistoryScanner`) passes such a Task over with the same predicate, so a session file copied here is not read into it;
- `TaskManager.record` writes nothing to such a Task: its events are numbered on its own machine, and one written here would take the place of one of its own;
- a merge grant is never recorded for it (`noteMergeGrant`);
- its row comes in with no state the instance acts on: a status of a turn in flight becomes idle, and the resume, queue and judging marks, a prompt held for a later start and the schedule it came from are emptied.

What is not refused: marking such a Task reviewed or archived in the instance's list, and renaming it. Those change how the instance shows it and nothing else.

## 4. A work machine writes nothing to the forge and decides nothing by itself

`isWorkMachine` (`SWITCHBOARD_UPLINK=send`, not a candidate) is the one judgement.

**The daemon.** Every `gh` call the daemon makes goes through the one runner the server is started with; on a work machine that runner is `workMachineGh`, which lets through only what is known to read (`ops-kit/src/gh-reads.ts`: anything not known to read counts as a write) and answers a write as a failed call without running it. The backlog itself is never asked: reading is the copy of section 6, writing is the bucket.

**What it does not start by itself** (`decidesNothing`): the schedules (none fires), the backlog queue, the start of a PBI after an import, the automatic resume of a Task that waited on other work, the automatic answers of saved policies, the promotion check. The backlog sweep (`バックログを進める`) fired by hand starts nothing either and says why in the schedules log. `TaskManager.send` refuses the daemon's own turn (`daemon: true`) on a work machine, whatever asked for it. What stays: a PBI's stage started by its own button, a reply, and the resume of the work machine's own Task after a usage limit.

**Its Tasks.** A Task's session gets `OPS_KIT_FORGE_READ_ONLY=1`, and the check in front of `gh` (`ops-kit/bin/gh`) then stops every command that is not known to read, before anything of it is read or sent: `gh pr create`, `gh pr comment`, `gh pr merge`, `gh api` with a write, a result of local CI posted to a PR. Issues, comments, labels and Project fields are written with `ops-kit backlog`, which goes through the bucket.

**What this does not guarantee.** A Task is a process of the same OS user as the daemon. It can unset the variable, call the real `gh` by its path, or run `git push`, with whatever that user is logged in as. The daemon cannot stop that; only the login can. A work machine's forge login must therefore be read only (section 8). With a login that can write, the statement "a work machine writes nothing to the forge" holds for the daemon and for a Task that does not work around the check, and for nothing more.

**Consequence.** Work done on a work machine reaches the forge only as backlog edits. Opening a PR for it is done by a Task on the instance. Whether a narrower write path for PRs should exist is an open question for the owner; none exists.

## 5. What the instance takes in

### Deltas (`uplink-s3.ts` `receiveUplink`, `uplink.ts` `applyDelta`, `uplink-in.ts`)

Before a byte is fetched: the machine must be registered (a prefix nobody registered is never listed); the key must be exactly `uplink/<machine>/<machine>-<time>-<n>.tar.zst`; the time in it must not be ahead of the instance's clock (a day of slack); the object's size, read from the list, must be within the limit.

While it is unpacked: as a stream, within limits (the object 96 MiB, everything it unpacks to 256 MiB, `delta.json` 96 MiB, one file 64 MiB, 20,000 files, 200 deltas a machine a round), so an object that expands without end is cut at the limit instead of filling memory. The entries are read by this code, not by an archive library: only plain files are accepted (a link or any other entry refuses the delta), and each is written to a numbered file in a stage — never by a name the object gives.

Before anything is written to the database or placed:

- the machine `delta.json` names, and the machine in its id, must be the one whose prefix the object lay under;
- only the tables a delta carries are accepted (not the grants, not the settings), and every value must be a text or a number;
- every Task it names must be new here or already that machine's. A Task of another machine refuses the delta; a Task of the instance's own is passed over with its rows and files. A row told apart by its own id (an artifact, an attachment, a staged change) stays with the Task it has here;
- every file's name must have one of two shapes — `attachments/<task>/<file>` or `artifacts/<task>/<artifact>/<path…>` — with no `..`, no absolute path, no backslash, no control character, no hidden name, at most twelve levels; it must resolve inside that Task's own folder under the Switchboard home, with no link on the way. One file that fails refuses the whole delta. The sender asks the same function, so it never packs what would be refused;
- a Task is put on a workspace only when its repository is one the machine is registered for;
- a usage report dated ahead of the instance's clock, or a limit said to reset later than any window lasts, is dropped (a report otherwise moves the instance to wait for that account, which is the safe direction).

A refused object does not hold what the machine sends after it. One that has a delta's name (refused for its size or for what it holds) is recorded and passed over: the mark moves past it and it is never listed again. One refused for its name — not a delta's, or dated ahead of this clock — is recorded and stepped over, unread, each round: the mark never moves to such a key, because its name is free to sort after every delta still to come. Either is told once: a notice under `判断待ち` per machine (`作業場 <machine> から届いたもの <n> 件を取り込まなかった`, with each key and its reason; closing it closes those objects, a new refusal opens it again), the log, and `/api/health` (`uplinkRefused`). The record keeps the newest 200 objects the mark passed and up to 50 a machine of those refused for their name; more of the latter are stepped over without a record.

A later delta that depends on a refused one is not put on the hole. A delta continues each Task's events right after the last event its machine sent, so the instance refuses, with that reason, a delta whose events for a Task start past what it has of that Task, and (as before) one that has rows of a Task whose own row never arrived. Deltas about other Tasks go in. What the refused deltas held is then missing on the instance until the work machine sends it again: the person takes the work machine's mark back (delete the row `uplink.cursor` of its `settings` table and restart it — every record is put again under new keys, and taking a record in twice changes nothing). There is no button for this yet. Two things still hold a machine's later deltas, because waiting mends them: a delta from a newer database, and a bucket that does not answer.

Where the files go: attachments and artifacts are placed in the two stores the screens read (`<home>/attachments/<task>/`, `<home>/artifacts/<task>/<artifact>/`), each inside the folder of a Task that belongs to that machine. They are not under one directory per machine, because the stores find a file by its Task's id.

### Backlog edits (`backlog-upbox.ts` `importBacklogOperations`, `checkEnvelope`)

An edit made on the work machine is put as `backlog/<machine>/<n>.json`, one key per version of the operation. The instance takes the registered machines' envelopes in key order, and an envelope is a closed set. It is taken only when:

- its key has that shape, it is at most 512 KiB, and the machine it names is the one it lay under;
- it is one of three operations, each with only the values it may carry: a new Issue (title, body, labels, milestone, parent, Project fields), a comment (`{ body }` and nothing else), or a field of an Issue or of its Project item with a value of that field's kind. A local change's branches (`change`), an artifact post, an unknown kind or field, or an extra key refuses it;
- **it is not the person's answer.** A comment may not hold a line that begins with `## 回答`, `## 保留`, `**確定**: 推奨のまま`, `**覆す**: 推奨`, `[merge-answer]`, `[recheck]`, `[local-ci]` or `[tag-ci]`; it may not carry the mark that an answer was given on the screen or a confirmation; a field edit may not take `needs-decision` off; a body may not check off a line that waits for the person's confirmation. The instance sends comments under the owner's login, so such a line would read as theirs;
- no text in it holds a value that signs in, by the instance's own check (it knows its own account's values; the work machine's check does not);
- its repository is one that machine is registered for and a workspace of the instance reads;
- the Issue it edits is stored on the instance; a draft it names was made by an envelope of the same machine.

What is stored is made on the instance from the checked values, not taken from the envelope: the operation, under the id `m:<machine>:<id>` — which records where it came from and which no operation of the instance's own can have, so a "later version" can only replace that machine's own earlier one — and the draft of a new Issue or comment. `screenAnswer` reads only operations made on the instance, so nothing taken in is ever "the person's words" to a stage Task or a merge grant.

An envelope that fails is refused with its reason (`upbox.refused`, the log, the same notice under `判断待ち`, `uplinkRefused` in `/api/health`) and passed over; it does not hold the ones after it (a key under the machine's prefix that is not an envelope's name is said once and stepped over; the mark never moves to it). The refusal goes back to the work machine: the instance writes `backlog-refused/<machine>/<the envelope's count>.json` (`{ key, reason, at }`, written once, before it passes the envelope — a write the bucket did not take is tried again with the envelope next round), and the work machine, after each put, reads the notes it has not read and ends the operation that was put under that count as failed with `Switchboard 本体が受け取りませんでした: <reason>` — if it still waits in the version that was put. It shows on the Issue as any edit that could not be sent, where the person edits it or sends it again. Without this an edit refused by a check only the instance runs (a line that waits for the person's confirmation, a value that signs in by the instance's own account, a repository the machine is not registered for) would wait on the work machine forever. The work machine runs the same check before it puts an envelope: an edit that would be refused — an answer given on the work machine's own screen among them — ends there as failed with `作業場からは送れません: …` and is never put. Answers are given on the instance.

Not covered: an edit taken back on the work machine after it was put in the bucket is still sent by the instance.

## 6. The backlog on a work machine

**Reading.** The work machine never asks the backlog's service. Its backlog is a copy of what the instance stored, laid under its own workspace in the tables it already reads the backlog from; `ops-kit backlog list` / `view` and the screen answer from it, and the sync line says it is a copy, when it was taken, and when the instance last imported.

The copy is taken from small objects the instance writes in the uplink bucket, not from the instance's database. After each intake of the uplink (`receiveUplink`, then the backlog edits taken in) the instance writes, for each machine of its registry and each repository that machine is registered for, `backlog-export/<machine>/<owner>/<repo>.json.zst` (`writeBacklogExports`; the owner and name in lower case; a repository no workspace of the instance reads, or one it has not imported yet, gets no object; so does a path that workspaces of two services or hosts read, in use or not, because the registry names a repository by its path only and which one is meant is not known — an export written before is then withdrawn). The object is zstd over one JSON document with only what a work machine shows: the repository's records as the service has them (never the instance's own unsent drafts and answers, nor the records it made with its own sync off, whose `sb:` ids belong to the database that made them), which repository and Project the instance's workspace reads, the time of its last import, and the rows of the operations **that machine** put (the id the instance keeps them under, their state, the id the service gave, the error). No Task, conversation, setting, ledger entry, other machine's operation or other repository is in it.

The work machine reads only the key under its own name (`readBacklogExport`) and takes the document in with the intake it always had (`importBacklogExport` in `backlog-replica.ts`: the records replace the copy whole, and the operations settle as below). Its credentials allow `s3:GetObject` on `backlog-export/<its name>/*` and nothing of the data bucket, so a leaked work-machine credential reads its own repositories' backlog and nothing else; the template holds no list of repositories, because the key carries the machine's name. The work machine lists the key first and reads it only when it is there. A document that is of a newer shape (`v`), that names another machine or another repository than its key, whose records are not of the shapes the backlog tables keep, or that cannot be read is refused with its reason and the copy before it stays; a missing key says the instance does not register this machine for the repository or has not imported it yet. The sync line's "taken" time moves only when the copy was laid in. The read limit of one compressed object is set with `SWITCHBOARD_BACKLOG_EXPORT_MAX_BYTES`.

The instance cannot delete, so an export that must no longer be read is written over with a tombstone, `{ kind, v, machine, repository, removed: true, at }`, once: each round, before it puts the live exports, it lists `backlog-export/` and, for every key whose machine or repository is no longer in the registry, or whose workspace is gone or disabled, or whose path two services or hosts read, writes the tombstone (the keys already done are remembered with the etag the tombstone got, and a key whose listed object has another etag — written over since, or a database restored from before — gets the tombstone again; registering the pair again writes a real export over it). The withdrawal is written also in a round whose intake failed. The work machine reads a tombstone addressed to it, of a shape it knows, exactly as a missing key, with the same message, and drops the records it had copied of that repository and the time of the instance's import if its workspace still reads that repository; a tombstone whose `repository` is not the key's is refused as an export for another repository (like a live export of one), and the copy stays. Its own waiting edits stay, and so do the records those edits are on and every record made on the work machine (an id that begins `sb:`), also when a later copy replaces this one. What the machine already copied is on its disk; the tombstone stops further reads of the bucket, so a de-registered machine cannot read the last export for good. The bucket's rule for old versions removes the earlier versions of an overwritten object after a week. The work machine keeps a read export in memory only for the reading interval; one older than that is let go when the next export is read.

The export is as fresh as the instance's last round of the uplink (`SWITCHBOARD_UPLINK_INTERVAL_S`): a change the instance imports between two rounds is in the next object. The round starts sending the edits it took in and does not wait for them, so what came of an edit reaches the work machine in the export of a later round (the instance does not write the exports when it stops, so a change imported after its last round reaches the work machine after its next start), and the work machine reads again after `SWITCHBOARD_BACKLOG_COPY_INTERVAL_S` or when the screen's reload asks.

**The result of an edit.** The next copy brings back what came of each edit the machine put: a sent Issue or comment takes the service's id and number, a sent field ends once the copy has its value, and an edit the instance could not send shows the instance's state and reason.

Load: the instance puts one small object per machine and repository at each round, and a work machine gets its own repositories' objects once per `SWITCHBOARD_BACKLOG_COPY_INTERVAL_S` while its daemon runs. With the compressed size of one object (`aws s3 ls --summarize --recursive s3://<uplink bucket>/backlog-export/`), the hours a day the daemon runs and the interval in minutes:

- monthly transfer out = the sum of the sizes of the objects the machine reads × (hours active per day × 60 / interval in minutes) × 30
- monthly requests = (hours active per day × 60 / interval in minutes) × 30 per repository, each a LIST and a GET, and the instance's PUTs: rounds per day × machines × repositories × 30, plus one LIST of `backlog-export/` per round (rounds per day × 30) and one PUT for each object withdrawn (once per object)

Price both from your own region's S3 price list. For example, 400 KB of objects read hourly for 8 hours a day is 240 reads, about 100 MB of transfer out a month; multiply it, and the request counts above, by your region's prices.

## 7. Who works on a PBI: the lease

Without it, the two machines could start the same PBI at once: the claim that keeps two sessions apart lives in the instance's records, which the work machine cannot write to.

One object per PBI, `lease/<owner>/<repo>/<number>.json`: `{ pbi, machine, token, state: "held" | "released", expiresAt }`. S3 decides who gets it:

- none there: written with `If-None-Match: *`. Of any number of machines writing at once exactly one succeeds.
- given back, run out, or this machine's own: written over with `If-Match: <the etag just read>`. A machine that lost the write reads again and finds the holder.
- held by another machine and not run out: not taken; the answer names the holder and the time.

A CLI too old to know the conditions fails on the unknown argument, and the stage is not started.

**Taking and giving back.** The daemon takes the lease before it starts any stage of a PBI or of a request, except a status check and a direct fix. A PBI another machine holds is not started; the reason (`PBI #N は <machine> が <time> まで持っている`) is the button's 409 and a line of the sweep's log. A lease taken for a start that then did not happen is given back at once. `scripts/parallel-guard.ts claim` asks the daemon after it won the claim comment and takes the comment back when the lease is held elsewhere; `release` gives it back. A PBI that closes gives its lease back at the next renewal round. So does a lease taken for a stage Task — by this daemon or by one before it — once no stage Task of that PBI is at it here any more (`leaseWanted` in `server/lease.ts`: none at work, queued, planned to resume, judged or with a job running, and the newest one not stopped on a wait it recorded or on the person's answer); a stage Task that ends gives it back at once, without waiting for the round. A Task that stopped on a question keeps its PBI's lease while the question is open — the other machine is refused the PBI for that long — and a lease a session took for itself through the route is left to that session.

**Renewing, and losing.** The daemon renews every lease it holds on its interval with one conditional write over its own last one. Every request the lease store makes has a time limit, 20 seconds by default (`SWITCHBOARD_LEASE_CALL_TIMEOUT_S`), so one that never answers is given up and does not hold the round that renews the other leases; a lease the round finds closed or unwanted is given back alongside the renewals, not before them. The uplink's own sends and receives have a longer limit of their own, 600 seconds by default (`SWITCHBOARD_UPLINK_CALL_TIMEOUT_S`), so that a big delta still goes through; a request that never answers ends the round at that limit, the next round runs, and the round still writes its withdrawals before it ends. A lease is lost when

- another machine wrote over it meanwhile: the conditional write is refused, or the write fails, and reading the lease again finds it missing, given back, or carrying another machine or another token (a refused or failed write after which the lease still carries this machine's token is kept: the renewal had landed, or the next round renews it), or
- it could not be renewed — the bucket not reached, the credentials run out, the machine asleep with its lid closed — until a fifth of its life before the end this machine last wrote, or that end has passed. From then on another machine may take it at any moment, so this one stops acting as its holder, and does not write the lease again as if nothing happened.

When a lease is lost, the PBI's stage Task on this machine **stops at its next turn boundary** (`server/lease.ts` `stopForLostLease`): a Task between turns stops at once — what it had planned by itself (a resume, a place in the queue) is dropped — and a Task whose turn runs is told, and stops when that turn ends. In both cases a stop that waits for the person is recorded, saying the lease was lost and that the PBI may be at work on two machines. Nothing else is decided: the lease is not taken back, nothing is retried, the other machine is not told. The person decides what comes next. Until the turn ends, the running turn goes on: the two machines can overlap for that long.

The Task that is stopped is the one at the PBI (`leaseWanted`), also one between turns that waits for a PR, a date or the person — it would go on later. And the lease is checked again in the one place a follow-up turn of a stage Task starts (`leaseGate`, the Task manager's `turnGate`: a reply, a planned resume, a wait that was met, a turn after a daemon restart all pass it), so a lease lost while nobody looked is found there:

- held by this machine: the turn starts, with no request to the bucket;
- not held, and the daemon starts the turn by itself: the bucket is read once (a daemon that just started has not seen its own leases yet); a lease that is still not this machine's refuses the turn and stops the Task with the same stop that waits for the person, recorded once however often it is tried. This is what keeps a daemon that was down while its lease ran out, and another machine took the PBI, from resuming it;
- not held, and the person replies: the reply is the person's decision to go on, so the lease is taken again for it — and the reply is refused with `PBI #N は <machine> が <time> まで持っている。…` while another machine holds it, or when the bucket cannot be asked.

Alone (no uplink configured) none of this runs and nothing is asked.

**Clocks.** Expiry is judged by each machine's clock, so the lease's life (15 minutes) must stay far above any difference between the clocks. A lease whose end lies more than two lives ahead — a holder whose clock runs ahead, or an end written by hand — is read as held for at most one life at a time, and as over once the same version has lain there unrenewed for a whole life as this machine saw it.

The lease is part of the one overlap decision, not a second one: a PBI another machine holds counts as at work there, so its open Tasks' files hold back other PBIs here the same way a running stage Task's do. For that the daemon reads the leases in the bucket every third of a lease's life (one list request, and one read per lease that changed); between two looks what it knows may be up to that old, and a start asks S3 itself.

A backlog that is not synced with its service has no lease. The instance's own judgement of an expired login reads only its own stage Tasks.

**Whose lease it is.** A lease only names its machine, and a work machine can write over the instance's lease with the etag it read. So a machine that takes a PBI first writes a proof, `lease-proof/<machine>/<owner>/<repo>/<number>.json` (`{ token, state: "held" | "released" }`; one per machine and PBI, holding only the current token, the same as the lease's), under a prefix only that machine can write, and then the lease. A machine that takes its own held lease again (also one that ran out) keeps the token and writes the same token's proof again once the lease is written (a failure half way leaves the lease and its proof agreeing); any other take (no lease, a given-back one, another machine's, a lease of its name with no proof) writes a new token's proof over the last one. A machine that reads a lease naming another machine (`take`, and the look that learns what others hold) first checks that the token has the shape this code gives (a UUID; anything else is no holder's and nothing is read for it), then lists that machine's proof key and, when it is there, reads it (a proof that is not listed is missing; a list that is refused or fails is not read as missing): when it is missing, carries another token or says `released`, the lease is not read as held — the PBI may be taken, as one that ran out — and the log says `[lease] PBI #N: <machine> を名乗るリースに証が無い`. A renewal keeps the token, so it does not write the proof. Within one machine the operations that change one PBI's lease (a take, a give-back, one renewal) run one at a time, so a give-back never lands between a take's read and its write. Giving a lease back, and losing one (another machine wrote over it, or it ran out before it could be renewed), mark the proof `released` when it is still the proof of that lease's token (before the lease is written, when giving back; a failure to do so when losing one is only logged), so the token left in the lease cannot be written back as a holding. A proof that cannot be read is not read as missing: `take` and `acquire` throw it to the caller (the PBI is not taken), and the look that learns what others hold keeps the lease as a holder's. A proof is never deleted (written over only). There is no signature and no key: that nothing else writes under `lease-proof/<m>/` is the bucket's permission, section 1.

**What it protects against, and what not.** It keeps two Switchboards that start PBIs through these paths apart, and a lease that names a machine is believed only when that machine wrote it: another machine, or anything with only its own prefix, cannot hold a PBI by writing a lease in the instance's or another machine's name. It does not stop anything that can write the named machine's own proof prefix (the same credentials as that machine) from doing both writes, nor a lease that ran out without being given back: the current token of a lease that was not given back (it ran out before that) can be written back by another machine and is believed, until that machine takes the PBI anew or gives it back. Nor does it stop a machine from writing over the lease of one that did write its proof — the lease key itself is still writable by every machine, and the proof of the holder shows only that the lease was taken under that token, not that it was not overwritten later. A Task started without a PBI is not covered either.

**Cost.** Count the requests, then price them from your own region's S3 price list (PUT and LIST are priced together, GET separately; check the current list before relying on any number):

- PUT a day = leases held at once × (hours active per day × 3600 / renewal interval in seconds)
- LIST a day = hours active per day × 60 / the look interval in minutes, for each machine whose daemon looks at the leases (the look interval is a whole number of renewals, the most that fit in a third of the lease's life — `SWITCHBOARD_LEASE_RENEW_S` × max(1, floor(`SWITCHBOARD_LEASE_TTL_S` / 3 / `SWITCHBOARD_LEASE_RENEW_S`)) seconds: 5 minutes by default), plus the instance's lists of the registered prefixes at their own interval
- GET: one per lease that changed at each look, plus the proofs read; a few thousand a month at most
- monthly cost = (PUT + LIST per month) / 1,000 × the PUT/LIST price + (GET per month) / 1,000 × the GET price

For example, in Tokyo S3 Standard charges $0.0047 per 1,000 PUT or LIST requests and $0.00037 per 1,000 GET requests. One lease renewed every 60 seconds for 8 hours a day is 480 PUT a day; three leases at once, 30 days: 43,200 PUT = $0.20 a month. Reading the leases every 5 minutes adds 2,880 LIST = $0.014 and at most a few thousand GET; the instance's lists every 10 minutes are another few thousand LIST. Together well under $1 a month.

## 8. Before deployment

Each is a condition, not a suggestion. Check each in your own environment and write down the result before you enable the feature.

1. **A work machine reads no database of the instance.** Its backlog copy comes only from the per-machine export of section 6, `backlog-export/<machine>/<owner>/<repo>.json.zst` in the uplink bucket: the records and operations that machine may see, written by the instance; the template's managed policy grants the read to the principal tagged with that machine's name alone and no access to the data bucket. Check against a real bucket (with item 2) that such a principal reads its own `backlog-export/<m>/*`, that its LIST of a missing key there is empty and the daemon then reports the copy as missing (its GET of a missing key answers NoSuchKey, as the list carries the prefix condition), cannot read another machine's prefix or write there, and that a tombstone is read as a missing key.
2. **The IAM policies of section 1**, as the template writes them; check against a real bucket, with a principal that carries the tag and one that does not (the one without the tag, and one whose tag holds a `/`, are denied everything): a work machine's and the instance's credentials can write their own `lease-proof/<m>/*` (every take of a new holding and every give-back writes one; without it those fail), and a work machine cannot write over or delete a key under `uplink/` and `backlog/`, cannot write under another machine's prefix, cannot read `uplink/`; a write to `lease/` without a condition is refused; the instance cannot delete. Check with the real `aws` CLI that a refused conditional write is read as a conflict (`s3.ts` `REFUSED`) and a missing key as none (also a lease or a lease proof that is not there yet, read with the work machine's credentials, which list `lease/` and `lease-proof/` under a prefix condition; the proof is listed first, so a missing one is none and a refused list is a failure); that a work machine reads `backlog-export/<m>/*` of its own name and no other machine's, and cannot write there; that the instance's overwrite of an export is accepted.
3. **The work machine's forge login is read only**: a token that can read the repositories and cannot push, comment, merge or write contents. Check that `git push` and a `gh pr comment` with the variable unset are refused by the forge itself.
4. **The registry** on the instance names each work machine and only the repositories it works on; a machine's name there is the value of the tag `switchboard-machine` on the IAM user or role whose credentials it uses, which is the name those credentials can write under; adding a machine is making that principal, tagging it and attaching the template's managed policy `UplinkWorkMachinePolicy` (its ARN is a stack output). The tag must be one only an IAM administrator can change: an IAM user, or a role that allows no session tags (`sts:TagSession`, or attribute-based access control from an identity provider) and whose name does not start with the stack's name and `-`.
5. **Limits against real data**: a first send of your real work machine's database fits the limits of section 5 after being cut, and the instance stays within its machine's memory while it takes them in. How much one intake holds is bounded by `SWITCHBOARD_UPLINK_MAX_BYTES` (the most one delta holds before it is cut); how many deltas the first send makes grows with the number of Tasks in the work machine's database. Measure it on the instance: just before the first send, with the daemon running, note the `available` column of `free -m` (MiB) and the daemon's RSS (`VmRSS` in `/proc/<daemon pid>/status`, in kB); after the intake, read the daemon's largest RSS from `VmHWM` in the same file (it keeps the peak, so it need not be polled; it counts from the daemon's start, so restart the daemon before the first send). Divide the kB values by 1024 to compare them with MiB. The growth (largest RSS minus the RSS before) must fit within the `available` memory noted before, with room left for the Tasks that run on the instance at the same time.
6. **A lease across two real machines**: taken by one, refused to the other; the work machine put to sleep past the lease's life, the instance takes the PBI, and the work machine's Task stops at its turn's end with the stop on the screen; clocks compared.
7. **The screens**: the machine's tag on a Task, the reply box off with its reason, the band for a delta that could not be taken in. A refused delta or envelope is told by the notice under `判断待ち` (and in the log and the health answer); on the work machine a refused edit shows on its Issue.
