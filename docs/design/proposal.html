0. 結論

作るものは「エージェント実行の制御面（コントロールプレーン）」であって、エディタでもチャット UI でもない。 Claude Code・Codex・DAK をそれぞれの公式ヘッドレス口（stream-json / app-server / ADK REST）から呼び、共通イベント形式に正規化するローカルデーモンを中核に置く。UI はその上の薄いクライアントに留める。

ランナーはすべて差し替え可能なプラグインで、どれが無くても本体は動く。 DAK も同格の一つとして扱い、名前にも依存関係にも DAK を持ち込まない。DAK が手元のファイルを触る経路は、デーモンが公開する Workspace MCP（スコープ付きファイル操作とコマンド実行）に一本化し、承認は他ランナーと同じ UI を通す。

技術はコアを TypeScript（Bun）に置き、UI はデーモンが配信するブラウザ UI（PWA）にする。デスクトップシェル（Tauri）は採らない。 コアは MCP・Codex・Claude の SDK が全て TS であること、LLM に書かせる反復速度で決める。当初は Phase 2 で Tauri 2 に包む計画だったが、2026-10-11 に不採用と決めた（判断・理由・到達点は §5 デスクトップシェル）。

まずローカル git リポジトリで作り、ライセンス整理が済んだ時点で DAK と同じ Apache-2.0 で GitHub に公開する。（現行: GitHub の private リポジトリで開発している。公開は別のリポジトリに新しい履歴で出す方式に決め、まだ公開していない — §7-2） Codex CLI は Apache-2.0、Claude Code CLI と Agent SDK は独自条項。プロセス境界を越えて呼ぶだけの構成にし、いずれの成果物も同梱しない。

1. 観察した事実（設計の前提）

手元の環境を確認した結果、3 つのランナーはいずれも「UI を外から差し替える」ための公式な口を既に持っている。ここが今回の設計の土台になる。

ランナーヘッドレス接続口セッション・設定の所在備考

2. 6 つの課題と、それぞれに答える設計原則

挙げられた 6 点は「ツールの不満」に見えるが、束ねると 主語がファイルとディレクトリになっている ことに起因している。エージェント時代の作業単位は「タスク」で、その属性として対象ディレクトリ・ランナー・予算・成果物（差分／文書）がある。主語をタスクに置き換えると、6 点は次のように整理できる。

課題 1

Claude と Codex の使い分け判断、ディレクトリ移動によるコンテキストの浪費

判断と移動を人がやっているのが浪費の原因。タスクを起こす瞬間に「対象ディレクトリ集合」と「推奨ランナー」を提示し、確認一回で走らせる。

Task Brief（目的・スコープ・ランナー・予算のカード）／ルーティング規則（v1 はルール、v2 で安価モデルによる提案）／Context Footprint メーター（スコープ内ファイル数・推定トークン）
課題 2

.claude / AGENTS.md / CLAUDE.md が分散し、思いつきから開発へ移りづらい

正本を一箇所（アプリ管理の Knowledge フォルダ）に置き、各ツールが読む形式へ 生成 する。文書はまずリポジトリの外で生まれ、必要になった時点でリポジトリに「配置」する。

Knowledge Store（Markdown + frontmatter、git 管理）／Materializer（CLAUDE.md、AGENTS.md、.claude/commands、.codex を管理ブロック付きで書き出す。現行: 書き出し先はユーザーレベルのファイルだけで、リポジトリには書かない — #197、packages/core/src/materializer.ts）／Inbox → Task 昇格
課題 3

エディタ経由が本当にベストか。ローカルフォルダ・テキストの管理は続けるか

手で読む・書くにはエディタが最適。エージェントに任せる仕事の主要オブジェクトは 差分 と 会話ログ で、エディタはそれを見る場所として過剰。保存形式はテキストのままにし、UI だけ差し替える。

差分ビューア中心／「エディタで開く」脱出口（vscode:// / cursor:// ディープリンク）／ストレージは Markdown + SQLite 索引（grep も Obsidian も効く）
課題 4

API 利用のコストが見えない

3 ランナーとも usage を返す。それを一つの台帳に落とし、タスク・リポジトリ・日ごとに見せる。定額プランは「API 換算額」と「レート制限枠の消費」として扱う。

Ledger（usage イベント → SQLite）／タスク予算（超過で一時停止し確認）／価格表は JSON データとして持ち、LLM が更新できる
課題 5

この環境自身を、その UI 上の LLM 指示で更新したい

アプリ自身のリポジトリを最初から「メタワークスペース」として登録する。UI は HMR、デーモンは自己再起動にし、ネイティブのシェルは持たない（§5）。

「このアプリを改善」ボタン（構成図・テスト手順を Brief に自動同梱）／Self-dev モード（差分 → テスト → 適用と再起動を UI 内で完結）／カスタマイズの大半をデータ（Markdown / YAML / JSON）にして再ビルド不要にする
課題 6

まずは Claude Code / Codex の呼び出しから。OSS 公開を前提に範囲を決めたい

ランナーを アダプタ として抽象化し、共通イベント形式を先に固める。DAK はその 3 番目として繋ぎ、どのランナーが無くても本体は動く。OSS には「ベンダ CLI を同梱しない・鍵を持たない・無審査の全許可を既定にしない」の 3 線を引き、公開はライセンス整理の後にする。Auto はランナーのリスク審査に委任し、許可された操作は人間への確認なしで進む（現行仕様: permission-modes.md）。

AgentEvent プロトコル（zod で型定義、バージョン付き）／Runner Adapter 3 種（プラグイン）／Workspace MCP／Phase 0〜3 の段階導入（§6）

3. アーキテクチャ

中核は 1 プロセスのローカルデーモン。UI からもスケジューラからも同じ WebSocket API で叩き、ランナーごとの差はアダプタに閉じ込める（現行: UI は HTTP の API と、AgentEvent を流す WebSocket を使う。スケジューラはデーモンの中で動く — packages/core/src/server.ts、scheduler.ts）。デーモンは同時に Workspace MCP サーバを公開し、自前のファイルツールを持たないランナー（DAK）はこの口を通して手元のリポジトリを触る。

Workspace MCP（DAK がクライアント側を触るための口）

Claude Code と Codex は自前のファイル操作とコマンド実行を持つが、DAK はコンテナの中にいて手元のリポジトリが見えない。そこで デーモン自身が MCP サーバになる。DAK 側は agent_config.yaml の mcp_servers に http://host.docker.internal:<port>/mcp を一行足すだけで、DAK の設計（ツールは MCP で動的発見、System ENABLES / Agent DECIDES）を壊さずに繋がる。

ツール挙動ガード
fs.list / fs.read / fs.grepスコープ内ディレクトリの読み取りTask Brief のスコープ外は見えない（パス正規化とシンボリックリンク解決の上で封じ込め）
fs.write / fs.patch書き込みはステージングに積む。実ファイルには触れないUI に差分として現れ、承認で適用。permission.ask と同じ経路
exec.runスコープ内 cwd でコマンド実行、出力はサイズ上限付きで返すallow/deny 規則（Knowledge の rules に書く）。既定は読み取り系のみ即時、それ以外は確認
task.note / task.artifactタスクへのメモ・成果物登録—

最低限は fs と exec で足りる。加えておきたい 2 点は、タスクごとに使い捨てのエンドポイント URL とトークンを発行すること（DAK に渡す URL がそのままスコープと権限になり、タスク終了で失効する）と、書き込みを直接ではなくステージングにする点。後者があると DAK のように放置して回す仕事でも、朝に差分をまとめて眺めて適用できる。DAK 側の mcp-server にある安全層と同じ発想を、クライアント側にも置く形になる。

この口は DAK 専用ではない。Claude Code にも --mcp-config で渡せば、タスク登録や Knowledge 検索をエージェント側から呼べる。

AgentEvent（共通イベント形式）

アダプタが必ず出す最小集合。ここを先に固めて zod でスキーマ化し、packages/protocol として公開する。これが OSS としての拡張点（他ランナーの追加）になる。

type AgentEvent =
  | { t:"session.start";   runner:"claude"|"codex"|"dak"; sessionId; cwd; scope:string[] }
  | { t:"message.delta";   role:"assistant"|"user"; text }
  | { t:"tool.call";       id; name; input; cwd? }            // Bash/Edit/MCP を同じ形に
  | { t:"tool.result";     id; ok:boolean; summary; bytes }
  | { t:"permission.ask";  id; kind:"exec"|"write"|"network"; detail }  // UI が承認/拒否を返す
  | { t:"usage";           inputTokens; outputTokens; cacheRead?; costUsd?; source:"reported"|"estimated" }
  | { t:"artifact";        kind:"diff"|"file"|"doc"; path; stat }
  | { t:"session.end";     status:"ok"|"error"|"aborted"; summary }

Claude は stream-json の assistant / tool_use / result を、Codex は app-server の通知を、DAK は /run_sse の Event と Workspace MCP への呼び出しをこの形に写す。permission.ask を UI に返せることが「Terminal より便利」の最初の根拠で、Claude の --permission-mode と Codex の --sandbox をカードの設定として統一的に見せられる。

ルーティング規則（v1 はルール表、LLM は使わない）

現行: ルール表（packages/core/src/routing.ts）が既定。加えて任意で、読み取り専用の 1 ターンでランナーを提案する設定（既定 off、suggest-llm.ts）と、Workspace を自動で選ぶ 1 ターン（suggest-workspace.ts）がある（docs/design/llm-routing.md）。提案が結果に役立ったかを見せる経路は #1143（未完）。

条件推奨理由（Brief に表示する文言）
複数リポジトリ横断／設計・調査／MCP・skills を使うClaudeプラグインと 1M コンテキストが効く。対話で軌道修正する仕事
単一リポジトリで完結・長時間・レビュー（codex review）Codexサンドボックスが強く放置しやすい。ChatGPT プラン内で消化できる
定型の保守（依存トリアージ等、DAK skill が既にある）／ローカル LLM で足りるDAKゼロコスト。DAK の eval にも寄与する
上記に該当しない前回このリポジトリで使ったランナーユーザーの選択を記録し、結果（成功・中断・コスト）を学習材料として残す

提案は常に 一クリックで上書き できる。判断ログと結果を Ledger に残しておけば、v2 で安価モデルにルーティングさせる時の教師データになる。

5. 技術選定

手元に何が入っているかは判断材料にしない。必要なツールチェーンは入れる前提で、コアの言語とデスクトップシェルを別々に決める。コアはネットワーク越しに叩けるデーモンとして独立させる（Workspace MCP、将来のモバイル承認、DAK からの接続がすべてこれを要求する）ので、シェルは「ウェブビュー + OS 統合」だけを担う薄い層になる。その層は結局ブラウザ（PWA）で足り、デスクトップシェルは採らなかった（下の判断）。

コアの言語

候補強み弱み判定
TypeScript（Bun）MCP の参照実装 SDK、Codex app-server の生成型、Claude の stream-json 読みがすべて TS で揃う。bun:sqlite・WebSocket・Bun.spawn が標準。bun build --compile で単一バイナリ化もできる。LLM に書かせる反復が最速node-pty など一部ネイティブ拡張の互換を Phase 0 で確認する必要（確認の結果、node-pty は Bun で動かず bun-pty にした — docs/design/spike-bun-compat.md）採用
Rust単一バイナリ、メモリ安全。Codex 自身が Rustプロセス編成とストリーム変換が主な仕事で性能要件がない。MCP サーバ・アダプタの試行錯誤で TS より遅く、UI と言語が割れて自己更新のループが重くなるコアには採らない
PythonDAK と同じランナー側の口が TS 寄り。配布と起動が重い採らない

デスクトップシェル

候補強み弱み判定
Tauri 210〜20MB、OS のウェブビュー、公式プラグインで通知・トレイ・ディープリンク・自動更新・サイドカー管理が揃う。既定のセキュリティ（capabilities）が堅い。Windows / Linux を同じコードで配布シェル側の Rust は数百行で済むが、変更時のコンパイルは要る。Linux の WebKitGTK に描画差が出ることがある不採用（2026-10-11）（当初は Phase 2 で採用の予定）
ElectronChromium 同梱で描画が均一。メインプロセスが Node150MB 級、メモリ大。コアが独立デーモンである以上「Node が同梱」の利点が効かない採らない
ブラウザ（localhost / PWA）パッケージング不要、HMR で自己更新が最速。PWA でデスクトップにもモバイルにも同じコード通知・トレイ・ディープリンク受けが弱い採用（現在の構成）
Flutter / Swift ネイティブ手触りUI が別言語になり、自己更新のループが重い採らない
判断（2026-10-11）: デスクトップシェルは作らない。Tauri は不採用で、後の Phase にも移さない。根拠は #1145 の回答 A（旧 PBI #17「Tauri 2 シェル」は not planned で閉じ、Phase 2 の Milestone にも破棄と記録済み）。
理由: シェルに期待した役割が、別の形で既に満たされている。ブラウザ UI は PWA としてデスクトップとスマートフォンのホーム画面に置け（apps/web/public/manifest.webmanifest、docs/design/mobile-approval.md）、自己更新は不変リリースの昇格と自動ロールバック、どのブラウザからでも開ける救援画面（sb-rescue）が担う（docs/design/releases-and-rescue.md、rescue/src/promote.ts）。シェルの再ビルドが無いぶん自己更新のループも軽い。通知は別 PBI #1138 で扱い、そのためにシェルは要らない。
到達点: ブラウザから本体への要望を出し、その変更が動いているデーモンに反映される（§6 Phase 2 の到達点と同じ）。本書の他の箇所の Tauri への言及は、この判断を指す。

推奨スタック

草案時の推奨。現行の依存は package.json（root・apps/web・packages/core）で、採らなかったものは各行に「現行」と書いた。

  • モノレポ：Bun workspaces + TypeScript strict。packages/protocol（zod スキーマ）、packages/core（デーモン + Workspace MCP）、packages/adapters/{claude,codex,dak}（プラグイン。どれを外しても本体が起動する）、apps/web（PWA）、rescue（sb-rescue）。デスクトップシェルの apps/desktop は作らない（判断）。
  • デーモン：Bun、Hono（HTTP + WebSocket + MCP の streamable HTTP）、bun:sqlite（FTS5 で Knowledge 全文検索）、@modelcontextprotocol/sdk で Workspace MCP、chokidar で Knowledge と生成先を監視（現行: Hono と chokidar は使わず、Bun.serve と node:fs の watch。bun:sqlite の FTS5 と @modelcontextprotocol/sdk は採用）。開発時は bun --watch、実運用は不変リリース（git archive + 依存の導入 + Web のビルド）を昇格して動かす（docs/design/releases-and-rescue.md）。
  • アダプタ：Claude は CLI を stream-json 双方向で spawn（Max ログイン・plugins・settings をそのまま継承。Agent SDK は独自条項のため依存しない）。Codex は codex app-server を stdio JSON-RPC で spawn し、型は codex app-server generate-ts でビルド時に生成（Apache-2.0、スナップショットを NOTICE 付きでコミット）。DAK は ADK REST の /run_sse を SSE で読み、Workspace MCP の URL を agent_config.yaml 経由で渡す。
  • UI：React 19 + Vite、TanStack Router / Query、Zustand。差分は diff2html か自作、コードは Shiki、Markdown 編集は CodeMirror 6（フル IDE にはしない）、ターミナルタブは xterm.js + node-pty（Phase 1 後半。Bun 互換が悪ければ PTY だけ小さな Rust サイドカーに逃がす）。（現行: 依存は React 19・Vite・xterm.js だけ。TanStack・Zustand・diff2html・Shiki・CodeMirror は使っていない。PTY はデーモンの中の bun-pty で、サイドカーは無い — docs/design/pty-bridge.md）
  • テスト：bun test。アダプタは 録画再生（各ランナーの実イベントを fixture 化）で決定論的に。DAK の fake-LLM と golden replay の考え方をそのまま持ち込む。
  • 導入手順：Bun をセットアップスクリプト（scripts/setup.sh）で入れる。Rust・Tauri CLI は要らない。ランナーは各公式インストーラ（Claude Code は公式手順、Codex は公式 curl インストーラ）に委ね、アプリは PATH を見るだけ。

採らないもの、後に回すもの

  • 独自エディタ。Monaco を積み始めると「VSCode の劣化版」に収束する。差分ビュー + ディープリンクで止める。
  • LLM による自動ルーティングは v2。v1 はルール表と記録に留め、判断の教師データを貯める。
  • ベンダ CLI の同梱依存。which codex → 見つからなければ公式 curl インストーラの手順を出す。
  • A2A。エージェント間通信の仕様であり、クライアントから叩く口としては REST が素直。DAK が将来 A2A で外部エージェントと話す際も、本体は関与しない。
  • クラウド同期・マルチユーザー。Knowledge は git、セッションはローカル。共有したければ git remote で足りる。

Phase 0 で潰す技術リスク

  • Bun 上で codex app-server の stdio JSON-RPC と Claude の stream-json を同時に安定して読めるか（バックプレッシャ、プロセス終了処理）。
  • Bun と node-pty、@modelcontextprotocol/sdk の互換。（結果: node-pty は動かない、SDK は動く — docs/design/spike-bun-compat.md）
  • Docker 内の DAK から host.docker.internal で Workspace MCP に到達できるか（Linux は extra_hosts が要る。DAK の nightly-eval が既に同じ問題を解いている）。

Self-dev を成立させる構造

  • 起動時に自分のリポジトリを meta workspace として自動登録し、Brief 生成時に構成図・パッケージ地図・テストコマンドを注入する。
  • apps/web の変更は Vite HMR で即反映、packages/core の変更は差分承認後にデーモンが自己 exec で再起動し、UI は WebSocket 再接続で復帰する。実運用では新しいコミットを予備のポートで起動してから昇格し、起動しなければ自動で戻す（rescue/src/promote.ts）。シェルは持たないので、その再ビルドは無い。
  • ルール・コマンド・価格表・ルーティング規則を全部データにし、「アプリを変える」の大半をビルドなしで済ませる。

6. ロードマップと OSS スコープ

各 Phase の終わりに「Terminal の Claude Code だけより便利か」を自分で判定できる到達点を置く。Phase 0 の終わりで便利でなければ、そこで止める判断もできる粒度にしてある。

PHASE 0 · 2–3 週

骨格（ローカル git）

  • protocol / core / Claude アダプタ
  • Task 画面（会話・承認・スコープ）
  • Ledger の Claude 分
  • ブラウザ UI、自リポジトリを meta workspace 登録
  • 技術リスクの spike（§5）
到達点：Claude Code を Switchboard 経由で一日使い、承認とコストが見える
PHASE 1 · 3–4 週

2 ランナーと正本

  • Codex アダプタ（app-server）
  • ルール表ルーティング + Brief
  • Knowledge Store + Materializer（CLAUDE.md / AGENTS.md / commands）
  • Inbox → Task 昇格
  • Workspace MCP の骨格（fs / exec / staging）
到達点：CLAUDE.md を手で編集しなくなる。使い分けを考えなくなる
PHASE 2 · 3 週

自己更新（デスクトップ化は不採用）

  • Tauri 2 で包む → 不採用（§5）。代わりに PWA、リリースの昇格と救援画面
  • Self-dev フロー（差分 → テスト → 再起動）
  • DAK アダプタ（/run_sse + Workspace MCP）
  • スケジューラ（DAK の nightly 系を起動）
到達点：本体への要望を本体の中で投げて反映できる。DAK が手元のリポジトリを安全に触れる
PHASE 3 · 公開以降

公開と学習

  • ライセンス整理の完了を条件に GitHub 公開（Apache-2.0）
  • LLM ルーティング（Ledger を教師データに）— 任意の提案は実装済み、効果の見せ方は #1143
  • モバイル PWA で承認（Tailscale）— 実装済み（docs/design/mobile-approval.md。iOS Safari と Tailscale は未検証）
  • ローカル LLM 向きの仕事を DAK に流すルール
到達点：ローカル LLM で済む仕事が DAK に流れ、実課金が下がる

公開時に載せるもの

  • protocol・core（Workspace MCP 含む）・アダプタ 3 種（Claude / Codex / DAK、いずれも任意）・Web UI（PWA）・救援画面（sb-rescue）
  • Knowledge Store と Materializer、Inbox
  • Ledger（reported usage + 価格表 JSON）、タスク予算
  • ルール表ルーティング、Task Brief、Context footprint
  • Self-dev モード、録画再生テスト
  • ライセンスは DAK と同じ Apache-2.0。Codex 生成型の NOTICE を同梱

公開の前に済ませること

  • Claude Code の定額認証を CLI 経由で使う構成の規約確認（§1）。結論次第で README の注記か、Claude アダプタを別配布にする — 済み（README の注記。#22）
  • Codex 生成型の取り込み方（ビルド時生成か、NOTICE 付きスナップショットか）の確定 — NOTICE 付きスナップショット（packages/adapters/codex/src/generated、NOTICE）
  • 依存ライセンスの一覧化（bun pm ls ベースのスクリプトを CI に）— bun run licenses:check（docs/design/licenses.md）
  • 履歴を持たない tree mirror として配布する（docs/design/public-repo.md）。fork は同梱の工程で開発できる

載せないもの・引く線

  • 後回し LLM ルーティング、スケジューラの高度化、モバイル承認、決済（AP2）連携
  • 載せない ベンダ CLI の同梱、Claude Agent SDK への依存、API キーの保管（各 CLI のログインに委ねる）、テレメトリ送信、既定での無審査の全許可（Auto のリスクベース自動審査は許容）
  • 載せない チーム機能・クラウド同期（Knowledge は git remote で共有できる）
  • 載せない DAK への依存。DAK アダプタを外しても、DAK を知らなくても、本体は完全に動く
OSS として説明しやすい一文：「あなたが既にログインしている Claude Code と Codex、あるいは自前のエージェントを、一つの画面・一つの正本・一つの台帳で扱うローカルクライアント。鍵は持たず、会話は使うランナーの提供者と、設定で選んだランナー（終わったターンの判定・評価、ルーティング）の提供者に送る。」

7. 決めてほしいこと

草案（2026-09-05）で利用者に了承を求めた 5 点。2026-10-13 に、実装で確かめられる「現在の状態」と、利用者の正式な採否（記録があるもの）を分けて照合した。

論点草案の問い → 現在の状態根拠
1. 名前草案: Switchboard（仮称、配電盤・交換台の意）。DAK は冠さない。候補は Switchboard / Relay / Dispatch。
Switchboard の名前で作り、使っている（リポジトリ名、パッケージ名 @switchboard/*）。DAK は冠していない。正式に決めた記録は見つからない — 未決		package.json、docs/design/public-repo.md
2. リポジトリの置き場草案: ローカル git で始め、公開判断の時点で GitHub へ push。依存は Switchboard → DAK の一方向。（草案の文の一部を省いた）
公開は main のツリーだけを新しい履歴で送る tree mirror。DAK は任意の接続先で、依存方向は Switchboard → DAK。DAK アダプタを外しても本体は動く。		docs/design/public-repo.md、README の Design rules
3. ブラウザで始める草案: Phase 0 をブラウザで始めることの了承。
ブラウザで始め、そのまま本線にした。Tauri のシェルは作らない（§5 の判断）。解決済み		#1145 の回答 A（2026-10-11）
4. Knowledge の場所草案: ~/Knowledge のような単独 git リポジトリを推奨。既存の blog / notes を取り込むかは Phase 1 で判断。
場所は ~/Knowledge（SWITCHBOARD_KNOWLEDGE で変えられる）。git で管理するかは任意（実装は git の状態を表示するだけ — knowledge.ts の gitStatus）。書き出し先はリポジトリではなくユーザーレベルのファイル（#197）。blog / notes の取り込みを決めた記録は見つからない — 未決		README の Data の段落、#197、packages/core/src/knowledge.ts
5. MCP の初期ツール草案: Workspace MCP は fs（list / read / grep / write / patch）と exec の 2 群で始める。ステージング書き込みと使い捨てエンドポイントは Phase 1。
実装済み: fs と exec、ステージングした書き込み、Task ごとのエンドポイントとトークン（/mcp/<taskId>）。利用者が正式に了承した記録は見つからない（実装の状態は確かめたが、採否は未記録）		packages/core/src/mcp.ts、docs/design/workspace-mcp.md
