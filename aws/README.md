# AWS: Switchboard that runs only while it is used

Design: `docs/design/cloud-hosting.md` §3–§6. One stack `switchboard-host` in your AWS account and chosen region: an EC2 instance (Graviton, on-demand by default; optional Spot with stop on interruption), CloudFront as the only way in, an S3 start page for when the instance is stopped, a small Starter Lambda (start / stop / rebuild), EventBridge Scheduler to wake it, S3 for the sqlite replica and the daily archive, and two budgets.

> Estimate the cost for your region, instance type and operating hours before deploying. See `docs/design/cloud-hosting.md` §3.2.

## What goes where

| | Where | Who writes it |
|---|---|---|
| The runners' logins | the instance (`~/.claude`, `~/.codex`, `gh`) — or the setup-token below | the runners themselves, in the terminal tab (§4) |
| `/switchboard/edge-header` | SSM SecureString; the same value is passed to the stack as `EdgeHeaderValue` | you, once |
| `/switchboard/start-token` | SSM SecureString; for machines only (the GitHub workflow, sb-rescue's rebuild). A person never types it | you, once |
| `/switchboard/session-signing-key` | SSM SecureString: an Ed25519 seed, exactly 32 random bytes in hex. **Only the Starter reads it**: it signs the `sb_session` / `sb_recent` cookies and the login's challenges. Replacing it (and the public key below) logs every browser out | you, once |
| `/switchboard/session-public-key` | SSM String: the seed's public key (raw 32 bytes, base64url, 43 characters). `sb-env` hands it to the daemon and sb-rescue, which check the cookie with it and cannot make one | you, once |
| `/switchboard/register-code` | SSM SecureString `<code>.<expiresMs>`, one-time: put by the agent to hand a person a passkey registration link; the Starter deletes it once used | the agent |
| `/switchboard/github-token` | SSM SecureString (fine-grained, your resource owner and only the repositories the instance works on). **Before the first deploy**: the instance clones the repository with it to get its `aws/host/` scripts. Repository permissions: Contents, Issues, Pull requests, Workflows (read and write); Actions, Checks, Commit statuses, Variables, Metadata (read) — without Checks and statuses `scripts/merge-gate.ts` cannot judge a PR. When you widen the repositories it can write to, or its permissions, revisit `docs/design/cloud-hosting.md` §6.5: root runs what main holds. Organization permissions: Projects (read and write) — the backlog screen and the setup scripts read and write the organization's Project with it | you |
| `/switchboard/archive-age-pubkey` | SSM String (an `age` public key; the private key stays off AWS) | you |
| `/switchboard/daemon-token` | SSM SecureString (optional). The API token of the daemon and sb-rescue: `sb-env` writes it to `~/.switchboard/token` before every start, as the OS user. It counts **only on the instance itself** (loopback: the runners' `/mcp`, sb-rescue's probe, a Task's own `curl`); from outside — CloudFront included — only the passkey cookie gets in. Rotate by updating it and restarting | you |
| `/switchboard/claude-oauth-token` | SSM SecureString, only if you use `claude setup-token` (`scripts/host/claude-wrapper.sh`, §4.2) | you |
| `/switchboard/anthropic-api-key` | SSM SecureString (the AWS managed key `alias/aws/ssm`), only if DAK runs on this instance with Anthropic's API. **No script here reads it**: DAK's `agent/ssm_exec.py` reads it inside its container at start and hands it to its own server process (DAK's `docs/getting-started/anthropic.md`, `docker-compose.anthropic.yml`). The Compose file carries the parameter name and the model name only; the value never goes to a file, a Docker setting, a log or the Switchboard daemon. A key under a customer managed KMS key would need that key's decrypt permission too: do not add it on your own — ask | you |
| `cdn-logs/` in the data bucket | CloudFront's standard access log: every request, the login's included; 90 days. The host role can neither read nor delete it | CloudFront |
| CloudWatch Logs `/switchboard/host` | the daemon's `access` / `op` lines from `~/.switchboard/daemon.log`, one stream per instance; 90 days, so a rebuild does not erase it. The host role can only write to it | the CloudWatch agent |

The host role (and the boundary) can call Amazon Bedrock for **any model** (`bedrock:InvokeModel*` on every inference profile and foundation model; versions are not pinned, so a new model needs no deploy), and `bedrock-mantle:CreateInference` on the account's projects in any region, which is how Codex reaches the OpenAI models; no other Bedrock action, no API key (`docs/design/bedrock.md`).

The host role (and the boundary) can also **read the account's cost**: `ce:GetCostAndUsage` and `ce:GetCostForecast` (Cost Explorer has no resource-level permissions, so `*`) and `budgets:ViewBudget` on this account's budgets. Reads only: no budget is created, changed or deleted, and no Cost Explorer setting. A weekly cost report (a scheduled Task that reads these and writes a report to Insights) uses it; the numbers are the whole account's, and the same OS user's Tasks can read them too. Each Cost Explorer call costs USD 0.01.

Adding it to a running stack: the `Boundary` changes, so it is a person's deploy (`bun scripts/host-ops.ts person-deploy --yes`, the Deploy section below), not the workflow's `deploy`. Read the change set it prints before executing it with `--execute=<change set ARN>`: it must list only `Boundary` and `InstanceRole`, as `Modify` / `False` — no `LaunchTemplate`, no `Instance`, and nothing else (another resource there is a template change that has not been deployed yet: look at it before running this one). Then on the instance, `aws ce get-cost-and-usage --region us-east-1 --time-period Start=$(date +%Y-%m-01),End=$(date -d tomorrow +%F) --granularity MONTHLY --metrics UnblendedCost --query 'ResultsByTime[0].Total' --output json` answers with an amount instead of AccessDenied.

CloudFormation cannot create SecureStrings, and a `String` placeholder would hold a secret in plain text, so the stack creates none of them. The instance role can read only the parameters the instance's scripts read, listed by name in the template (the table's except register-code, and the stack's `web-url`, `starter-url` and `offload-project`), and nothing else in SSM: not `/switchboard/register-code`, so an agent on the instance cannot use a registration link before the person it was made for. A new parameter the instance reads goes into that list too (`aws/template.test.ts` checks that the list names exactly the scripts' parameters plus `anthropic-api-key`, the one read by DAK rather than by a script).

Backups: the data bucket keeps versions. The instance role (which agents can reach, since they run as the same OS user) writes only `litestream/` and `archive/`, reads `releases/`, may add a delete marker but cannot remove a version or change the bucket's versioning or lifecycle. Old versions and archives expire after 30 days. `history/` is what leaves the instance's database for good (finished Tasks' events and transcripts): it has no expiration, and the instance role may read it and put a new key there, but not overwrite or delete one — removing something under `history/` is a person's job, with their own credentials. A put must carry `If-None-Match: *`, which `aws s3 cp` does not send: `aws s3api put-object --bucket <DataBucket> --key history/<…> --body <file> --if-none-match '*'` (an existing key answers 412 PreconditionFailed; without the header the role is denied).

Request logs: the daemon (off loopback) writes one JSON line per request and per strong operation to its output, the CloudWatch agent ships `daemon.log` to `/switchboard/host`, the Starter writes failed logins and the rate limit as `"log":"auth"` lines to its own Lambda log group, and CloudFront's standard log goes to `cdn-logs/`. The daemon's and the Starter's lines carry metadata only: no body, cookie, token or query value. CloudFront's own log cannot leave the query out, so a search term or a Task id in a query does appear there; the registration link's code is in the URL fragment (`#register=`) for that reason, so it never reaches any log. Deploy notes: the Data bucket gets ACLs enabled (`BucketOwnerPreferred`; the public-access block stays), which CloudFront's log delivery needs; the instance's CloudWatch agent config is installed by bootstrap only, so an existing instance needs one rebuild before `daemon.log` is shipped; the daemon's lines carry the viewer's address once the distribution forwards `CloudFront-Viewer-Address` (until then, the connection's peer, i.e. CloudFront). Logs exist from the deploy on; there is nothing before it.

The way in: CloudFront reaches the instance as a **VPC origin** (by instance id, inside the VPC), one per port (47831 Switchboard, 47841 sb-rescue). The private address survives stop/start, nothing goes over the internet in plain text, and a stopped instance's released public IP is never contacted. The instance keeps a public IPv4 only for its own egress (GitHub, npm, the runners' APIs); the security group lets in CloudFront's origin-facing prefix list only. AWS documents VPC origins for instances in private subnets; the migration procedure there runs with the subnet still public, which is how this stack uses it — **confirm on the first deploy**. If CloudFront refuses it, the choices cost money and are the user's: a private subnet with a NAT gateway (about USD 45 a month) or a NAT instance, or an Elastic IP with an https origin. Pick a subnet outside apne1-az3 (no VPC origins there).

Roles: `HostAssumeRoleArns` is the exception to the resource scope below: the deployer may name extra roles the instance may assume (empty by default). Every role the stack makes carries the `<stack>-boundary` permissions boundary, and the rest of the boundary names this stack's own resources (its parameters `/switchboard/*`, its two buckets, its instance by the stack tag, its roles `<stack>-*`, its log groups; KMS only through SSM and EC2 for the AWS managed keys). `DeployRole`, which the workflow updates the stack through, may create or change roles only with that boundary, cannot change the boundary, a trust policy or itself, and cannot touch another stack's instance — so a template change to `DeployRole` or `Boundary` needs a person's deploy. Nothing reachable from the internet can pass `DeployRole`: the Starter has no CloudFormation permission at all.

`DakFunctionArn` optionally lets the host (the instance role and the boundary) call one Lambda function, DAK's, by its exact ARN: `lambda:InvokeFunction` (which also covers a streaming invoke) and `lambda:GetFunction`, on that ARN only, with no name pattern. Empty (the default) adds no Lambda permission to either the boundary or the host policy. The function's own resource-based policy must also allow the host role, which is done on the DAK side. The `Boundary` changes, so adding it to a running stack is a person's deploy (the Deploy section below), and its change set must list only `Boundary` and `InstanceRole`.

## Deploy (after approval)

**Who deploys how.** A person deploys with their own administrator login in two steps: `bun scripts/host-ops.ts person-deploy --yes` makes the change set, prints each resource it changes and stops; after reading it, `bun scripts/host-ops.ts person-deploy --execute=<change set ARN> --yes` (the command it prints) runs it. `bun scripts/host-ops.ts deploy` is the GitHub workflow's: it runs as `DeployRole`, which cannot change the `Boundary`, a trust policy or itself, so a person does not use it. Do not pass `--role-arn` by hand either: CloudFormation keeps a role passed to a stack and runs every later operation on that stack (a drift detection too) as that role; it cannot be removed, only replaced by passing another. Anyone who may operate on the stack can use the role attached to it, which is why the person's deploy role holds no permission between runs. Steps written in an issue for a deploy name `person-deploy` (or `person-drift`), not `deploy`.

**The person's deploy role, once** (`aws/person-deploy.yaml`): a person's deploy runs as this role, which holds no permission except while `bun scripts/host-ops.ts person-deploy --yes` runs. Create its stack with your own administrator login and no `--role-arn`, after the host stack exists:

```sh
aws cloudformation deploy --template-file aws/person-deploy.yaml --stack-name switchboard-host-person-deploy --capabilities CAPABILITY_NAMED_IAM --tags Project=switchboard
```

Pass `--parameter-overrides HostStack=<name>` (and set `SWITCHBOARD_PERSON_DEPLOY_STACK`) for a host stack with another name. Afterwards `aws iam list-attached-role-policies --role-name switchboard-host-person-deploy` must be empty.

A drift detection also runs as the role attached to the stack, so with your own login it fails on that role's missing permissions: run `bun scripts/host-ops.ts person-drift --yes` instead, which lends the role the same permission for the detection only and lists the drifted resources.

`HostAssumeRoleArns` optionally grants the instance role permission to assume the listed role ARNs (comma separated, for example `HostAssumeRoleArns=arn:aws:iam::<account>:role/build-role,arn:aws:iam::<account>:role/check-role`). The target roles must also trust the instance role. Empty (the default) adds no AssumeRole statement to either the boundary or the host policy. Existing deployments must pass their additional role ARNs on the next deploy; omitting the new parameter removes that permission. Keep the override in the deployment parameters, including `SWITCHBOARD_HOST_PARAMS` if using the workflow. Inspect the change set: this migration must change only the boundary and host policies, with no change to Instance or LaunchTemplate.

Development repository owner/name is supplied as `GitHubRepo=<owner>/<repo>` at deploy time (no default; UserData clones it, so a new value replaces the instance). Set the administrator-owned SSM parameter too:

```bash
aws ssm put-parameter --name /switchboard/github-repo --type String --value <owner>/<repo>
```

Use `--overwrite` to change an existing parameter. The instance reads it at every start (bootstrap and `sb-host-update`), so it follows a rename without replacing the instance — once the instance role may read it, which a stack deployed before that parameter existed does not allow (adding it is a list change, above: compare the change set with the merged template first — it must add only the one `ssm:GetParameter` resource and touch neither `LaunchTemplate` nor `Instance` — then run the workflow's `deploy`). bootstrap starts by fetching the `main` of that repository into the root-owned clone and running that copy of itself, so a rebuild runs the bootstrap of the repository the parameter names without a replacement. This only works once the clone UserData makes (from the stack's `GitHubRepo`) holds a bootstrap with this step. Without a readable, valid parameter, bootstrap goes on with the clone of the stack's `GitHubRepo` and clones that repository for the OS user, and `sb-host-update` follows the root-owned clone's origin. When the parameter is readable but the fetch fails, bootstrap goes on with the clone UserData made (the OS user's clone still comes from the parameter's repository) and `sb-host-update` keeps the installed scripts. Each says so on stderr (`journalctl -u switchboard.service` for `sb-host-update`). The OS user's worktree settings are never used for this root step.

AWS CLI v2, SAM CLI (for `sam validate` only) and a login for the profile. From the repository root. The deploy is `aws cloudformation package` + `aws cloudformation deploy`, not `sam deploy`: SAM CLI cannot read the template's `Fn::ForEach` (the VPC origins, see Deploys that replace the instance); the SAM transform still runs in CloudFormation.

```sh
# once: the parameters (use the console instead if you do not want the values in your shell history)
openssl rand -hex 32   # → EDGE; another one → START; a third → SEED (the login's Ed25519 signing key)
PUBLIC=$(bun -e 'import { publicKeyOf } from "./aws/auth.ts"; console.log(publicKeyOf(process.argv[1]))' "$SEED")
aws ssm put-parameter --name /switchboard/edge-header --type SecureString --value "$EDGE" --profile YOUR_PROFILE --region <region>
aws ssm put-parameter --name /switchboard/start-token --type SecureString --value "$START" --profile YOUR_PROFILE --region <region>
aws ssm put-parameter --name /switchboard/session-signing-key --type SecureString --value "$SEED" --profile YOUR_PROFILE --region <region>
aws ssm put-parameter --name /switchboard/session-public-key --type String --value "$PUBLIC" --profile YOUR_PROFILE --region <region>
IMAGE=$(aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 --query Parameter.Value --output text --profile YOUR_PROFILE --region <region>)   # pinned: change it only in a deploy you watch
aws ec2 describe-managed-prefix-lists --filters Name=prefix-list-name,Values=com.amazonaws.global.cloudfront.origin-facing --query 'PrefixLists[0].PrefixListId' --output text --profile YOUR_PROFILE --region <region>

sam validate --lint --template aws/template.yaml
bun run --cwd aws build                       # the Starter: the template's CodeUri is dist/starter/
# BUCKET: a bucket of yours for the upload (the first deploy only, e.g. aws s3 mb s3://<name>); later deploys use the stack's DataBucket output
aws cloudformation package --template-file aws/template.yaml --s3-bucket "$BUCKET" --s3-prefix releases/sam \
  --output-template-file dist/template.packaged.yaml --region <region> --profile YOUR_PROFILE
aws cloudformation deploy --template-file dist/template.packaged.yaml --stack-name switchboard-host --s3-bucket "$BUCKET" --s3-prefix releases/sam \
  --capabilities CAPABILITY_IAM CAPABILITY_NAMED_IAM CAPABILITY_AUTO_EXPAND \
  --region <region> --profile YOUR_PROFILE --no-execute-changeset --tags Project=switchboard \
  --parameter-overrides GitHubRepo=<owner>/<repo> ImageId="$IMAGE" VpcId=vpc-… SubnetId=subnet-… CloudFrontPrefixListId=pl-… BudgetEmail=… \
    EdgeHeaderValue="$(aws ssm get-parameter --name /switchboard/edge-header --with-decryption --query Parameter.Value --output text --profile YOUR_PROFILE --region <region>)" \
    HostUser=…
```

Look at the change set, then execute it. In Billing → Cost allocation tags, activate `Project`: budgets count only resources tagged `Project=<CostTag>`. Check that `Project` shows as Active on that page: a budget's actual can stay at 0 until the tag is active and the tagged spend has been counted, which can take a day. Leave `HostHome` and `ReposDir` at their defaults unless you need different paths. Importing history from another machine is optional; follow `docs/design/cloud-hosting.md` §5 and use `relocate` to map old paths.

The first deploy has no real `PublicOrigin`. Take the `Origin` output and deploy again with `PublicOrigin=https://<distribution>.cloudfront.net`. If your account already has a GitHub OIDC provider, pass `GitHubOidcProviderArn=arn:aws:iam::<account>:oidc-provider/token.actions.githubusercontent.com`.

**Scripts in `aws/host/`**: the instance's UserData clones the repository's `main` with `/switchboard/github-token` and runs `aws/host/bootstrap.sh` from it, on every new instance; bootstrap then moves to the `main` of `/switchboard/github-repo` (see the parameter above). Nothing is uploaded by hand; put `/switchboard/github-token` and `/switchboard/archive-age-pubkey` before the first deploy.

What `bootstrap.sh` sets up (once per disk): the OS user with `HostHome`, bun / git / gh / age / Litestream (pinned versions, SHA-256 checked) / claude / codex, the repository in `ReposDir` (with the GitHub token), `sb-rescue` (`bun rescue/install.ts`), sqlite restored from Litestream when the disk is new and a replica exists, `claude-wrapper.sh` ahead of the real `claude` when `/switchboard/claude-oauth-token` exists, and the units:

| unit | what |
|---|---|
| `switchboard.service` | sb-rescue running the daemon from its release; `SWITCHBOARD_HOST=0.0.0.0`, `SWITCHBOARD_IDLE_STOP_CMD=/usr/local/bin/sb-stop`; before every start, as root, `sb-host-update` (the `aws/host/` scripts again from `main`) and the edge header and the other values from `sb-env` |
| `litestream.service` | sqlite → `s3://<DataBucket>/litestream/` (on stop it syncs the database and the replica one last time) |
| `sb-archive.timer` | daily `export --encrypt` → `s3://<DataBucket>/archive/`. Works in `~/.switchboard/archive-out` (on the disk, not /tmp), and writes the result to `~/.switchboard/archive.status`. Then finished Tasks' events 30 days old → `s3://<DataBucket>/history/events/` (kept; the rows are cut down only for what arrived, `docs/design/cloud-hosting.md`) |

`sb-stop <ISO|->` (called by the daemon after 20 idle minutes) registers `switchboard-wake` in EventBridge Scheduler (with `-`, removes a leftover one), stops Litestream (its last sync) and shuts down. The OS user may run exactly those two commands as root (`/etc/sudoers.d/switchboard`). Writes the daemon makes between Litestream's stop and the shutdown stay on the disk (a start keeps them) but are not in the replica, so a rebuild right after can lose those last seconds.

**Starter, login and start page**: build the Lambda before `aws cloudformation package` (the template's `CodeUri` is `dist/starter/`), and after the deploy put the start page in the start-page bucket (it only sends the browser to `/_auth/`):

```sh
bun run --cwd aws build                       # → dist/starter/index.mjs
aws s3 cp aws/startpage/index.html s3://<StartPageBucket>/_start/index.html --profile YOUR_PROFILE --region <region>
```

**Calling the Starter directly**: the Function URL answers 403 to every path, `/status` included, unless the request carries `x-switchboard-edge` (the value of `/switchboard/edge-header`, which CloudFront adds). Machines (the `host.yml` workflow, sb-rescue's rebuild) send it together with the start token. Order of a rollout: install the new sb-rescue first (`bun run rescue:install` on the instance, then restart sb-rescue with the `再起動` (Restart) button; promoting the daemon does not update it), then deploy the Lambda — deploying it first makes the rescue page's rebuild answer 403. After a deploy, `curl -s -o /dev/null -w '%{http_code}' <StarterUrl>/status` must print 403.

**Logging in (a person)**: open the distribution's URL. There is nothing to type: `/_auth/` (the Starter, through CloudFront, answering while the machine is stopped) logs in with a **passkey** (Face ID / a fingerprint), shows the machine's state, and starts it with one button when it is stopped; after 20–30 s it goes on to the page that was asked for. The cookie it sets (`sb_session`, HttpOnly, Secure, SameSite=Lax) ends 7 days after the login, or 24 hours after the last action (the body is `<passkeyId>.<idleUntilMs>.<expiresMs>`), and is accepted by the daemon and by the rescue page, so the web UI and `/rescue/` accept it (the strongest operations also need a recent passkey check, below). The Starter signs it with an Ed25519 seed only it can read; the instance holds the public key alone, so nothing on the instance — an agent included — can make a cookie. The daemon and the rescue page also ask the Starter (`/_auth/status`) whether the cookie's passkey is still registered, keeping the answer 5 minutes; when it cannot be asked, the cookie is refused. Starting, stopping, rebuilding, the rescue page's buttons and the daemon's terminal tab, restart, promote, workspace registration, settings save and dangerous-mode tasks also need a passkey check within the last 5 minutes (`sb_recent`, set with every login; the table is in `docs/design/cloud-hosting.md`); the page asks for it and goes on. The passkeys live in the data bucket as `auth/passkeys.json` (public keys and counters only; the instance role cannot write there). To log out, use the link at the bottom of `/_auth/` or the web UI's settings (`ログイン` → `ログアウト` (Login → Log out), shown with the passkey login only); both call `POST /_auth/logout`, which clears both cookies, and the next request goes to `/_auth/`.

- **The first passkey, or every device lost**: the agent makes a one-time link and gives it to the person in chat:
  ```sh
  CODE=$(openssl rand -hex 16); EXP=$(( ($(date +%s) + 3600) * 1000 ))
  aws ssm put-parameter --name /switchboard/register-code --type SecureString --overwrite --value "$CODE.$EXP" --profile YOUR_PROFILE --region <region>
  echo "https://<distribution>.cloudfront.net/_auth/#register=$CODE"   # valid for an hour, once
  ```
  Opening it on the phone and confirming with Face ID registers that device's passkey and logs it in. This link is not capped by the 5 passkeys below (it is the way back when every device is lost).
- **Another device, from a logged-in one**: open `/_auth/#devices` (or `/_auth/` while the machine is stopped) on a device that is logged in. The `登録済みのパスキー` (Registered passkeys) card lists each passkey (device, registered, last used, `この端末` (this device)). `別の端末を追加` (Add another device) asks for that device's passkey — a signature made for this request, so the cookies alone (`sb_session`, `sb_recent`) cannot ask — and shows a one-time link (`/_auth/#register=<code>`, 10 minutes, a new one replaces the last); open it on the new device and confirm with Face ID. The Starter keeps only the code's SHA-256, in `auth/passkeys.json` (the instance role cannot read it). A device code brings the list to 5 passkeys at most (409 beyond that: delete one first).
- **Removing a passkey / logging everyone out**: on the same card, `削除` (Delete) on a row, after a confirmation and the device's passkey (a signature made for this request); the last passkey cannot be deleted (409). Without a logged-in device, delete its entry from `auth/passkeys.json`. Either way the Starter refuses it at once, and the daemon and `/rescue/` within 5 minutes (open terminal and event sockets are closed on the same period). The passkey stays in the device's password manager and in its picker; choosing it makes the login page call `PublicKeyCredential.signalUnknownCredential` (the Starter answers 401 `reason: "unknown"` for an id not in the list), so a browser that supports it hides the passkey from the next picker. A device without that API shows a sentence saying the passkey was removed; delete it in the device's password manager settings. To log everyone out, make a new seed and public key (as in Deploy), update both parameters, then reboot the instance (EC2 → Instance state → Reboot): `switchboard.service` starts again and `sb-env` hands the new public key to the daemon and sb-rescue. Not the rescue page's `再起動` (Restart): until sb-rescue restarts it still holds the old public key, so it refuses every new cookie and the page is out of reach. The Starter reads the seed again within a minute. Without a seed (missing, or not 64 hex characters) the login answers 503 and signs nothing.
- Failed logins are limited per viewer (10 in 10 minutes; the viewer is CloudFront-Viewer-Address, an IPv6 address counted by its /64). The Starter runs at most 5 at once (reserved concurrency), so the open URL cannot run up the bill; `/_auth/status` without a cookie reads only the machine's state.

sb-rescue gets the Starter's URL and the start token from `sb-env`, which runs before every daemon start (on the very first boot the stack may not have written the URL yet: the button appears after the next restart), and shows the rebuild button (`作り直す`) on the rescue page.

**The GitHub workflow** (`.github/workflows/host.yml`, Actions → host → Run workflow): `status`, `start`, `rebuild`, `deploy`. Its steps are `scripts/host-ops.ts`: when Actions does not run, a person runs the same `bun scripts/host-ops.ts <action> --yes` with their own AWS CLI login, except `deploy`, for which a person runs `person-deploy` (`--dry-run` prints the plan and calls nothing). A repository that uses GitHub's immutable OIDC subject (`gh api repos/<owner>/<repo>/actions/oidc/customization/sub` shows `use_immutable_subject: true`) sends `repo:owner@id/name@id:…`: pass its `sub_claim_prefix` as `GitHubSubPrefix`, or the role refuses the workflow ("Not authorized to perform sts:AssumeRoleWithWebIdentity"). With the prefix set, only that subject is trusted, not the name. Put `GitHubSubPrefix=…` in `SWITCHBOARD_HOST_PARAMS` too, so a stack made from those parameters alone does not lock the workflow out. Set these repository variables (the SSM names `/switchboard/start-token` and `/switchboard/edge-header` are the stack's own and stay as they are): `SWITCHBOARD_AWS_REGION` and `SWITCHBOARD_HOST_STACK` only when they differ from `ap-northeast-1` and `switchboard-host`, and `SWITCHBOARD_HOST_ROLE_ARN` (the `OidcRoleArn` output) and `SWITCHBOARD_HOST_PARAMS` (the non-secret `--parameter-overrides`, space separated, e.g. `ImageId=ami-… VpcId=vpc-… SubnetId=subnet-… CloudFrontPrefixListId=pl-… BudgetEmail=… HostUser=… GitHubOidcProviderArn=…`). `deploy` builds a change set run by `DeployRole` and executes it only when it touches neither the launch template nor the instance; anything else is a person's deploy. The SAM transform (`aws:transform/Serverless-2016-10-31`) runs as `DeployRole` too, so `DeployRole` may create the transform's change set; `DeployRole` cannot change itself, so until a person has deployed a template with that permission once, the workflow's `deploy` fails (red) on `cloudformation:CreateChangeSet`.

## Narrowing who can reach it: countries and a Web ACL

Both are off by default (the template's parameters are empty, so the distribution is as before). They are switches for when something looks wrong, not always-on protection.

- **Countries**: `AllowedCountries=JP` (comma-separated ISO 3166-1 alpha-2 codes) makes CloudFront answer 403 to every other country, before the Starter or the instance. No extra cost. Remove it by deploying with `AllowedCountries=''`.
- **Travelling**: with `AllowedCountries` set, a trip needs a temporary extra country; there is no way in from abroad, so set it **before leaving**.
  - (a) Before the trip: open the Web UI's Settings → `海外から使う` (Use from abroad) (it goes to `/_auth/#countries`), log in with the passkey, and save the countries (2-letter codes, e.g. `US`), a start and an end (at most 90 days; an end is required; one allowance at a time). Saving and cancelling need a passkey check within 5 minutes. CloudFront takes a few minutes to apply it.
  - (b) It ends by itself: the Starter runs every 5 minutes and puts the whitelist back to `AllowedCountries` once the end has passed. If a redeploy puts the whitelist back to `AllowedCountries` while the allowance is in force, the next run restores the extra countries. With `AllowedCountries` empty (no restriction) nothing is touched.
  - (c) Forgot to set it, or want it back sooner while abroad: the page is not reachable from a country that is not allowed, so change `AllowedCountries` with your AWS permissions and redeploy (a person's deploy, as in the Countries line above). Every set, cancel, expiry and restore is one JSON line with `"log":"countries"` in the Starter's CloudWatch log group.
  - If the 5-minute run keeps failing (a missing parameter or permission, an SDK fault), a temporary country could stay allowed past its end unseen. So the Starter's errors have a CloudWatch alarm (`<stack>-starter-errors`: errors in each of three 5-minute windows) that mails `BudgetEmail` through an SNS topic; confirm the subscription AWS mails after the first deploy, or no mail arrives. On a mail, read the Starter's log group for the error and the `"log":"countries"` lines; to close the gap at once, set `AllowedCountries` by a deploy.
  - The first deploy of this feature changes the Boundary (a new `Countries` statement), so it is a person's deploy, not the workflow's `deploy`. Only the Starter's role may change the geo restriction (`cloudfront:GetDistributionConfig` / `cloudfront:UpdateDistribution` on this distribution); the instance cannot.
- **Web ACL** (rate limits per source IP: 100 requests in 5 minutes on `/_auth/`, 2000 in 5 minutes on everything; the numbers are constants in `aws/waf.yaml`): a Web ACL for CloudFront exists only in us-east-1, so it is its own stack. It costs money every month while it exists (2026-10 list prices: Web ACL USD 5, two rules USD 1 each, USD 0.60 per million requests).

```sh
aws cloudformation deploy --template-file aws/waf.yaml --stack-name switchboard-waf \
  --region us-east-1 --profile YOUR_PROFILE --tags Project=switchboard
WEBACL=$(aws cloudformation describe-stacks --stack-name switchboard-waf --query 'Stacks[0].Outputs[?OutputKey==`WebAclArn`].OutputValue' --output text --region us-east-1 --profile YOUR_PROFILE)
# then the host stack's deploy above with the extra overrides:  WebAclArn="$WEBACL" AllowedCountries=JP
```

Taking the Web ACL off: deploy the host stack with `WebAclArn=''`, then delete `switchboard-waf` (a Web ACL still attached cannot be deleted).

## Offload: docker checks too big for the instance

The rootless dockerd runs in `sb-dockerd.service` with `MemoryMax=1536M`. Checks that exceed that limit are killed. `sb-offload` runs them outside the instance instead, in one build of the stack's CodeBuild project `<stack>-offload`: a fresh arm machine with docker (privileged, `aws/codebuild/amazonlinux-aarch64-standard:3.0`) that goes away when the build ends. The machine's size is chosen per call: `--size small|medium|large` before the command, small when it is left out. sb-offload passes it as the build's `--compute-type-override`, so the project's own `BUILD_GENERAL1_LARGE` applies only to a build started without sb-offload. Anything else (`xlarge`, a typo) starts nothing and exits 2. The largest on the list is the project's own size, so a build through sb-offload never costs more than one started without it.

| `--size` | compute type | vCPU / memory | ap-northeast-1, on demand (checked 2026-10-22) |
|---|---|---|---|
| `small` (default) | `BUILD_GENERAL1_SMALL` (`arm1.small`) | 2 / 4 GiB¹ | USD 0.00425 a build minute |
| `medium` | `BUILD_GENERAL1_MEDIUM` (`arm1.medium`) | 4 / 8 GiB | USD 0.009 a build minute |
| `large` | `BUILD_GENERAL1_LARGE` (`arm1.large`) | 8 / 16 GiB | USD 0.020 a build minute |

¹ The price list's build row says 3 GB; the machine has 4 GiB. vCPU and memory checked on the instance with `nproc; free -m` at each size (2026-10-22).

Start with small and leave `--size` out. A type check or a test run usually fits there. Only when a check dies out of memory there, run it again one size up (`medium`, then `large`); a compose stack's checks (an image build plus the stack's services) can end up needing `large`. When the command itself exits 137 (a SIGKILL, which usually means out of memory), sb-offload prints the size to try next on stderr (`sb-offload: exit 137 usually means out of memory on small; retry with --size medium`); on `large` there is no next size, so it prints nothing. It reads only the command's own exit code: a step killed inside `docker build` or `docker compose up --build` usually makes the command exit 1, which prints no hint, so look for `exit code: 137` in the log too.

```sh
sb-offload docker compose up --build --abort-on-container-exit       # in the repository's work tree; small
sb-offload 'docker compose up -d --build --wait && uv run pytest tests/integration; docker compose down'
sb-offload --size large docker compose up --build --abort-on-container-exit   # the retry after it ran out of memory on small and medium
sb-offload 'nproc; free -m'                                                   # small: 2 vCPU
```

- What goes: the git work tree it is run in — tracked and untracked files with their uncommitted changes, not ignored ones (`.env`, `node_modules`), not the contents of an untracked clone inside it; a submodule's tracked files go — packed under `~/.cache` and put at `s3://<DataBucket>/offload/`. Nothing else: no runner login, no GitHub token, no file from the instance. The build's role may only read `offload/` and write its log group
- What comes back: the log, streamed to the terminal as it arrives (every 5 s), and the exit code: the command's own, 124 when the build hit the time limit, 130 when it was stopped, 1 when it failed before the command ran (the upload could not be unpacked), its state could not be read 3 times in a row, the start was refused for any reason but the limit of 2, or no build freed up in 15 minutes; 2 without a command, with a `--size` off the list, outside a git work tree, or without `/etc/switchboard-host.env` (below). A step before the build that fails (packing the work tree, reading `/switchboard/offload-project` before the deploy, the upload) exits with that tool's own code, which can be any value (the AWS CLI's 254 / 255, tar's 2); the tool's own error is on stderr, with no `sb-offload:` line
- What does not come back: anything the command starts. A compose stack's ports, a browser on its page, files it writes — only the log and the exit code. A check that needs localhost or bind mounts stays on the instance (`docker` itself is never sent off: `docker build` / `docker compose up` only print a one-line hint)
- It ends: whatever the command returns, the build ends and its machine is released. Ctrl-C (or TERM, a stopped Task) stops the build; so does sb-offload giving up on it. The project caps a build at 60 minutes and runs 2 at a time; CodeBuild refuses a third instead of queueing it, so sb-offload waits for a free one for up to 15 minutes. The upload is removed at the end; `offload/` also expires after a day. To check a build from the instance, `aws codebuild batch-get-builds --ids <project>:<uuid>` with the id from sb-offload's first stderr line (`sb-offload: sent the work tree … and started <project>:<uuid>`; in the cases below it is the only place the instance has it); the host role cannot list builds, so `aws codebuild list-builds-for-project --project-name <stack>-offload` (anything still `IN_PROGRESS`) needs a person's credentials or the console. Two gaps leave a build that sb-offload cannot stop, which then ends at the 60-minute limit (its upload goes with `offload/`'s one-day expiry): a Ctrl-C that reaches the whole process group while the start request is in flight, and sb-offload being killed outright (SIGKILL, the OOM killer, systemd-oomd; INT, TERM and HUP do stop the build)
- Without `/etc/switchboard-host.env` it says so and exits 2
- local-ci uses it too: on the instance, `bun scripts/local-ci.ts <PR>` runs its type check and `bun test` in two small builds at the same time (what goes, what stays on the instance and the cost: [docs/design/local-ci-offload.md](../docs/design/local-ci-offload.md))
- Cost (the price list for ap-northeast-1, on demand, checked 2026-10-22; the table above): billed per minute of the build, the machine's start-up included. `small` is **USD 0.00425 a build minute**, `large` **USD 0.020**. A 10-minute check 30 times a month is 300 minutes: about USD 1.3 on small, USD 6 on large. The log group (7 days) and `offload/` add next to nothing. The project carries the `Project` tag, so builds count toward the two budgets. For a month's ceiling: the budgets only notify; what bounds a build through sb-offload is its largest size (`large`), the 60-minute limit and 2 at a time (at most USD 2.40 an hour while both run). The host role can call `aws codebuild start-build` itself with a bigger machine (`xlarge` and up) or a longer limit (CodeBuild's overrides have no IAM condition): the budgets' mail is the check on that
- Turning it on: the `Boundary`, the instance role and `DeployRole` change, so (1) a person deploys the template (not the workflow's `deploy`), then (2) a rebuild, which installs `sb-offload` on the instance. Until (2) `sb-offload` is missing; until (1) it fails reading `/switchboard/offload-project`

## Deploys that replace the instance

What this is: a deploy whose change set modifies `LaunchTemplate` or replaces `Instance` — a new `ImageId`, UserData, `GitHubRepo`, `HostUser` / `HostHome` / `ReposDir`, `InstanceType`, `Market`, the disk.

What happens: a new instance with a new disk. The bootstrap restores sqlite from Litestream (the last seconds before the stop may be missing). The runners' logins on the old disk are gone, so log in to each runner again. A VPC origin in use cannot point at a new instance (`CannotUpdateEntityWhileInUse`). The two origins' logical ids therefore come from the `LaunchGeneration` parameter: with a new value, CloudFormation creates new origins, moves the distribution to them, and deletes the old ones once nothing uses them. Without one, the change set modifies the origins in place, fails and rolls back.

The GitHub workflow's `deploy` never runs this kind of change set: `aws/change-set-check.ts` stops it and prints why. A person runs it, from the repository root, with their own AWS login, as a person's deploy that lets the replacement through:

```sh
# 1. the change set: the change itself (e.g. ImageId=ami-…) and a new generation; parameters not named keep their values
SWITCHBOARD_HOST_PARAMS="ImageId=ami-… LaunchGeneration=$(date -u +%Y%m%d%H%M)" bun scripts/host-ops.ts person-deploy --allow-replace --yes
# 2. look at the change lines it printed: two VPC origins Add and two Remove, none Modify
# 3. with Market=spot, cancel the Spot request first (Start, stop, rebuild: With Market=spot); then the command it printed:
bun scripts/host-ops.ts person-deploy --execute=<change set ARN> --yes --allow-replace
```

Run these from a machine that is not the instance being replaced: `person-deploy` waits for the stack and detaches the role's permission at the end, which a terminated instance cannot do.

`--allow-replace` lets a change set that replaces the instance through; `aws/change-set-check.ts` still refuses one that would update a VPC origin in place (a missing `LaunchGeneration`), when it is made and again before it runs.

Then open the distribution's URL (`/_auth/`, then `/rescue/`) and log in to the runners again. Do not put `LaunchGeneration` in `SWITCHBOARD_HOST_PARAMS`: the stack keeps the last value, and later deploys leave it as it is.

Whose permissions the change set runs with: the role passed with `--role-arn`, or else the role the stack already has (`aws cloudformation describe-stacks --stack-name switchboard-host --query Stacks[0].RoleARN`), never your login once a role was passed. `person-deploy` passes the person's deploy role and `deploy` passes `DeployRole`, so each runs as its own role whatever the last one left attached. `DeployRole` can replace the instance, but it cannot change the `Boundary`: a deploy that changes the `Boundary` (the first deploy below, for one) is a `person-deploy`.

A stack deployed before `LaunchGeneration` existed: its first deploy of this template is one of these deploys, run by a person. It changes the `Boundary`, `DeployRole` and `GitHubOidcRole` (the LanguageExtensions transform), and it replaces the instance even when no parameter changes. The transform writes the parameters into the processed template as values (`ImageId: ami-…`, not `Ref: ImageId`), so CloudFormation sees a new `LaunchTemplate`, and `Instance` and both origins with it. So pass a new `LaunchGeneration` in this one too. Without it the change set modifies `HostVpcOrigin4` / `RescueVpcOrigin4` in place, and `aws/change-set-check.ts` refuses it. NoEcho parameters (the edge header) stay as `Ref`.

## Start, stop, rebuild

- Stopped: opening the URL shows the start page (CloudFront answers the instance's 502/504 with `/_start/index.html`), which goes to `/_auth/`: log in with the passkey, press `起動する` (Start)
- Running but not answering: `/_auth/` shows `停止する` (Stop) and `作り直す` (Rebuild) as soon as Switchboard does not answer (no 90-second wait) and says whether `/rescue/` answers. `停止する` sends StopInstances through the Starter (cookie + a passkey check within 5 minutes; running / pending only); when the machine stays stopping for 2 minutes the page offers `強制停止` (Force stop) (`Force: true`, after a confirmation). When it is stopped the page offers `起動する`. This is the way back from a stalled instance, a bootstrap that stopped halfway, or memory exhaustion; no EC2 console and no agent. On a healthy instance `/_auth/` moves on to Switchboard and never shows `停止する`: use `停止する` on the rescue page (`救援画面`, `/rescue/`) instead, which posts the same `/_auth/stop` and asks for the same passkey check, then `起動する` on `/_auth/` once the machine is stopped. That is also how to try stop and start on a phone without breaking the daemon first. The Starter's `ec2:StopInstances` is in the `Boundary` and the Starter's role, so it reaches a stack only through a person's deploy (the workflow's DeployRole cannot change the `Boundary`); until then `停止する` answers 403 from AWS
- No Spot capacity (`InsufficientInstanceCapacity`): the start answers 409 with `reason: "capacity"` and the page tries again every 15 seconds for 3 minutes, then says so and gives the button back. The Spot instance's type cannot be changed (EC2 refuses it for Spot); switching market or type requires replacing the instance (see Market)
- Scripts in `aws/host/`: at every start of `switchboard.service`, `sb-host-update` clones `main` again into `/opt/switchboard-host` (as UserData does, the token in a header), checks out the promoted release's sha there when it is in `main`'s history (otherwise `main`'s head, said on stderr), and, if every script parses and the new `sb-env` completes a trial run into a temporary file, puts `sb-env`, `sb-stop`, `sb-archive`, `sb-runner-sync`, `sb-offload` and itself into `/usr/local/bin`; when it cannot fetch, or the new scripts fail that check (or the 60 s the update may take of the unit's 90 s start run out first), the installed ones stay and the start goes on. It replaces itself only when moving forward in `main`'s history from the commit its installed copy came from (kept in `/opt/switchboard-host.updater`), so a promotion back to an older release keeps the pinning updater, start after start. The units and sb-rescue itself still change only with a rebuild. An instance built before this has no `sb-host-update`: it needs one rebuild to get it. The same start also applies the security updates of Amazon Linux 2023's latest repository (the `sb-security-update` unit; failures are in `journalctl -u sb-security-update`); a new kernel is used from the next stop and start
- The instance stops itself after 20 idle minutes and registers the next wake-up with EventBridge Scheduler (`switchboard-wake`)
- Rebuild: the Starter's `/rebuild` replaces the instance's **root volume** with one in its launch state (`CreateReplaceRootVolumeTask`); the instance, its id, its VPC origins and its Spot request stay. The instance must be running (EC2 requires it; a stopped one gets 409 "start it first"); EC2 reboots it, UserData runs again on the fresh disk and the bootstrap restores sqlite from Litestream. The bootstrap first applies the security updates of AL2023's latest release (the pinned AMI's own packages would bring a fixed CVE back) and, when one needs a reboot (a new kernel), enables the units without starting them and reboots once more, so a rebuild takes a minute longer then. Nothing in CloudFormation changes, so a failed rebuild leaves the stack as it was (EC2 keeps the old root volume attached when the task fails)
- Memory: `bootstrap.sh` makes a 2 GiB swap file (`memory.sh`, `vm.swappiness=10`, in `/etc/fstab`). `switchboard.service` uses `MemoryMax=85%`, `MemorySwapMax=512M`, `OOMPolicy=continue` and systemd-oomd's `ManagedOOMMemoryPressure=kill`. `MemoryMax` counts RAM only, so swap is capped separately. `MemoryHigh` is omitted because throttling can leave the UI unresponsive. Processes started by runners remain in the unit's cgroup even after `setsid`. Docker uses its separate `sb-dockerd.service` with `MemoryMax=1536M` and `MemorySwapMax=256M`. OOM kills or memory pressure can affect sb-rescue too. Use `停止する` → `起動する` on `/_auth/`, or Stop then Start in EC2, if the screen does not answer. Existing instances receive bootstrap changes through a rebuild.
- Memory alarms: the CloudWatch agent (`aws/host/cloudwatch-agent.json`, started by the bootstrap; a failed install is logged and the instance still starts) sends `mem_used_percent` and `swap_used_percent` to `CWAgent` every minute. Three alarms are there to be watched (CloudWatch → Alarms, or `aws cloudwatch describe-alarms --alarm-name-prefix <stack>`); they have no action: no mail, no stop, no reboot: `<stack>-memory` (memory at 80% or more for 5 minutes: the unit is capped at 85%, so a higher threshold may not be reached), `<stack>-swap` (swap at 20% or more for 3 minutes: the unit is at its 512M swap cap, which can precede a stall even when memory is below its alarm threshold) and `<stack>-disk-read` (EC2's own `EBSReadBytes` over 15 GB in each of 3 five-minute periods, so it still goes into ALARM when the agent has no memory left to report). Missing data is not an alarm, so a stopped instance is quiet. **When one is in ALARM and the screen does not answer: stop the instance and start it again** (open `/_auth/` and press `停止する`, then `起動する`; the EC2 console — Instance state → Stop, then Start — is the other way; the status checks stay green through this kind of stall, so they will not tell you). Cost: 2 metrics + 3 alarms. Order to turn it on: (1) a person deploys the template (the `Boundary` and `DeployRole` change, so `deploy` from the workflow cannot); (2) a rebuild, which is what installs the agent and applies the swap and the limits on an existing instance. Until (2) `<stack>-memory` has no data and stays quiet; `<stack>-disk-read` works from (1)
- Market: **on-demand** by default. Spot can be interrupted and may not restart for lack of capacity. An instance's market and type cannot be changed in place. Changing it replaces the instance: see Deploys that replace the instance. A deploy keeps every parameter not in `--parameter-overrides` at its previous value.
- With `Market=spot`: the Spot request is `persistent` (needed for "stop on interruption"): while it is open, a terminated instance is launched again outside the stack. Two things terminate the instance: a deploy whose change set **replaces** `Instance` — any change to the launch template (ImageId, UserData, the instance type, the disk) — and delete-stack. Both must be done by a person (the deploy: Deploys that replace the instance; the GitHub workflow's deploy refuses it). The AMI is a pinned parameter for this reason. Cancel the request right before either, not earlier — a cancelled request's instance can no longer be stopped, only terminated. If such a deploy rolls back after creating the new instance, CloudFormation terminates that one without cancelling its request: look for an instance tagged with the stack that the stack does not list, and cancel its request and terminate it
- Remove: cancel the Spot request, then delete the stack. The data bucket is kept (`Retain`); empty and delete it by hand when you are sure

```sh
RID=$(aws ec2 describe-instances --instance-ids <InstanceId> --query 'Reservations[0].Instances[0].SpotInstanceRequestId' --output text --profile YOUR_PROFILE --region <region>)
aws ec2 cancel-spot-instance-requests --spot-instance-request-ids "$RID" --profile YOUR_PROFILE --region <region>
aws cloudformation delete-stack --stack-name switchboard-host --profile YOUR_PROFILE --region <region>
```

## Must be confirmed on the first deploy

Run these checks on your own stack before relying on it. Check restoration with your own data and keep a separate backup before replacement or removal.

- The account's unreserved Lambda concurrency allows the Starter's reserved 5 (a new account may have a limit of 10 in total, and AWS keeps 10 unreserved: if the deploy refuses it, drop `ReservedConcurrentExecutions` or raise the quota)
- `CloudFront-Viewer-Address` reaches the Starter through the `/_auth*` origin request policy (the login's rate limit is per viewer; without it the first X-Forwarded-For entry is used)
- `wafv2:GetWebACL` on `global/webacl/*` in us-east-1 (the DeployRole) is enough for CloudFront's `UpdateDistribution` to attach a Web ACL: confirm it the first time you set `WebAclArn`. `AllowedCountries=JP` from a non-JP address answers 403, and removing it restores the answer
- CloudFront accepts a VPC origin for an instance in a **public** subnet (the docs list a private subnet as a prerequisite). If not, the fallback costs money and is the user's choice (see "The way in")
- Rebuild: after `CreateReplaceRootVolumeTask` (launch state) the instance reboots on a fresh root volume and UserData runs again — cloud-init keeps its once-per-instance marker under `/var/lib/cloud` on the root volume, which the replacement discards. If it does not run, the bootstrap has to be started another way
- The boundary's KMS statement (through SSM and EC2 only) is enough for: reading the SecureStrings on the instance, the Starter's `StartInstances` on the encrypted root volume, and the root volume replacement
- The Starter's `CreateReplaceRootVolumeTask` permissions (instance, task, volume, the AMI's snapshot and image) are enough for a launch-state replacement
- The root volume a replacement creates keeps the `Project` tag (the launch template tags volumes only at launch); if not, tag it after each rebuild or the disk drops out of both budgets
- Litestream reaches the data bucket with the region from the config and no `s3:GetBucketLocation` (restore on first boot, replicate after)
- `claude auth status` exits 0 for a `claude` that has only `CLAUDE_CODE_OAUTH_TOKEN` (the setup-token wrapper, `docs/design/cloud-hosting.md` §9)
