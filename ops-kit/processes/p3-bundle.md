# p3-bundle — まとめ型

利用者が選んだ複数の PBI を、1 つの worktree・1 本の枝でまとめて実装し、まとまりごとの PR をスタックにして入れ切る。PBI を 1 件ずつ工程型で進めると、同じファイルや同じ判定を触る PBI が並列ガードの重なりで後回しになり続けたり、分割・改名・移動のような構造の変更が PBI ごとの小さな差分に散って整合が取れなくなったりする。束にして、根の課題ごとに設計の正本を 1 つにし、まとまりごとに並行に実装して、最後に合わせる。

- 向かない対象: 外部や利用者の判断が関門のもの（判断待ちの答えが要るもの、お金・認証・他の持ち主の操作に関わるもの）、1 件で閉じていて重なりの無いもの（工程型か直行型の方が速い）
- 緩めるもの: 途中の型検査と一式のテスト（実装の間は各自が自分のテストファイルだけ回し、型検査と影響範囲のテストは (4) で 1 回）、PBI ごとの Task の分解（まとまりごとにサブエージェントへ渡す）、PBI ごとの PR（まとまりごとの PR にする）
- 緩めないもの: マージ判定（`scripts/merge-gate.ts`）、不変条件（`ops-kit/invariants.md`）、主レビュアーのレビュー、歯止めの検査（lint・file-size・public-docs・issue-refs など。検査を緩めず製品の側を合わせる）、途中の版を昇格させないこと
- 選ぶのは利用者が始めたときだけ（`auto` を持たない。バックログの自動処理はこの型を選ばない）

入口は 1 つ。Task が受け取るのは入口の文だけなので、段ごとに入口を分けると、次の段の文を読みにリポジトリの外のファイルを開くことになる。代わりに、入口の文が PBI の決定ログとスタックの PR の状態を見て、済んでいない段から続ける。

穴: `{{pbis}}` = 利用者が選んだ PBI の番号の並び。`{{reviewer}}` = 主レビュアーの呼び方（アプリのレビューの設定で決まる。別のランナーか、同じランナーの新しいセッション）。

束の止め（定期実行と昇格の止め）と解除は `scripts/bundle.ts`、状態は `GET /api/bundle` が持つ。

## entry bundle

次の PBI をまとめて、1 本の枝で実装して入れ切ってください: {{pbis}}。始める前に、各 PBI の決定ログと開いている `sb/bundle-*` の PR を見て、済んだ段を確かめ、下の 1〜7 のうち済んでいない段から続けます（済んだ段はやり直さない）。

どの段でも:
- main の作業ツリーでは作業しない。枝は `sb/bundle-<topic>`、worktree は CLAUDE.md の規則に従う
- 始めたときに止めた定期実行と昇格の止め（`GET /api/bundle` で見える。戻す先の版も）を確かめてから (3) に入る
- 使用上限や会話の長さで止まって再開したら、スタックの PR と PBI の決定ログから済んだ段を読んで、続きから進める。段の終わりは各 PBI の決定ログに「YYYY-MM-DD: 束（Task <id>）の（<段の番号>）済み」と書き、(6) は「束（Task <id>）: スタックを入れ切った」（最後の PR をマージした直後）「束（Task <id>）: 止めを解いた」「束（Task <id>）: 昇格した」をそれぞれ書く。読むのは自分の Task の id の行だけ。止めを解くのと昇格は、自分の id の「スタックを入れ切った」がある場合だけ続きから行う（開いている PR が無いことや止めが残っていることからは決めない）

1. **集める**: 各 PBI を `ops-kit backlog view <n> --fresh` で読む。外すもの（`needs-decision`・`on-hold` が付いたもの、外部や利用者の判断が関門のもの、CLAUDE.md やスキルなど利用者の指示のファイルを書き換えるもの）は、理由を各 PBI の決定ログに 1 行書いて束から外す。残すものには「YYYY-MM-DD: 束（Task <id>）に入れた」と書き（<id> は環境変数 `OPS_KIT_TASK_ID`）、並列ガードの `claim` を取る
2. **切る**: 根の課題ごとにまとまりを切り、「正本を 1 つ」をまとまりごとの設計の指示にする。許可・マージ判定・昇格・外からの取り込み・設定の権限を触るまとまりには安全の印を付ける
3. **入れる**: 1 つの worktree・1 本の枝で、まとまりごとにサブエージェントへ並行に実装させる。途中の型検査と一式のテストは求めず、各自は自分のテストファイルだけ回す
4. **合わせる**: 型検査と `bun scripts/test-changed.ts` で食い違いを直す。歯止めの検査（lint・file-size・public-docs・issue-refs など）は緩めず、製品の側を合わせる
5. **攻める**: {{reviewer}}に main と読み比べさせ、指摘を「main と比べて後退」と「main と同じか良い」に分けさせる。後退だけ直し、残りは要望 Issue にする。安全の印のまとまりは、実装の直後に別のランナーが攻める側から読む
6. **入れ切る**: まとまりごとの PR をスタックにし（`.claude/skills/stacked-pr-delivery/SKILL.md`）、全部の PR の指摘を処理してから、下から順にマージ判定 `scripts/merge-gate.ts` を通してマージする（`[聞く]` は Task の会話で聞く）。途中の版は昇格させない。最後の PR をマージしたら「スタックを入れ切った」の行を書き、`bun scripts/bundle.ts release` で止めを解いてから `bun scripts/promote.ts <main の sha>` で昇格する
7. **確かめる**: マージの前に確かめられなかった受け入れ条件を、種類（画面・E2E・実ランナー・日数の観測）ごとに 1 つの要望 Issue にまとめ、各 PBI の結果節に残りとその要望の番号を書く。全部済んだ PBI だけ閉じる。閉じた PBI も残した PBI も、(1) で取った並列ガードの占有を `bun scripts/parallel-guard.ts release <PBI> <理由>` で外す（残す PBI は理由に残りの要望の番号を書く）

返答に、束に入れた PBI と外した PBI（理由つき）、マージした PR、残りの段、聞いていること（あれば）を書いてください。
