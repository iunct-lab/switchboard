# PBI → Tasks（Ready 化）

目的: PBI の受け入れ条件を**全部**、実装者が迷わない Task に落とし、**Task が全部 Done なら PBI の受け入れ条件が全部満たされる**関係を作る。
Task の親は必ずその PBI（sub-issue）。Task は 1 PR で終わる大きさ。

## 手順

### 1. PBI を確かめる

`ops-kit backlog view <num> --fresh` で本文を読む（Task の作成・Project も `ops-kit backlog`。`issue-workflow` の「操作」）。無ければ**先に直す**（`request-to-backlog` の書式。決定ログに日付つきで「書き直し」）:
ユーザーストーリー / 検証つき受け入れ条件 / スコープ外 / `**Story Points**: N` / `## 元要望`。`ops-kit lint --fresh` が exit 0。

元要望（`## 元要望` の Issue）の原文も読む。PBI の解釈が原文からずれていたら PBI を直してから分解する。

受け入れ条件の誰かに伝える・投稿する行（〜に知らせる、〜にコメントする）に、投稿先（リポジトリ `owner/name` と Issue の番号か URL）が名指しされているか確かめる。無ければ Task を切らずに `## 判断待ち` で投稿先を聞く（`issue-workflow` の「Ready の判定（PBI）」の 5）。

### 2. コードを読む

受け入れ条件ごとに「今どこで何が起きているか」を確かめ、触る場所を `path:line` で控える。読むもの:
README の構成と設計ルール（場所は CLAUDE.md）、該当 `docs/design/*.md`、当該のソースと既存テスト（同型のテストをどう書いているか）、部品のあいだで共有する型の定義。
似た仕組みが既にあるか探す（`grep -rn` / `Explore` エージェント）。**あるなら同じ形で作る**（例: 新しい自動選択は、既にある自動選択の仕組みと同じ形の関数にする）。
**触らないが前提が変わる場所**も控える: 既存の流れに条件で新しい道を足すか、既存の値・記録・状態の意味や鍵を変えるなら（`task-to-pr` の「古い前提の一覧」と同じ見分け）、古い道の前提に頼る箇所を、語を決めて `ops-kit old-paths list HEAD <語>…` で挙げ、出た項目を Task の本文に貼る（実装者が PR で 1 行ずつ確かめる最初の一覧）。当たらなければ「古い前提を持つ既存の箇所: なし」。
画面の見た目・操作を変える PBI で、`**画面イメージ**:` の行が無い・その成果物が消えている・コードを読んで画面の決めた形が変わったなら、Ready にする前に `issue-workflow` の「画面イメージ」の「問いの無い PBI」で作り直して行を書く（差し替えたら 5 の決定ログに 1 行）。

### 3. 設計チェック（シンプルさ）

Task に書く前に、案を次で削る。**通らない項目は Task の本文に「設計チェック: 〜はしない（理由）」と 1 行残す**。

**値は 2 つに分ける（前提）**: 環境・運用で変わる値（容量・件数・期間・間隔・上限など、マシンの大きさや使い方で適値が変わるもの）は、環境から導く（例: ディスクの割合）か、既定値を持ったうえで PR なしで上書きできる形を既定にする。変えられない形を既定にしない（変えられないことに理由があるときだけ、その理由を設計チェックの行に書く）。決めれば済む値（形式・方針・経路の選択）は決めて、設定にしない。下の表の YAGNI は使う当ての無い機能・口に効かせ、値を変えられる余地には効かせない。

| 入れない | 代わりに |
|---|---|
| 後方互換の層（古い形式も読む、旧 API も残す、非推奨のまま置く） | 変える。データは 1 回の移行（DB の migration）。利用者と外部クライアントの前提は CLAUDE.md（書いていなければ互換層は入れない） |
| 一度しか使わない抽象（interface + 実装 1 つ、汎用ヘルパ、プラグイン機構） | 具体的な関数 1 つ。2 つ目が来たら抽象化する |
| 機能の入り切り・経路の切り替えの設定・フラグ（決めれば済む値） | 決める。上の前提の、環境・運用で変わる値の上書きの口はここに入らない |
| 環境・運用で変わる値を固定の定数にする | 環境から導くか、既定値つきで上書きできる形。上書きの口はリポジトリに既にある形（環境変数・設定）に揃える。既定値は安全側のまま |
| ランナー / アダプタなど実装先ごとの分岐 | 1 本の経路（例: ファイルはパスで渡す。アダプタは触らない） |
| 表示・集計のための記録（PR や Issue のコメント、ログ）や、ゲートされる側が書ける値（環境変数・枝の名前・本文の印）をゲートの鍵にする | 判定が自分で読む差分か、記録の正本を持つ側（アプリ）の記録。この行は「既存に足す」の行より先に効く |
| 新しいテーブル・エンドポイント・画面 | 既存の表 / API / 部品に列・項目を足す。足せない理由があるときだけ新設 |
| 繰り返し呼ぶもの（定期・ポーリング・接続し直し・Task ごと）の、重さを見ない使い回し | 呼ぶ頻度 × 応答の大きさ（今の実データでの値と 3 か月後の見込み）を Task の本文に `負荷: <頻度> × <大きさ>（今 <値> / 3 か月後 <値>）` の 1 行で書く。既存の口の使い回しでも、その値が大きければ要るものだけを返す形（引数・列を足す）にするか新設する |
| 新しい依存パッケージ | 標準 API か既存の依存。足すならライセンス（リポジトリのライセンスと互換。CLAUDE.md）を確かめる |
| アプリが持つ可変の値を doc に写す DoD | 書かない（`issue-workflow` の「アプリが持つ可変の値を写さない」）。docs の完了条件を加える条件も同節に従う |
| 「あとで使うかも」の口 | 書かない。YAGNI（効かせる範囲は上の前提） |
| 数字なしに、レビュー・再チェック・マージ判定の決まりを厳しくする・緩める（「安全の側なので」「念のため」） | 背景に往復の表（リポジトリの記載が名指しする）の該当の行があるかを見る。無ければ Ready にせず `## 判断待ち` で止める（`request-to-backlog` の「3. PBI を書く」）。リポジトリに往復の表が無ければ「表が無いので数字は書けない」と書いて進む（前提の節が無いときと同じ形） |
| 今は動いていない仕組み（止めている CI・自動化、無効にした定期実行）を理由に、安全の検討を省く | 動かしたときに起きることで判断する。権限・入口は、自動化に使われたとき・乗っ取られたときに何ができるかで考え、今止まっていても塞ぐ（一時的に止めているものは、動かしたときに穴になる） |
| 頼まれていない OS・環境（別の OS、別のサービス管理）の対応・手順・検証 | 足さない。要望の各項目が利用者の言葉かエージェントの推測か（`request-to-backlog` の「誰の言葉」）を分け、利用者が名指ししていない環境はスコープ外に書くか落とす |
| 最初の実使用に要らない自動化（定期実行、偽の相手でのリハーサル） | 手動の手順を先に。自動化は別の Task に残し、節目（公開など）を過ぎたら着手する。手動を先にするのは節目を止めないためで、自動化をやめる意味ではない |
| 別 OS / 実機 / 課金でしか検証できない工程 | Task にしない。PBI のスコープ外か、受け入れ条件の行に `（利用者確認: …）`（`issue-workflow` の「利用者確認の項目」） |
| どのリポジトリにも要る仕組みを、このリポジトリの中だけに作る | 共通キットに置く（`request-to-backlog` の「どのリポジトリにも要る仕組み」）。PBI がこのリポジトリの中だけを前提にしていたら、決定ログに書いて `## 判断待ち` で止める（勝手に置き場所を変えない・個別に作らない） |

例: 2 秒ごとの状態表示が全件の Task 一覧（実データで MB 単位、件数とともに増える）を読む使い回しは、`負荷` の行を書いた時点で引っかかる。必要なのは running と waiting の Task だけ。

設計原則との衝突（承認を迂回する既定値、ベンダ CLI のコード取り込み、鍵やテレメトリ、ランナー必須化）は Task にしない。PBI の決定ログに書いて止める。

PBI のユーザーストーリーが CLAUDE.md（`AGENTS.md`）の前提（信頼モデル・使い勝手）と矛盾していたら（この手順より前に作られた PBI など）、Task にしない。PBI に `## 判断待ち`（`**進め方**: 止めて待つ`、ラベル `needs-decision`）を出し、Ready にしない。照らし方は `request-to-backlog` の「2.5 前提と照らす」。

### 3.5 またぐ条件の確認

**当たる PBI**（見分けはここだけ）: 複数の部品か Task にまたがって状態を持つ / 外から取ったものを動かす / 更新や昇格 / 権限 / 保存の形を変える。当たらなければ決定ログに `またぐ条件: なし（理由）` の 1 行で済ませ、4 へ（文書だけ・1 つの部品だけの PBI はこれ）。

当たるなら、Task を切る前に次の 4 つを PBI の決定ログに書く（受け入れ条件に無くても、どの Task にも割り当たらない条件を残さないため）:

1. **守る条件**を 1 文ずつ（例: 確認した版だけが上がる）。決定ログやスコープ外が名指しする脅威・失敗も条件にする
2. 条件ごとに、それを通る**入口の一覧**（自動・手動・入れ直し・やり直しなど。コードを `grep -n` して挙げる）
3. **失敗したときの扱い**（止める / 頼み直す）と、似た既存の仕組みと同じ形かどうか（違う形にするなら理由）
4. 部品の間で渡す**値の意味**と、その値を既に読んでいるコード（`path:line`。2 の `ops-kit old-paths list` の出力）

### 4. Task を切る

指示のファイル（CLAUDE.md・AGENTS.md・スキル）は、それだけの Task に分ける（テストは同じでよい。混ぜた PR は判定が `[分ける]` で止め、指示のファイルは `instructions` で聞く）。

触る場所はリポジトリからの相対パス（`src/db.ts`、ディレクトリなら末尾に `/`）で書く。並列ガード（CLAUDE.md。`pbi-complete` の「並列で動かす」）の `overlap` がこのパスで他のセッションとの重なりを見る（パスの無い Task は判定できず着手できない）。付いてくるファイル（名指ししたファイルの隣のテスト、設計の文書 `docs/design/*.md`、公開の一覧 `ops.config.json` の `publicSync.include` / `exclude` のうちその PR 自身が足す・消すファイルの行）は名指ししなくてよい（マージ判定が通す）。判定の読み方は `issue-workflow` の「Task 粒度チェック」1。
粒度は `issue-workflow` の「Task 粒度チェック」6 項目（場所の名指し / 番号つき手順 / 満たす受け入れ条件 / コマンドで書ける検証 / 1 PR ≤ 500 行 / 利用者の判断点の明示）。
順番の目安: **共有の型 → 中核 → 周辺（アダプタなど）→ UI → 実構成での確認**。前の Task・ほかの PBI の成果を使うなら、本文に決まった 1 行 `**前提**: #N, #M`（PR のマージが動いている版に入るまで待つなら `#M（リリース）`、無ければ `**前提**: なし`）。並列ガードとデーモンが読むのはこの 1 行だけで、自由文の「前提: #K が Done」は読まれない。番号には要る成果（PR）を書く。番号と `（リリース）` の書き方は `issue-workflow` の「PBI 本文」の `**前提**:` の行と同じ。ほかの PBI の Task を待つ順、決定ログや `## 回答` で決まった順もこの行に書く。`## Tasks` の着手順の行や手順の自由文（「#K の後」「#K のマージ後」）だけに書かない — lint が warning で出す（#2149）。同じ PBI の Task の順は前提にしなくてよい（スタックの順）。
日数の経過を待つ受け入れ条件を確かめる Task は、「〜日後に始める（それより前なら止めて待つ）」とは書かず、「期日を書いて止まる → 再開したら集計して結果を書く」の手順にする。期日の起点は、その変更のマージ（リリースが要るなら昇格）の後で、起点が決まった時点で絶対の日時にする。手順の型: 1. 起点の後の期日（ISO 8601 のタイムゾーンつき日時）を決めて Task と PBI に書く 2. 期日を書いて止まる（止まり方は `pbi-complete` の「期日を待つとき」。手で始めた Task も同じ段落） 3. 再開したら検証の欄の集計を回し、結果を Issue に書く 4. 受け入れ条件が全部埋まれば PBI を閉じる。

Spike が要るなら timebox と成果物（`docs/design/<name>.md`）を書いた Task にする。

被覆表を作ってから起票する（本文には書かないが、PBI の決定ログに残す）:

```
受け入れ条件 1 → Task A
受け入れ条件 2 → Task A, B
…
守る条件 1 → Task B → 証明するテスト（<file> の "<name>"）
```

守る条件（3.5）は 1 つずつ、**1 つの Task** が、条件の両側を本物の実装でつないだテスト（偽にしてよいのは外のサービスだけ。両側が偽のテストは、つないだときの条件を証明しない）を検証の欄に持つ。その Task の本文に `守る条件:` の行で書く。
覆われない条件（受け入れ条件も守る条件も）があれば Task を足す。**条件をスコープ外に移すのは利用者の判断**（要件の変更）: PBI の決定ログに理由を書き、`## 判断待ち`（`**進め方**: 止めて待つ`、ラベル `needs-decision`。`issue-workflow` の「判断待ちの出し方」）で利用者に聞き（画面に関わる問いは同じ節の画面イメージを添える）、返事があるまで Ready にしない（headless でも同じ。勝手に条件を削って Ready にしない）。

```bash
ops-kit backlog create --title "Task: <触る場所 — 何をするか>" --label type:task --body-file "$W/task.md" --parent <PBI番号>     # W=$(mktemp -d "${TMPDIR:-/tmp}/<リポジトリ名>.tasks<PBI>.XXXXXX")。固定の /tmp/task.md にしない
ops-kit backlog triage <num> <P0-P3> <PBI番号> Backlog     # 親 = PBI
```

Task 本文（`.github/ISSUE_TEMPLATE/task.yml` の見出し。「やること」の末尾に設計チェックの 1 行）:

```
## 親 PBI            #N
## やること           1 段落。触るパッケージ / ファイル。満たす受け入れ条件: 親 PBI の n, m
**前提**: #K         （無ければ **前提**: なし。字下げせず行の頭に置く）
                     設計チェック: 〜はしない（理由）/ 既存の〜に足す
                     負荷: <頻度> × <大きさ>（今 / 3 か月後）。繰り返し呼ぶものが無ければ「負荷: なし」
                     守る条件: <この Task が担う条件を 1 行。証明するテストは検証の欄>。無ければ「守る条件: なし」
                     古い前提を持つ既存の箇所: <`ops-kit old-paths list` の項目>。当たらなければ「なし」
## 手順              1. path: 何を（関数名・型名・エンドポイント・設定キーを決めて書く） 2. … （3〜6 ステップ）
## 検証              テストのコマンド（CLAUDE.md）で <file> の "<name>" が pass / curl … | jq .<key> / Chrome で <操作> → <結果>
                     「〜の無い環境で」「〜の道で」と言う条件は、その環境・道に入っていることを確かめるテストにする（`task-to-pr` の 4）
## 完了条件 (DoD)     - [ ] テスト追加（既存への追加・軽い階層を先に検討） - [ ] typecheck / test green - [ ] 実構成で確認 - [ ] 結果コメント
```

満たす条件が `（マージの後: …）` の行なら、「実構成で確認」は PBI の行に回る（Task はマージで閉じる）。

### 4.5 ゲートの鍵（ゲートの PBI だけ）

ゲートの PBI（子 Task がマージ判定・`gh` の前段・昇格・許可の記録のファイルを名指しする。Ready にするコマンドが止める）は、本文に `## ゲートの鍵`（`**鍵の変更**: あり|なし` の行と、鍵・誰が書けるか・どこで読むか・利用者の操作の表）を書く。`あり`（Task が書ける値を鍵に足す・変える）なら、同じ節を写した `## 判断待ち`（`**進め方**: 止めて待つ`）を出して画面の回答を待つ（Task が書いた回答は数えない）。`なし` の根拠は決定ログに 1 行。止まったら出た文のとおりに足す。

### 5. PBI を Ready にする

本文は `ops-kit backlog view <PBI> --fresh --json | jq -r .issue.body > "$W/pbi.md"` で取り（`--fresh` で GitHub の新しい本文を読む）、書き足して `ops-kit backlog edit <PBI> --body-file "$W/pbi.md"` で戻す（`.body` は `null` になる）。

1. PBI の `## Tasks` に着手順を 1 行（`sub-issue 参照。順番: core → web`）
2. 決定ログに「YYYY-MM-DD: Task 分解（#a, #b, #c）。またぐ条件: …（3.5。無ければ「なし（理由）」）。被覆: …。Story Points N → M（理由）」
3. `issue-workflow` の「Ready の判定（PBI）」の 5 つを確かめる（1 の投稿先の名指しを含む）
4. `ops-kit backlog set <PBI> Status Ready`
5. `ops-kit lint --fresh` → exit 0

## 報告（利用者への返事の型）

```
PBI #<num> を Ready にしました（Task <n> 件）。
| Task | 触る場所 | 満たす条件 | 前提 |
| #..  | ..      | ..        | ..   |
設計で決めたこと: <入れなかったもの 1〜3 行>
利用者の判断が要る箇所: <あれば>
次: /task-to-pr #<最初の Task> または /pbi-complete #<num>
```

## やらないこと

- Task を 1 件作っただけで Ready にする（受け入れ条件の被覆が条件）
- 守る条件に、担う Task と証明するテストの割り当てが無いまま Ready にする
- 「適切な場所に」「必要に応じて」の手順。名前を決めて書く
- PBI の願望をそのまま Task にする（`issue-workflow` の「PBI と Task の境界」: 本文 1 行の Task が膨らんで Windows まで着手した）
- 実装しながら設計を決める。決めるのはここ。実装で変わったら Task と PBI の決定ログを直す
